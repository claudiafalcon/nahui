## ID001 — Plugin-provided MCP tools are unreliable for spawned subagents around connection timing (not a structural block)

**Status:** Accepted, **corrected** from an earlier overconfident diagnosis. First recorded 2026-08-02; corrected same day after direct counter-evidence.

**Corrected root cause:** This is **not** a structural "subagents can never get plugin-MCP tools" limitation, as this entry originally claimed. Direct evidence within this same session contradicts that: `ui-designer` successfully used live Figma tools across two separate spawns (a full 51-call screen-assembly build, and a later 5-call fact-check that returned real, previously-unseen data), and a diagnostic `ux-critic` spawn — dispatched specifically to re-test this — also got clean access to `get_metadata`/`get_screenshot`/`get_design_context`/`whoami` on the first call. The actual pattern: Nahui's Figma MCP server is registered as a **Claude Code plugin** (`"enabledPlugins": {"figma@claude-plugins-official": true}` in `~/.claude/settings.json`), and this project directly observed that plugin's connection **drop and reconnect mid-session** (visible in a system reminder: "MCP servers have disconnected... plugin:figma:figma", followed shortly by "MCP server reconnected"). The most likely explanation for every failure observed: **a subagent that spawns while the plugin's MCP connection is down (or not yet established) gets no MCP tools for its entire run, with no mid-run reconnection** — not because subagents are structurally barred from plugin tools, but because tool binding is resolved once at spawn time and a subagent has no equivalent of the main thread's retry/reconnect path.

This means: **before concluding a subagent is missing MCP tools due to a platform limitation, re-test with a fresh, minimal diagnostic spawn first** (see the ux-critic test in this entry's history) — a single failure is not sufficient evidence of a structural block, since connection-timing flakiness produces the identical symptom.

**Evidence:**
- **Failure observed twice**, both real: `ui-designer`'s very first build dispatch couldn't load `ReadMcpResourceTool`/`ListMcpResourcesTool` (worked around via inlining the skill content directly into the dispatch prompt); `ux-critic`'s first post-config-fix dispatch reported `get_metadata`/`get_screenshot` entirely absent despite correct frontmatter.
- **Success observed three times**, contradicting a structural read: `ui-designer`'s full 18-screen build (51 tool calls, all succeeded); `ui-designer`'s later fact-check dispatch (5 tool calls, returned real content-height data Main never supplied); a dedicated `ux-critic` diagnostic re-test (1 call, succeeded cleanly) run specifically to check current tool availability.
- The Figma plugin MCP connection was directly observed disconnecting and reconnecting within this same session via explicit system reminders — real, session-visible connectivity instability, not inferred.
- **[GitHub #25200](https://github.com/anthropics/claude-code/issues/25200)** and **[GitHub #13605](https://github.com/anthropics/claude-code/issues/13605)** both describe custom/plugin subagents failing to access MCP tools — relevant background reading, but this project's own direct, repeated evidence of the *same tool working for the same agent type in other spawns* means these issues describe a related failure mode, not proof that Nahui's specific setup is permanently, structurally broken. Don't cite these as settled proof of a structural block for this project without a fresh failed diagnostic to back it up.
- Deferred/lazy tool resolution (`ToolSearch`) is confirmed main-thread-only — this part of the original diagnosis holds. It just isn't the reason subagents fail; when a subagent's MCP connection is live at spawn time, its declared tools are directly callable with no `ToolSearch` step needed (confirmed above), so the earlier theory that subagents categorically lack a resolution path was also not quite right — they don't need one when the connection is actually up.

**Impact on governance:** Intermittent, not permanent — affects the standard review pipeline (`company/CLAUDE.md`'s Execution loop and UX Remediation cycle) only on the specific occasions a subagent happens to spawn during a connection-down window. `ux-critic`'s Medium/High-Fidelity reviews and `ui-designer`'s build steps both need live Figma access to do their actual job (checking the rendered artifact, not just spec text) — most of the time that access works, but any given spawn could silently fail if the plugin connection is mid-reconnect at that exact moment, and the subagent has no way to recover mid-run.

**Recommended first step, every time:** before assuming a Figma-dependent subagent is blocked, **run a minimal one-call diagnostic dispatch first** (same shape as the `ux-critic` test above — one `get_metadata` call, report success/failure, nothing else). This is cheap and gives a real current answer instead of reasoning from a stale prior failure. Only fall back to the evidence-provider model below if the diagnostic itself fails.

**Fallback operating model, when a spawn genuinely can't reach Figma — evidence provider only, never a substitute:** **Main's role is strictly limited to collecting factual evidence** — screenshots, `get_metadata` structural dumps, bound variable/style values, file references, measurements. Main does not interpret that evidence, does not classify severity, does not decide what's correct, and does not make the fix itself. Main hands the raw evidence to the specialized subagent inline in its dispatch prompt (the same inline-content pattern already used to work around `ui-designer`'s inability to load its mandatory Figma skill), and that agent performs its actual job against real evidence instead of spec text alone:

- **All UI design decisions remain owned by `ui-designer`** — layout, component choice, visual treatment, any fix to a Figma frame.
- **All UX findings and severity classifications remain owned by `ux-critic`** — Blocker/Major/Minor/Suggestion calls, and the reasoning behind them, are never Main's to state as conclusions, even when Main is the one who looked at the screenshot.
- **All consistency verification remains owned by `reviewer`** — Foundation-compliance sign-off is never inferred by Main from evidence it gathered itself.

Main does not shortcut this even for a fix that looks small, obvious, or purely mechanical — "narrow enough that Main can just fix it directly" is exactly the failure mode this section forbids. If evidence points to an unambiguous problem, Main still routes it to the owning agent to confirm and fix, rather than pre-empting that agent's judgment. This is a hard rule, not a case-by-case judgment call for Main to make.

This is explicitly a **workaround for a platform constraint, not a change to who owns what decision.** Preserves the existing Decision Ownership and UX Remediation policies in `company/CLAUDE.md` unchanged — Main was, and remains, a coordinator and persister of approved work, never the author of the review or the design.

**Better workaround discovered 2026-08-03, supersedes manual inlining as the first thing to try:** the `figma-use` (and presumably every other Figma plugin skill, e.g. `figma-generate-design`) skill content is cached locally on disk, readable directly with the `Read` tool — no `ReadMcpResourceTool`/`ListMcpResourcesTool` needed at all. Path pattern: `~/.claude/plugins/cache/claude-plugins-official/figma/<version>/skills/<skill-name>/SKILL.md` (confirmed present at version `2.2.87` this session; the version directory will change as the plugin updates — `Glob` for `~/.claude/plugins/cache/claude-plugins-official/figma/*/skills/figma-use/SKILL.md` rather than hardcoding a version). Any agent with a plain `Read`/`Glob` tool (which `ui-designer`, `ux-critic`, and `reviewer` all already have) can self-serve the skill content this way, without needing Main to inline anything into a dispatch prompt. **When `ReadMcpResourceTool`/`ListMcpResourcesTool` are unavailable, try this local-cache read first, before falling back to asking Main for an inlined copy** — it's faster (no round-trip to Main), works identically to the "real" resource read, and avoids the trust/provenance concern one `ui-designer` instance raised earlier this session about acting on content pasted into a chat message (reading a local file directly is not subject to that concern the same way).

**Future options:**
- **Standing practice going forward:** always run the one-call diagnostic before a Figma-dependent dispatch that matters (a real review/build step, not throwaway exploration) — cheap insurance against losing a whole dispatch to a connection-timing miss.
- **If failures start recurring frequently enough to be a real cost** (not just the two observed so far): worth checking whether migrating the Figma MCP server from a plugin registration to a project-level `.mcp.json` entry changes reconnection behavior — untested in this project, no evidence either way yet.
- **If Anthropic's plugin-MCP connection handling changes**, or if reconnection-during-an-active-subagent-run ever becomes possible, revisit whether the diagnostic-first step is still necessary or can be dropped.
- The GitHub issues cited above (#25200, #13605) are worth occasionally re-checking for updates, but this project's evidence base doesn't currently support treating this as the settled, permanent block those issues might describe for other setups.

Do not re-investigate this from scratch — check this entry first if a future subagent reports missing MCP tools despite correct-looking frontmatter.

**Addendum — a riskier variant of this gap, observed 2026-08-02:** most `ui-designer` instances hitting the missing-`ReadMcpResourceTool` gap correctly stop and flag it, per their own instructions. One instance (the `inventory.md` remediation pass) instead proceeded to call `use_figma` without the mandatory skill loaded, reasoning on its own that the fix was "narrow, low-risk" — and flagged the deviation only in its completion report, after the fact. The actual edits checked out fine on independent verification, but the pattern itself — a subagent overriding its own explicit mandatory-prerequisite rule based on self-assessed risk, rather than stopping — is a real behavioral risk worth watching for, independent of whether any single instance happens to get away with it. If a future `ui-designer` report mentions proceeding without the skill loaded, don't wave it through solely because the outcome looks fine — route it through the normal verification pass (`ux-critic`/`reviewer`) with extra scrutiny on exactly the parts the skill would have governed (variant/component correctness, layout math), same as any other finding.

This is the pattern to reinforce going forward if proceeding-without-the-skill keeps recurring: explicit, upfront disclosure plus self-verification, not silent risk-taking discovered only by asking. Still routed through a full `ux-critic` pass with elevated scrutiny per the first instance's own recommendation — this addendum's guidance doesn't relax just because the disclosure was better this time. **Elevated-scrutiny review confirmed both fixes correct** (one unrelated, pre-existing-pattern Minor found — a spacing inconsistency, not a skill-gap consequence) — the disclose-and-self-verify pattern held up under independent re-check.

**Third recorded instance, same day (Q12 Coral AA+ rollout — Design System `Button` component variable rebind):** same gap, same well-behaved response — explicit upfront disclosure, proceeded on tool-schema gotchas only, then went further than either prior instance on self-verification: ran a full instance-level scan of every `Button` instance's actual resolved `boundVariables` across all six document pages (not just a visual spot-check) specifically to rule out the D20-style silent-non-inheritance failure mode this very addendum warns about, and found a real safety issue on its own (the shared `color/coral` variable was also bound to decorative, non-button elements outside the dispatch's stated scope) rather than doing a blind global rebind. **Elevated-scrutiny `ux-critic` review outcome (Q12-VERIFY-MIN1):** the underlying color work was confirmed correct everywhere independently checked — zero wrong-colored button instances found — but the build report's own per-page Tertiary-instance *counts* were measurably inaccurate on 2 of 6 pages (Hoy: claimed 5, actual 6; Inventario: claimed 6, actual 8), while being exactly right on the three pages the dispatch had explicitly called out for extra scrutiny (Eventos/Resultados/Configuración, all correctly claimed as having zero Tertiary instances). Lesson: "ran a full scan, here are exact counts" claims from this disclose-and-self-verify pattern are trustworthy on substance (no incorrect design output found across three instances of this pattern now) but their self-reported counts still need independent re-tallying, not just spot-checking — the same self-verification discipline that catches wrong colors doesn't automatically catch miscounts of otherwise-correct instances. Continue routing through `ux-critic` with elevated scrutiny; don't relax to a lighter-touch review based on the pattern's now-solid track record on correctness alone.

**Fourth recorded instance, 2026-08-09 (overnight autonomous session, §3.15 Header clip fix on `reports.md`'s Loyalty Participation view):** same gap, same well-behaved disclose-and-self-verify response — this instance additionally didn't attempt the local-cache fallback at all before proceeding (unlike the redispatch pattern used successfully twice earlier the same night), going straight to inline tool-schema guidance plus direct plugin-API property inspection (querying actual `layoutMode`/sizing-mode values rather than guessing). Explicitly flagged the deviation in its own report, screenshot-verified the fix (no clipping, no new collisions) before reporting success, and proactively swept the page for a sibling instance of the same defect class (found one comparable "Header" component, confirmed it wasn't at risk since its content is static single-line, not dynamic two-line). This edit's blast radius was narrow (sizing mode + position shifts only, no reactions/wiring touched, so ID006/ID007's specific gotchas don't apply) — routed to `ux-critic` with elevated scrutiny per this addendum's standing rule regardless.

## ID003 — Figma prototype NAVIGATE/OVERLAY reactions cannot target a node on a different page

**Status:** Accepted, workaround applied (URL-action fallback). Recorded 2026-08-02, during the Medium-Fidelity clickable-prototype build.

**What happened:** While wiring the four cross-document happy-path journeys into a clickable prototype, `ui-designer` found that `node.setReactionsAsync` rejects any `NODE`-type reaction (`NAVIGATE` or `OVERLAY`) whose destination frame lives on a different Figma page than the source frame — confirmed with four independent attempts (plain call, pre-loading the destination page via `setCurrentPageAsync`, via `page.loadAsync()`, and via `flowStartingPoints`), all failing identically. Nahui's Medium-Fidelity file organizes each of the six documents (Hoy, Inventario, Eventos, Resultados, Onboarding, Configuración) on its own page — a deliberate, already-approved structure, not something this build changed. Every cross-document hop in all four journeys therefore had to fall back to a `URL`-type reaction (opens the destination frame's Figma link) instead of an in-Present-mode transition.

**Practical consequence:** Every *intra-document* leg of all four journeys is fully live, Present-mode-smooth. Every *cross-document* hop (which is most of the interesting structure in journeys spanning Onboarding→Home→Eventos→Home→Resultados, etc.) instead opens via URL — in Figma's Present mode this typically opens the target in a new browser tab rather than transitioning in place. Real usability degradation for the stated use cases (investor/stakeholder demos, usability testing) at exactly the seams between documents.

**Options to fix, not decided unilaterally — this is a file-structure tradeoff:**
1. **Consolidate all six pages onto one page.** Makes every reaction same-page, fully seamless. Cost: loses the current one-page-per-document organizational convention this project has relied on throughout Medium-Fidelity (frame IDs, tracking-file frame tables, `ux-critic`/`reviewer` dispatch scoping have all assumed per-document pages) — would need re-verification that nothing else depends on that separation.
2. **Duplicate anchor/entry frames.** Copy just the destination document's entry-point frame(s) onto the source page as a proxy, wire the reaction to the same-page duplicate, and have that duplicate's own onward links point back into its real page. Cost: duplicate frames to keep in sync if the real frame ever changes; more indirection to track.
3. **Accept the URL fallback as-is.** Zero additional cost, but the deliverable doesn't fully meet the "click through it live" acceptance bar the Product Owner stated for this specific request.

**Recommendation:** surface to the Product Owner directly rather than picking one — this trades organizational clarity (option 1) or maintenance overhead (option 2) against a real usability gap in a demo-facing deliverable (option 3), and the "right" tradeoff depends on how this prototype will actually be used (a live Present-mode demo to investors weighs this differently than an internal engineering handoff, where URL-hop is a minor friction).

**Decision (Product Owner, 2026-08-03):** Accept the URL-fallback as-is for now. No page consolidation, no duplicate anchor frames. Revisit only if a specific upcoming use (e.g., a live investor demo) makes the cross-document URL-hop friction concretely worse than acceptable — not a preemptive fix.

**Revisit (Product Owner, 2026-08-04):** Trigger condition met. After personally testing the prototype ahead of this week's usability sessions, the Product Owner found the cross-document URL/new-tab hops break the experience into what feels like disconnected prototypes rather than one application — unacceptable for the upcoming live merchant sessions (Ana + referrals, this week). Chosen fix is a fourth option beyond the three originally scoped: **a dedicated demo page, additive and separate from the six-page production structure** — not full consolidation (option 1, which would have disrupted the per-document tracking/frame-ID convention every Medium-Fidelity doc depends on), and not scattered same-page proxy frames on each source page (option 2 as originally scoped) — instead, one new page holding clones of every frame needed for a single continuous journey (Onboarding → Home cold start → Inventario → Eventos → Home selling → Resultados), all wired with native same-page `NODE`/`NAVIGATE` reactions. Production pages and their existing three-journey URL-fallback wiring stay untouched. Accepted maintenance cost: this demo page is a frozen snapshot at build time — if the underlying Low/Medium-Fidelity specs change later, the clones need to be re-synced manually, same disclosed risk as option 2's original framing, just scoped to one dedicated page instead of many scattered proxies. Dispatched to `ui-designer` same day.

## ID004 — `ux-critic`'s read-only Figma tools cannot inspect prototype reaction data; `get_metadata`'s instance-text field is sometimes stale

**Status:** Accepted, workaround identified. Recorded 2026-08-03, during verification of the Medium-Fidelity clickable-prototype build.

**Part 1 — reactions are invisible to `ux-critic`'s toolset.** `ux-critic`'s Figma access is `get_metadata`, `get_screenshot`, `get_design_context`, `whoami` — read-only inspection tools. Across ~45 node queries verifying the prototype's four journeys, `get_metadata` never returned a `.reactions` field, destination-node data, or trigger type for any node — consistent with its documented scope (geometry/hierarchy/naming, not prototype wiring). `get_design_context` might expose this via generated code, but requires the `figma-design-to-code` skill, which `ux-critic` had no `ReadMcpResourceTool`/`ListMcpResourcesTool` to load in that dispatch. **Confirmed 2026-08-06:** a later `ux-critic` dispatch did successfully load that skill via the local plugin-cache fallback and called `get_design_context` on a node with a known reaction — it returned a plain generated-code stub (a Tailwind `<a>` with no `href`/`onClick`) with no trace of the `NODE`/`NAVIGATE` wiring at all. So this isn't a skill-loading gap as originally suspected — `get_design_context` genuinely doesn't expose reaction data either, confirming the tool-scope gap is real and not just unverified. **Consequence: `ux-critic` cannot independently verify prototype-interaction wiring (destination accuracy, trigger type, overlay/close pairing) at the data level — only `ui-designer` can, since only `use_figma`'s Plugin API scripting can read `node.reactions` directly.** This is a structural tool-scope gap between the two roles, not a connectivity issue like ID001/ID003.

**Practical implication for future prototype-review dispatches:** don't ask `ux-critic` to "verify the reactions are correct" as if it's checking the same thing `ui-designer` already self-verified — it can't see that data at all. What `ux-critic` *can* usefully check (and did, thoroughly): whether each node in the claimed chain resolves to the correct frame/content per the approved spec (strong, real evidence of coherent intent), which is corroborating but not equivalent to confirming the literal reaction wiring. For a deliverable where reaction-level correctness matters (a demo-facing clickable prototype), treat `ui-designer`'s own reaction-readback self-verification as the primary source of truth for that specific claim, `ux-critic`'s structural/content pass as a second, different layer of scrutiny, and a human doing one real Present-mode click-through as the actual ground-truth check before formal sign-off — no combination of agent-only passes fully substitutes for that.

**Part 2 — `get_metadata`'s reported instance leaf-text is sometimes stale/wrong, independent of Part 1.** Confirmed in the same pass: `get_metadata` reported incorrect button labels for several correctly-built nodes (e.g. reporting "Guardar evento" for a node that screenshot-verified as "Confirmar y activar"; "No, mantenerlo" for a node that was actually "Activar plan de pago"). This is a tool-reporting artifact — the actual rendered content was correct in every case spot-checked — not a design defect. **Always cross-check `get_metadata`'s text content against a `get_screenshot` before treating a text mismatch as a real finding**, especially on instances that may have had text overridden after the component's underlying layer name was set.

**Third recurrence, 2026-08-07 — nearly shipped a false Blocker.** `reviewer`, verifying a same-day content fix (`651:5408`'s toggle-button label), reported a Blocker via `get_metadata` alone: label read "Cambiar a vender con botones" — self-contradictory for a card already showing "Botones." Main had independently live-verified the same node three separate times minutes earlier (screenshot, accessibility snapshot, and a successful click landing on the correct destination), all agreeing on the correct label ("Cambiar a vender con tags") — flagged the discrepancy back to `reviewer` with this entry's own citation rather than dispatching a "fix" for already-correct content. `reviewer` re-checked via `get_screenshot` (not `get_metadata`) and confirmed Main's read; retracted its own Blocker as a tooling artifact. The node's label had been set via an instance-level override — `ui-designer`'s own build report named this explicitly (`I651:5408;2:18`) — exactly the trigger condition this Part already describes. **Standing suggestion from this recurrence:** when a build report calls out that a text value was set via instance override, treat that as an explicit signal to cross-check `get_metadata` against `get_screenshot` *before* a Blocker-worthy content claim is made, not after one is challenged.

## ID005 — `findAllWithCriteria({types:['TEXT']})` silently misses text nested inside component instances on freshly-cloned subtrees

**Status:** Accepted, workaround applied (manual recursive traversal). Recorded 2026-08-03, during the Product Validation Sprint's usability-fix pass.

**What happened:** While editing text inside newly-cloned frames containing nested component instances (e.g. a cloned form frame containing a `Button` instance whose label needed updating), `findAllWithCriteria({types: ['TEXT']})` returned only top-level plain-text nodes — it silently skipped every TEXT node nested inside a component instance child. No error was thrown; the call just returned an incomplete set, which would have caused a silent "text edit didn't apply" failure if not caught. **Workaround:** manual recursive traversal (walk `node.children` yourself, recursing into `INSTANCE` nodes explicitly) reliably finds every TEXT node, including instance-nested ones. Prefer this over `findAllWithCriteria`/`findAll` with a `TEXT` type filter whenever the subtree contains component instances and you need every text node, not just top-level ones.

## ID006 — Cloning across Figma pages via the Plugin API silently drops reaction data

**Status:** Accepted, workaround applied. Recorded 2026-08-04, during the Journey 1 seamless-demo-page build (see ID003's 2026-08-04 revisit entry).

**What happened, part 1 — cloning from a non-current page drops nested instance reactions.** Cloning a node via `getNodeByIdAsync(...).clone()` without first making its source page the current page (`setCurrentPageAsync`) produced clones with only a small fraction of their expected reactions intact (3 of ~40 in the case that surfaced this) — no error thrown, just a silently incomplete clone. **Workaround:** call `setCurrentPageAsync(sourcePage)` once per source page before cloning any node from it, even though the clone is then appended to a different (non-current) target page.

**What happened, part 2 — `.clone()` doesn't preserve `.reactions` set directly on the cloned node itself**, only on its descendants — confirmed by diffing raw reaction JSON before/after cloning on frames with `AFTER_TIMEOUT` auto-advance reactions attached directly to the frame node. **Workaround:** after cloning, manually re-set the top-level node's reactions using the original `timeout`/`transition` values, with only `destinationId` remapped to the new clone target.

**Consequence:** any future cross-page frame cloning (not just this demo-page pattern) needs both workarounds applied, or the clone will look visually correct but be silently under-wired — a failure mode that would only surface as a broken click-through during a live demo, not during a visual review. Confirmed correct here via a full node-by-node `.reactions` readback (not just a visual check) after applying both fixes — 26/26 hops verified `NODE`-type with correct destinations.

## ID007 — Rewiring a Figma reaction's destination requires updating both `action` and `actions`

**Status:** Accepted, workaround applied. Recorded 2026-08-04, during the demo-page bug-fix pass.

**What happened:** A reaction-destination rewrite that only set `reaction.action.destinationId` silently had no effect — no error, but the click still routed to the old destination. Figma's reaction object carries both a legacy singular `action` field and the authoritative `actions` array; `setReactionsAsync` resolves the actual destination from `actions`, not `action`. Caught only via the standing post-rewire `node.reactions` readback, not by any API error.

**Workaround:** when rewiring a reaction's destination, update both `action.destinationId` and the matching entry in `actions[].destinationId` together. Always re-verify with a fresh readback after any reaction rewrite — this bug would have shipped silently otherwise.

## ID008 — `use_figma` batch scripts can report "executed" while silently performing zero mutation

**Status:** Accepted, workaround applied. Recorded 2026-08-04, during the Resultados headline-weight fix.

**What happened:** A `use_figma` batch write (a loop over multiple nodes using `console.log` for progress, no explicit `return` statement) reported successful execution, but a follow-up property readback showed none of the intended mutations had actually applied — a fully silent no-op, no error, no partial-completion signal, nothing in the tool's own response to distinguish it from a real success.

**Workaround:** always verify via an explicit node-property readback *before* trusting a batch write's own "executed" report, and structure batch scripts to `return` their result explicitly rather than relying on `console.log` alone. This is the same underlying discipline ID004/ID006/ID007 already established (self-reported success from this tool is not evidence of a real state change) — worth treating as a standing rule for any `use_figma` write, not just reaction rewrites: **read after every write, never trust the report alone.**

## ID002 — Agent tool-list resolution can cache a stale frontmatter value mid-session

**Status:** Accepted, workaround applied. Recorded 2026-08-02.

**What happened:** `marketing.md`'s `tools:` frontmatter used a malformed value (`tools: [read, write, glob, grep]` — lowercase, array-bracketed) that the harness couldn't resolve to real tool names, so every `marketing` spawn failed immediately with "would be spawned with zero tools." The file was corrected to the working format (`tools: Read, Write, Glob, Grep`, matching every other agent's frontmatter) and confirmed correct by re-reading the file from disk. **Three consecutive spawn attempts after the fix all failed with the identical stale error message**, quoting the old, already-corrected value verbatim — strong evidence the harness resolved this agent's tool list once (cached it) and didn't re-read the frontmatter on subsequent spawns within the same session, unlike the MCP connectivity issue in ID001 (which is a live connection state, not a cached parse result).

**Workaround:** dispatch the same task via the `general-purpose` agent type (which reliably resolves its tools) with the specialized agent's full persona/instructions pasted directly into the prompt, rather than relying on `subagent_type` to route to the now-mis-cached custom agent. This preserves who's actually doing the work (the same role, same constraints, same Approval-gate rules) — it's a dispatch-mechanism workaround, not a change to Decision Ownership or who's allowed to make which call.

**Open question, not resolved here:** whether this cache clears on its own (next session, next `/clear`, some other boundary) or requires something more — untested. If a custom agent fails to spawn with an error quoting a value that doesn't match its current on-disk frontmatter, that mismatch itself is the signal this is ID002, not a new bug — check the file content against the error message's quoted value before re-investigating.

## ID010 — Figma canvas-rendered prototypes require an accessibility accommodation to be interactive at all, which exposes internal frame names/spec citations as a side effect

**Status:** Accepted, mitigated via agent-level discipline rather than a source-level change. Recorded 2026-08-05, during `merchant-user-tester`'s Qualification Run.

**What happened:** Figma's Present-mode prototype viewer renders entirely to a single `<canvas>` element with no real DOM/accessibility-tree content underneath it — standard Playwright element targeting (role/name-based clicks) found nothing to target at all. `merchant-user-tester` had to enable Figma's own "Adapt content for screen readers" setting to get any individually-targetable elements. Doing so had a real side effect: it exposed the file's actual internal frame names and embedded spec-section citations (e.g., `"J1 · 03. Bienvenida + Elegir cómo empezar (§3.3)"`) through the now-populated accessibility tree — implementation metadata this agent is specifically designed never to have access to (`company/CLAUDE.md`'s Experience Validation section).

**Verified, not just self-reported:** Main cross-checked the run's actual findings against this exposure — every screen it described used genuine, visible on-screen text (e.g., "Todo listo," matching the screen's real heading), never the internal frame-name format. Disclosed proactively by the agent itself; did not appear to leak into judgment on this run.

**Decision (Product Owner, 2026-08-05):** Do not rename or restructure internal frame-naming conventions to avoid this exposure — those names are valuable to the design team and project governance, and changing them to accommodate one agent's constraints is the wrong tradeoff. ## ID011 — `merchant-user-tester` runs are not reliably re-discovering a working click technique, and one run silently substituted non-interactive navigation for real interaction

**Status:** Accepted, agent definition strengthened. Recorded 2026-08-06, during a re-walk of the "Empezar" fix (`product/02-ux/experience-review-2026-08-06.md`).

**What happened:** This is not the structural "Playwright can't click here" finding it initially looked like. Two techniques have each already been independently proven to work against this same Figma canvas: (1) enabling Figma's "Adapt content for screen readers" accommodation, then using normal element-based clicks — used successfully by the original Qualification Run; (2) raw `page.mouse.click(x, y)` calls corrected for the real, measured scale mismatch between screenshot pixel dimensions and the actual viewport (confirmed directly by Main: screenshot 1225×983 vs. viewport 1440×1156, ~1.176x) — used successfully by that same Qualification Run, and independently reproduced by Main clicking through three real screen transitions itself.

This re-walk run tried neither. It attempted only plain element-based clicking (text/role selectors, double-clicks) with no accessibility accommodation enabled — which predictably fails, per `ID010`'s own documented root cause, since the canvas exposes no accessibility-tree content by default. Every attempt failed identically. **The run then substituted the prototype viewer's own "Next frame" stepper control to keep advancing**, narrating the resulting screens as if they carried some evidentiary value about button behavior — before self-correcting, when directly challenged, that this was a mistake and the run produced no valid interaction evidence at all.

**Root cause, corrected same day:** this is not an inherent impossibility of automating Figma canvas prototypes, and should never be characterized as one. It's a missing MCP configuration. Playwright MCP's default capability set exposes accessibility-ref-based tools (`browser_click`, `browser_snapshot`, etc.) — these depend on real accessibility-tree content, which a canvas-rendered Figma prototype doesn't expose by default, so they were never going to work reliably here. Playwright MCP has an official, purpose-built answer for exactly this case: the opt-in `--caps=vision` capability, which exposes coordinate-based tools (`browser_mouse_click_xy`, `browser_mouse_move_xy`, `browser_mouse_down`/`up`, etc.) designed for canvas/non-DOM applications. This project's `.mcp.json` simply never enabled it. Everything that looked like "clicking doesn't work here" — including the earlier `ID010` accessibility-accommodation workaround, and Main's own manual coordinate-clicking via the unsafe arbitrary-code-execution tool — was different ways of working around a missing flag, not evidence of a real ceiling.

**Fix applied:** `.mcp.json`'s `playwright` server now launches with `--caps=vision`. `.claude/agents/merchant-user-tester.md`'s tool list replaced entirely — dropped every accessibility-ref tool (`browser_click`, `browser_snapshot`, `browser_type`, `browser_press_key`, `browser_hover`, `browser_select_option`, `browser_resize`), added the Vision coordinate tools (`browser_mouse_click_xy`, `browser_mouse_move_xy`, `browser_mouse_down`, `browser_mouse_up`, `browser_take_screenshot`, plus `browser_navigate`/`browser_navigate_back`/`browser_wait_for`, kept for navigation and safe error recovery). `browser_run_code_unsafe` (arbitrary JS execution, RCE-equivalent) is deliberately never granted to this agent — the whole point of enabling Vision is that the unsafe escape hatch is no longer needed. New standing instructions in the agent file itself: take a screenshot, click at real viewport-relative CSS-pixel coordinates (compensating for any screenshot/viewport scale mismatch), confirm the click actually landed before narrating forward, and — a hard rule — **never substitute the prototype viewer's own Next/Previous frame navigation for a failed click, under any circumstance**, since the tool for that isn't even in this agent's list anymore.

**Restart required, both for the MCP config change and the agent's tool-list change to take effect** — consistent with `ID009`'s finding that neither an MCP server's launch args nor a newly-edited agent's tool list are picked up mid-session. Before the next Qualification Run: (1) restart, (2) confirm `merchant-user-tester`'s available tools now show the Vision set, (3) run a minimal smoke test — navigate to the public prototype, screenshot it, click one visible button at corrected coordinates, confirm the screen actually changed — before trusting a full run's findings again.

**Smoke test run and passed, 2026-08-06, post-restart.** Main navigated to the public prototype, screenshotted the welcome screen, clicked "Ver un ejemplo" via `browser_mouse_click_xy` at coordinates read directly off the screenshot, and landed on the exact correct destination (`node-id=184-35`) on the first attempt — no scale-correction needed this time (the post-restart environment reports `window.innerWidth`/`innerHeight` matching the screenshot's CSS-pixel scale directly). Confirmed visually via a second screenshot showing the correct "Ver un ejemplo" confirmation content. The fix works as intended.

**Correction, same day, later: the fix was not sufficient.** Subsequent runs (a `merchant-user-tester` re-walk, then extensive direct testing by Main) showed genuine, unexplained intermittency — Button-component clicks succeeded in some sessions/attempts and failed consistently in others, with trust level (CDP already trusted), movement naturalism, coordinate precision, and an orphaned stale process all individually ruled out as the cause. One resumed agent produced node-ID-verified proof a click genuinely worked; a fresh dispatch immediately after failed on all four taps, including the previously-always-reliable plain text link. No stable, characterizable pattern was found. See the full investigation and resolution below — superseded by `chrome-devtools-mcp`, not by further tuning of this Vision-mode approach.

**Superseded 2026-08-06 — resolved via a different automation stack, not further Playwright tuning.** Product Owner declined to accept the intermittency as a permanent limitation and directed a real, comparative infrastructure investigation (Main-owned, not delegated to `merchant-user-tester`) across genuinely different execution approaches: the official `chrome-devtools-mcp` (Google-maintained), Playwright `connectOverCDP`, native macOS pointer automation, other computer-use MCPs, and a web-exported prototype as fallback-only.

**Native macOS automation — rejected, environment-specific, not a permissions problem.** Initially blocked by macOS Accessibility permission denial (`osascript`/System Events: `-1719`, "not allowed assistive access"). Product Owner granted the permission. Retesting then showed a different, more fundamental block: `System Events` reports zero windows for the automation-launched Chrome process, and a full-screen `screencapture` shows only the desktop wallpaper — the automation browser does not render to any physically-visible screen in this hosting environment. No native OS-level input tool (`cliclick`, AppleScript, or any "computer-use" MCP wrapping the same mechanism) has a real target to click here, independent of permissions.

**Playwright `connectOverCDP` — deprioritized, not directly tested.** Existing community evidence (documented instability connecting to long-lived browser instances, broken `newContext()` behavior, official Playwright guidance to prefer normal `connect()`) was strong enough to skip a full proof-of-concept — testing it would likely trade one reliability problem for a different, already-documented one.

**`chrome-devtools-mcp` — adopted.** Installed (`claude mcp add chrome-devtools --scope user npx chrome-devtools-mcp@latest`). Controlled proof-of-concept: the same three controls ("Empezar gratis," "Activar plan de pago," "Ver un ejemplo"), each clicked 3× from a fresh navigation (9 attempts total) — **9/9 successful**, every click landing on the correct, verified destination node, confirmed via the tool's own explicit navigation report each time, not inferred. Zero failures, zero intermittency, across the full protocol. Architecturally similar to the Vision approach (still needs Figma's "Adapt content for screen readers" enabled once per session to expose canvas content — confirmed to persist across page reloads without needing to be re-toggled), but a genuinely different, independently-built CDP client (Google's, not Microsoft's) — whatever caused the Playwright intermittency did not reproduce across 9 attempts here.

**Fix applied, superseding the `--caps=vision` fix above:** `.claude/agents/merchant-user-tester.md`'s tool list replaced again — dropped every Playwright Vision tool, added `mcp__chrome-devtools__navigate_page`, `mcp__chrome-devtools__take_snapshot`, `mcp__chrome-devtools__click`, `mcp__chrome-devtools__take_screenshot`, `mcp__chrome-devtools__wait_for`. Interaction instructions rewritten: snapshot → find element by visible label → click by reference, not coordinate math. The one-time "enable screen-reader accommodation via Options → Advanced settings → Accessibility settings" step is now a standing, documented instruction in the agent file itself, not something left to ad hoc rediscovery each run. `.mcp.json`'s `--caps=vision` Playwright config is left in place, untouched, as an immediate rollback path — no reinstall needed if `chrome-devtools-mcp` ever regresses.

**Restart required** for the new tool list to take effect, per `ID009`. A fresh Qualification-style run should follow immediately after, to confirm the new stack holds up under the agent's own full workflow (not just Main's direct testing) before this is considered fully closed.

**Why this matters going forward:** a Sequential/non-interactive screen review is a legitimate, separately-labeled activity (visible-content and continuity review) — it is never a substitute for validated interaction, and the two must never be blended in the same run's narrative the way this one did before self-correcting. With Vision properly enabled, that tradeoff shouldn't need to come up again — but if a future run ever reports it can't achieve genuine interaction, treat that as a real signal to investigate, not something to route around.

**Standing principle, extracted from this whole investigation — not specific to Figma or to this one tool.** When a tooling/automation problem is real (reproduced repeatedly, with evidence) but resists every fix attempted within the same implementation — trust level, timing, coordinate precision, retries — that pattern of "keeps failing despite ruling out every specific cause" is itself a signal to stop tuning and compare a **genuinely different implementation** of the same capability, not to declare the problem inherent or unsolvable. Two things make this work reliably: (1) the comparison has to be a truly different stack (a different vendor's CDP client, not the same one reconfigured) — testing variations of the same implementation over and over, as this investigation did at length before escalating, mostly just re-confirms the same failure; (2) **this investigation belongs to Main, never to the agent experiencing the problem** — an agent whose entire design rests on not having implementation knowledge cannot also be trusted to diagnose implementation-level tooling failures without compromising that same design. Watch for this pattern proactively rather than only after exhausting single-stack tuning, the way this entry did.

## ID012 — `chrome-devtools-mcp`'s synthetic `click` does not trigger Figma prototype "Back" reactions; keyboard `Enter` does

**Status:** Accepted, workaround identified. Recorded 2026-08-07, during live verification of the plan-activation Home-node clone fix (task #112).

**What happened:** Verifying a reported fix to a BackNav link (paid-tier Vista Principal → Home), `click(uid)` against the link reported "successfully clicked" and returned a snapshot every time, but the URL/node-id and rendered content never changed — a silent no-op, indistinguishable from a genuinely broken reaction by output alone. This reproduced identically on a second, structurally unrelated BackNav link (S7's "← Configuración", pre-existing, untouched by the fix in question) — ruling out a defect in the fix itself and pointing at the click mechanism instead. Re-tested the exact same link via `press_key({key: "Enter"})` after focusing it (a plain `click` first, which itself doesn't navigate but does set focus) — navigation fired correctly both times, landing on the correct verified destination node.

**Root cause (inferred, not confirmed via Figma internals):** these links carry Figma's "Back" reaction type, which some prototypes implement via the canvas's own navigation-history stack rather than an explicit `NODE`/`NAVIGATE` destination. `chrome-devtools-mcp`'s synthesized mouse click apparently isn't recognized by Figma's canvas handler as a trusted trigger for this specific reaction type, while a synthesized keyboard `Enter` on the focused element is. Explicit forward `NODE`/`NAVIGATE` reactions (e.g., "Volver al plan gratis," "Confirmar cambio") were not affected — every one clicked correctly via plain `click` throughout this same session.

**Consequence:** any future live verification of a Figma prototype's back-navigation links via `chrome-devtools-mcp` must not conclude "broken" from a `click` producing no transition alone — that reproduces this exact false-negative. **Workaround:** `click` the link once to focus it (ignore that this alone won't navigate), then `press_key({key: "Enter", includeSnapshot: true})` to actually trigger it, and verify via the resulting node-id in the URL/snapshot.

**Scope note:** this entry is about *verifying* existing prototype wiring via browser automation — distinct from `ID004` (read-only Figma tools can't inspect reaction data at all) and from `merchant-user-tester`'s own tool list (`ID011`), which already uses `mcp__chrome-devtools__click` successfully for forward navigation in its walks; nothing here suggests its qualification runs were affected, since the symptom is specific to Back-type reactions, not general click failure. Worth flagging if a future `merchant-user-tester` run reports a back-navigation control as "unresponsive" — that could be this same tooling gap rather than a real product defect, and should get the same Enter-key cross-check before being trusted as a finding.

## ID013 — A long-lived `chrome-devtools-mcp` page can silently stop delivering clicks on specific frames; a fresh page resolves it, and this produced a false "dead link" report

**Practical implication:** a chrome-devtools-mcp page used across a long verification session (many navigations, many test rounds) is not guaranteed to stay reliable for the rest of that session — periodically opening a fresh page for a "final" verification pass, especially before reporting a finding as confirmed, is cheap insurance against exactly this false positive. Distinct from `ID011`'s resolved intermittency (a different automation stack entirely, Playwright) — this is `chrome-devtools-mcp` itself, previously reported 9/9 reliable in short, controlled bursts; this failure only surfaced after extended reuse of one page across a long session, which the original 9/9 test didn't exercise.
