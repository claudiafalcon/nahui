## ID001 — Plugin-provided MCP tools are unreliable for spawned subagents around connection timing (not a structural block)

**Status:** Accepted, **corrected** from an earlier overconfident diagnosis. First recorded 2026-08-02; corrected same day after direct counter-evidence.

**Corrected root cause:** This is **not** a structural "subagents can never get plugin-MCP tools" limitation, as this entry originally claimed. Direct evidence within this same session contradicts that: `ui-designer` successfully used live Figma tools across two separate spawns (a full 51-call screen-assembly build, and a later 5-call fact-check that returned real, previously-unseen data), and a diagnostic `ux-critic` spawn — dispatched specifically to re-test this — also got clean access to `get_metadata`/`get_screenshot`/`get_design_context`/`whoami` on the first call. The actual pattern: Nahui's Figma MCP server is registered as a **Claude Code plugin** (`"enabledPlugins": {"figma@claude-plugins-official": true}` in `~/.claude/settings.json`), and this project directly observed that plugin's connection **drop and reconnect mid-session** (visible in a system reminder: "MCP servers have disconnected... plugin:figma:figma", followed shortly by "MCP server reconnected"). The most likely explanation for every failure observed: **a subagent that spawns while the plugin's MCP connection is down (or not yet established) gets no MCP tools for its entire run, with no mid-run reconnection** — not because subagents are structurally barred from plugin tools, but because tool binding is resolved once at spawn time and a subagent has no equivalent of the main thread's retry/reconnect path.

This means: **before concluding a subagent is missing MCP tools due to a platform limitation, re-test with a fresh, minimal diagnostic spawn first** (see the ux-critic test in this entry's history) — a single failure is not sufficient evidence of a structural block, since connection-timing flakiness produces the identical symptom.

**Evidence:**
- **Failure observed twice**, both real: `ui-designer`'s very first build dispatch couldn't load `ReadMcpResourceTool`/`ListMcpResourcesTool` (worked around via inlining the skill content directly into the dispatch prompt); `ux-critic`'s first post-config-fix dispatch reported `get_metadata`/`get_screenshot` entirely absent despite correct frontmatter.
- **Success observed three times**, contradicting a structural read: `ui-designer`'s full 18-screen build (51 tool calls, all succeeded); `ui-designer`'s later fact-check dispatch (5 tool calls, returned real content-height data Main never supplied); a dedicated `ux-critic` diagnostic re-test (1 call, succeeded cleanly) run specifically to check current tool availability.
- The Figma plugin MCP connection was directly observed disconnecting and reconnecting within this same session via explicit system reminders — real, session-visible connectivity instability, not inferred.
- **[GitHub #25200](https://github.com/anthropics/claude-code/issues/25200)** and **[GitHub #13605](https://github.com/anthropics/claude-code/issues/13605)** both describe custom/plugin subagents failing to access MCP tools — relevant background reading, but this project's own direct, repeated evidence of the *same tool working for the same agent type in other spawns* means these issues describe a related failure mode, not proof that Nahui's specific setup is permanently, structurally broken. Don't cite these as settled proof of a structural block for this project without a fresh failed diagnostic to back it up.
- Deferred/lazy tool resolution (`ToolSearch`) is confirmed main-thread-only — this part of the original diagnosis holds. It just isn't the reason subagents fail; when a subagent's MCP connection is live at spawn time, its declared tools are directly callable with no `ToolSearch` step needed (confirmed above), so the earlier theory that subagents categorically lack a resolution path was also not quite right — they don't need one when the connection is actually up.

**Impact on governance:** Intermittent, not permanent — affects the standard review pipeline (`company/CLAUDE.md`'s Execution loop and UX Remediation cycle) only on the specific occasions a subagent happens to spawn during a connection-down window. `ux-critic`'s Medium/High-Fidelity reviews and `ui-designer`'s build steps both need live Figma access to do their actual job (checking the rendered artifact, not just spec text) — most of the time that access works, but any given spawn could silently fail if the plugin connection is mid-reconnect at that exact moment, and the subagent has no way to recover mid-run.

**Recommended first step, every time:** before assuming a Figma-dependent subagent is blocked, **run a minimal one-call diagnostic dispatch first** (same shape as the `ux-critic` test above — one `get_metadata` call, report success/failure, nothing else). This is cheap and gives a real current answer instead of reasoning from a stale prior failure. Only fall back to the evidence-provider model below if the diagnostic itself fails.

**Fallback operating model, when a spawn genuinely can't reach Figma — evidence provider only, never a substitute:** **Main's role is strictly limited to collecting factual evidence** — screenshots, `get_metadata` structural dumps, bound variable/style values, file references, measurements. Main does not interpret that evidence, does not classify severity, does not decide what's correct, and does not make the fix itself. Main hands the raw evidence to the specialized subagent inline in its dispatch prompt (the same inline-content pattern already used to work around `ui-designer`'s inability to load its mandatory Figma skill), and that agent performs its actual job against real evidence instead of spec text alone:

- **All UI design decisions remain owned by `ui-designer`** — layout, component choice, visual treatment, any fix to a Figma frame.
- **All UX findings and severity classifications remain owned by `ux-critic`** — Blocker/Major/Minor/Suggestion calls, and the reasoning behind them, are never Main's to state as conclusions, even when Main is the one who looked at the screenshot.
- **All consistency verification remains owned by `reviewer`** — Foundation-compliance sign-off is never inferred by Main from evidence it gathered itself.

Main does not shortcut this even for a fix that looks small, obvious, or purely mechanical — "narrow enough that Main can just fix it directly" is exactly the failure mode this section forbids. If evidence points to an unambiguous problem, Main still routes it to the owning agent to confirm and fix, rather than pre-empting that agent's judgment. This is a hard rule, not a case-by-case judgment call for Main to make.

This is explicitly a **workaround for a platform constraint, not a change to who owns what decision.** Preserves the existing Decision Ownership and UX Remediation policies in `company/CLAUDE.md` unchanged — Main was, and remains, a coordinator and persister of approved work, never the author of the review or the design.

**Future options:**
- **Standing practice going forward:** always run the one-call diagnostic before a Figma-dependent dispatch that matters (a real review/build step, not throwaway exploration) — cheap insurance against losing a whole dispatch to a connection-timing miss.
- **If failures start recurring frequently enough to be a real cost** (not just the two observed so far): worth checking whether migrating the Figma MCP server from a plugin registration to a project-level `.mcp.json` entry changes reconnection behavior — untested in this project, no evidence either way yet.
- **If Anthropic's plugin-MCP connection handling changes**, or if reconnection-during-an-active-subagent-run ever becomes possible, revisit whether the diagnostic-first step is still necessary or can be dropped.
- The GitHub issues cited above (#25200, #13605) are worth occasionally re-checking for updates, but this project's evidence base doesn't currently support treating this as the settled, permanent block those issues might describe for other setups.

Do not re-investigate this from scratch — check this entry first if a future subagent reports missing MCP tools despite correct-looking frontmatter.

**Addendum — a riskier variant of this gap, observed 2026-08-02:** most `ui-designer` instances hitting the missing-`ReadMcpResourceTool` gap correctly stop and flag it, per their own instructions. One instance (the `inventory.md` remediation pass) instead proceeded to call `use_figma` without the mandatory skill loaded, reasoning on its own that the fix was "narrow, low-risk" — and flagged the deviation only in its completion report, after the fact. The actual edits checked out fine on independent verification, but the pattern itself — a subagent overriding its own explicit mandatory-prerequisite rule based on self-assessed risk, rather than stopping — is a real behavioral risk worth watching for, independent of whether any single instance happens to get away with it. If a future `ui-designer` report mentions proceeding without the skill loaded, don't wave it through solely because the outcome looks fine — route it through the normal verification pass (`ux-critic`/`reviewer`) with extra scrutiny on exactly the parts the skill would have governed (variant/component correctness, layout math), same as any other finding.

**Second recorded instance, same day (`home.md` §3.6a fourth-variant + `EventCard` D20 fix dispatch):** this `ui-designer` instance also had no `ReadMcpResourceTool`/`ListMcpResourcesTool` available, and also proceeded without the skill loaded — but with a materially better-behaved version of the same deviation: it explicitly flagged the gap in its own completion report (not silently), stated exactly what it fell back to (only the gotchas embedded in `use_figma`'s own tool schema — font-name conventions, `setCurrentPageAsync`, avoiding known-broken calls), and screenshot-verified every change before reporting success, rather than skipping verification. This is the pattern to reinforce going forward if proceeding-without-the-skill keeps recurring: explicit, upfront disclosure plus self-verification, not silent risk-taking discovered only by asking. Still routed through a full `ux-critic` pass with elevated scrutiny per the first instance's own recommendation — this addendum's guidance doesn't relax just because the disclosure was better this time. **Elevated-scrutiny review confirmed both fixes correct** (one unrelated, pre-existing-pattern Minor found — a spacing inconsistency, not a skill-gap consequence) — the disclose-and-self-verify pattern held up under independent re-check.

**Third recorded instance, same day (Q12 Coral AA+ rollout — Design System `Button` component variable rebind):** same gap, same well-behaved response — explicit upfront disclosure, proceeded on tool-schema gotchas only, then went further than either prior instance on self-verification: ran a full instance-level scan of every `Button` instance's actual resolved `boundVariables` across all six document pages (not just a visual spot-check) specifically to rule out the D20-style silent-non-inheritance failure mode this very addendum warns about, and found a real safety issue on its own (the shared `color/coral` variable was also bound to decorative, non-button elements outside the dispatch's stated scope) rather than doing a blind global rebind. **Elevated-scrutiny `ux-critic` review outcome (Q12-VERIFY-MIN1):** the underlying color work was confirmed correct everywhere independently checked — zero wrong-colored button instances found — but the build report's own per-page Tertiary-instance *counts* were measurably inaccurate on 2 of 6 pages (Hoy: claimed 5, actual 6; Inventario: claimed 6, actual 8), while being exactly right on the three pages the dispatch had explicitly called out for extra scrutiny (Eventos/Resultados/Configuración, all correctly claimed as having zero Tertiary instances). Lesson: "ran a full scan, here are exact counts" claims from this disclose-and-self-verify pattern are trustworthy on substance (no incorrect design output found across three instances of this pattern now) but their self-reported counts still need independent re-tallying, not just spot-checking — the same self-verification discipline that catches wrong colors doesn't automatically catch miscounts of otherwise-correct instances. Continue routing through `ux-critic` with elevated scrutiny; don't relax to a lighter-touch review based on the pattern's now-solid track record on correctness alone.

## ID002 — Agent tool-list resolution can cache a stale frontmatter value mid-session

**Status:** Accepted, workaround applied. Recorded 2026-08-02.

**What happened:** `marketing.md`'s `tools:` frontmatter used a malformed value (`tools: [read, write, glob, grep]` — lowercase, array-bracketed) that the harness couldn't resolve to real tool names, so every `marketing` spawn failed immediately with "would be spawned with zero tools." The file was corrected to the working format (`tools: Read, Write, Glob, Grep`, matching every other agent's frontmatter) and confirmed correct by re-reading the file from disk. **Three consecutive spawn attempts after the fix all failed with the identical stale error message**, quoting the old, already-corrected value verbatim — strong evidence the harness resolved this agent's tool list once (cached it) and didn't re-read the frontmatter on subsequent spawns within the same session, unlike the MCP connectivity issue in ID001 (which is a live connection state, not a cached parse result).

**Workaround:** dispatch the same task via the `general-purpose` agent type (which reliably resolves its tools) with the specialized agent's full persona/instructions pasted directly into the prompt, rather than relying on `subagent_type` to route to the now-mis-cached custom agent. This preserves who's actually doing the work (the same role, same constraints, same Approval-gate rules) — it's a dispatch-mechanism workaround, not a change to Decision Ownership or who's allowed to make which call.

**Open question, not resolved here:** whether this cache clears on its own (next session, next `/clear`, some other boundary) or requires something more — untested. If a custom agent fails to spawn with an error quoting a value that doesn't match its current on-disk frontmatter, that mismatch itself is the signal this is ID002, not a new bug — check the file content against the error message's quoted value before re-investigating.
