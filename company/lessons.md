## 2026-08-15 — Substantial agent deliverables must be persisted to a file immediately, not left living only in conversation text
- Two full deliverables — a five-part merchant validation campaign package (`marketing`) and a set of 6 concrete `frontend-design` enhancement proposals (`ui-designer`) — were produced, relayed to the Product Owner in conversation, and never written to any file in the repository. When the conversation was later summarized (a routine context-compaction, not a restart or crash), the campaign package survived only partially in the summary and had to be reconstructed from what remained; the 6 proposals were gone entirely and had to be regenerated from scratch by re-running the evaluation — real, duplicated work, not a free retry.
- This is the same failure this project's own continuity principle already names ("overall project continuity — the property that no completed work, decision, or discovery becomes invisible to a future session," `company/CLAUDE.md`, Main's role) and the same class of gap the Session Recovery Protocol was written to catch for a *restart* — but a mid-session context-compaction is a quieter, more frequent version of the same event, and nothing was watching for it specifically.
- **Lesson:** the moment a specialized agent returns a deliverable meant to be reviewed, decided on, or acted on later — not a status update, not an intermediate finding, the actual thing — persist it to a real file before relaying it to the Product Owner or moving to the next task, even if it isn't "approved" yet. A proposal-stage or pending-decision document still belongs in the repository (marked Draft/Proposed in its own status line, per this project's existing convention) — "not yet approved" is not a reason to leave it un-persisted; only "approved" work being un-persisted was ever the narrower rule. Conversation history, including a task-notification's full result text, is not a durable store — treat anything living only there as already at risk, regardless of how recently it arrived.

## 2026-08-08 — "Forget the software, what does the merchant actually do" needs to be applied literally, not by analogy from a different context
- During the MVP pricing-model discovery (Day-0 workstream, `decision-log.md` D33), `ux-designer` rejected a proposed per-selling-group, per-Event price-override mechanism as "not merchant-native," reasoning by analogy from H2's catalog-capping finding (Ana avoids per-line cognitive load) and proposing an unvalidated "blanket adjustment" alternative in its place.
- Both moves were wrong in the same way: H2's friction is scoped specifically to *live, real-time* cognitive load during selling — it was applied to a structurally different moment (offline, deliberate Event-planning) without evidence the aversion generalizes across that context boundary. And the "blanket adjustment" replacement was never evidenced either — Ana's own words were entirely absolute-dollar, per-venue; nothing she said implied a percentage/global framing.
- The Product Owner caught both by asking `architect` to re-derive the answer from the literal evidence text and Nahui's own already-Approved precedent (`events.md`'s existing "Nuevo Evento" flow already asks for a comparable handful of named values at the identical planning moment, with zero complexity finding ever raised) — not from what felt intuitively simpler to build.
- **Lesson:** when checking whether a proposed mechanism is "merchant-native," reasoning by analogy from a validated finding in a *different context* is not the same as evidence, and proposing a simpler-sounding alternative is not automatically the safer/more-validated choice — it can just be a second, unvalidated hypothesis wearing a plausible label. The check that actually works: reread the literal evidence text, and check whether a comparable already-Approved precedent exists in this project's own specs before assuming a new interaction is more complex than what's already shipped. Apply this whenever a specialist (any of them, not just `ux-designer`) argues "this doesn't match how the merchant thinks" — ask what specific evidence, read literally, supports that claim, not what feels right by comparison to an unrelated prior finding.

## 2026-08-02 — Main directly edited settings.md content instead of dispatching ux-designer (process lesson, not a product defect)
- During `settings.md`'s remediation, `ux-designer` was redispatched twice to fix flagged findings and, on both redispatches, introduced new regressions while fixing what it was asked to fix (round 2 reverted an already-verified SET-M2 fix back to a worse state and reintroduced SET-M1's identity-implying copy in a new spot). Rather than risk a fourth regression cycle, Main made the final three corrections directly — restoring the verified-correct SET-M2 text, reapplying the SET-M1 copy pattern, and fixing a `reviewer`-caught D22 joint-gating copy issue.
- This was the same failure mode later corrected explicitly for `ui-designer`/`ux-critic`/`reviewer` (Main substituting its own judgment for a specialized agent's, even when the fix looked small/obvious/mechanical) — it just happened first, in a different agent's territory, before the pattern was named. `ux-designer` owns Low-Fidelity content decisions; "the agent keeps drifting on redispatch" is a reason to dispatch more narrowly (hand back the exact diff needed, not a full regeneration), never a reason for Main to make the edit itself.
- **Explicit Product Owner decision: `settings.md` is not reopened or invalidated.** Its content was independently verified correct by `ux-critic` and `reviewer` regardless of which path produced it — this is a governance lesson about *how* the fix should have been made, not a defect in *what* was fixed. Treat this as closed, Approved, done.
- **Corrected going forward** (`company/CLAUDE.md`, "Main's role"): Main never performs the responsibilities of any specialized agent — `ux-designer`, `ui-designer`, `ux-critic`, `reviewer`, `architect`, `planner`, `builder`, `marketing` — under any circumstance, including tooling limitations and repeated agent regression. Main coordinates, dispatches, and (when a tool is genuinely unreachable) relays factual evidence — the owning agent always makes the actual decision.

## 2026-07-31 — Removed the "no real data yet" gate on Reports/segmentation
- `company/backlog.md` #2 originally blocked customer segmentation work until sale registration (#1) had produced real usage data — a reasonable gate at the time, set before the Product Foundation (`product/00-foundation/`) or the `product/02-ux/` UX-documentation process existed.
- That gate no longer applies: Reports (Resultados) is now part of current MVP UX scope and is being documented alongside Home/Inventario/Eventos, not held back pending real sales data. Removed the "blocked by / do not start" language from backlog.md #2 rather than leaving a stale constraint next to a live decision to proceed.
- Any future doc that still cites "blocked until real history exists" for Resultados/segmentation is referencing this obsolete assumption and should be corrected.

## 2026-07-25 — Initial tap-to-register prototype
- Decision: simulate NFC tap with large per-product buttons instead of waiting for physical tags, so the core mechanic (registration speed) can be validated without being blocked by hardware.
- Added automatic per-registration timer (not manual) because eyeballing time isn't reliable for the success metric (<3 seconds).
- Pending: once physical NFC tags arrive, replace the button with real NFC reading via Web NFC API (Android/Chrome only) or an external reader.

## 2026-07-26 — NFC scan mode, tag assignment, and multi-item sales
- Added an NFC mode alongside the existing button mode, using the Web NFC (`NDEFReader`) API. It only works on Android Chrome over HTTPS, so desktop/other browsers show an inline "not supported" message instead of failing silently — this is a hardware/browser constraint we can't fix, only work around.
- Added an "Asignar" sub-mode so a vendor can link many physical tag UIDs to one product (e.g. 5 pajama tags -> "Pijama"). Assignments are stored in `localStorage` as a flat `{uid: producto}` map — good enough for a single-device prototype, not meant to survive a real multi-device rollout.
- Scanning an unassigned tag during a sale shows an explicit message instead of silently dropping it or adding a phantom item, since a missed sale is the exact failure mode we're trying to avoid.
- Reworked registration around a "Nueva venta" / "Finalizar venta" session so one transaction can hold multiple items (same product tapped/scanned more than once). This changes the core metric: we now time whole transactions, not individual taps.
- The old <=3s threshold was per single tap; it doesn't make sense for a multi-item sale. Used a simple placeholder: 3s budget per item in the transaction (first item covers "greeting the customer", extra items are just repeat taps/scans). Not validated with Ana yet — worth revisiting once we have real multi-item sale timings.
