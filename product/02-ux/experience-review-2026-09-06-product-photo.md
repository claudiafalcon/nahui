# Experience Review — 2026-09-06: Product photo (Q23)

**Persona:** Ana. **Purpose:** first `merchant-user-tester` walk of the `Product.photo` feature (`product-decisions.md` Q23, `decision-log.md` D54), after `ux-critic`/`reviewer` both passed clean on the built code. Task: set up Nahui, add a product (optionally with a photo), then find and use the photo-editing affordance in Inventario. Run twice — once before a fix, once after — per this project's "full rerun from the beginning, not a resume" discipline.

## Finding — landing on an already-configured, paid account instead of a fresh one

Both runs, Ana landed directly on a working Home screen with an existing paid Business, an existing selling mode, and existing products (Gorras, Pijamas) already in the Catalog — no onboarding flow at all, despite the task framing ("for the first time"). **Verification status: Tooling Artifact.** Confirmed via direct code inspection (`store.tsx`'s `initialState()`): the local dev server reads persisted `localStorage` state before falling back to a blank Business, and this codebase deliberately seeds convenience state for fast dev-time reach into populated screens (the same pattern this project's own pass history already documents, e.g. Slice 10's "seeded directly through localStorage for fast, repeatable reach into each state"). Not a first-time-onboarding defect — a dev-environment convenience, not routed as a fix.

## Finding — "Agregar foto" gives no visible response

Both runs, tapping "Agregar foto" (in Onboarding's row-level field, Inventario's product-creation sheet, and the standalone "Editar foto" sheet) produced no visible change on screen — no picker, no preview, no error. **Verification status: Tooling Artifact.** Confirmed via direct code inspection: the button triggers a genuine native `<input type="file">`, which opens the OS's own file picker — a UI surface that renders outside the page DOM and is structurally invisible to `chrome-devtools-mcp` browser automation. Ana disclosed this exact hypothesis herself in the first run. Not a product defect; a known, disclosed limit of this testing channel for any file-upload control, not specific to this feature.

## Finding — "Guardar foto" saved silently, no confirmation either way — real defect, fixed

**Run 1.** Saving a photo edit (with nothing actually attachable, per the finding above) gave zero feedback — no success message, no error, nothing. Ana named this as more worrying than an outright error would have been: "if this had been a real product photo, she'd have no way of knowing whether it actually saved." **Verification status: Independently Verified.** Confirmed via direct code inspection: `handleGuardarFoto()` wrote the value and closed the sheet but never triggered this same file's existing toast/confirmation mechanism, despite `inventory.md §3.4b`'s own spec text explicitly citing the same near-instant/slow/error save convention every other write in this document family already follows. **Fixed** — `handleGuardarFoto()` now fires the standard toast ("Foto guardada"), reusing the exact mechanism already used elsewhere in this file (`CatalogView.tsx`, commit `d49a9d2`).

## Finding — the fix's first version produced a false-positive confirmation — real defect, fixed

**Run 2** (after the first fix, full rerun from the beginning). "Foto guardada ✓" now fired — but unconditionally, including when Ana tapped "Guardar foto" having never actually staged a photo (a direct, unavoidable consequence of the file-picker tooling limit above, but also a real case a real merchant could hit on her own — opening "Editar foto," changing nothing, and tapping "Guardar foto" out of habit instead of "Cancelar"). Ana called this out directly as worse than the original silence: "I was told something succeeded that, as far as I could see, didn't actually happen... it made me wonder what else in this app might be telling me something worked when it didn't." **Verification status: Independently Verified.** **Fixed** — `handleGuardarFoto()` now diffs the staged photo against the value captured at the moment the sheet opened (a new `openedPhotoRef`); the write and sheet-close still always happen, but the confirmation toast only fires when something actually changed. A no-op save now behaves, from the merchant's point of view, exactly like "Cancelar" (`CatalogView.tsx`, commit `1a065a9`). Verified correct via direct code inspection of the final diff (ref set at open time in `openPhotoSheet`, compared pre-write in `handleGuardarFoto`) rather than a third full walkthrough, per this project's own reactive-round discipline — the fix is mechanically checkable, not a subjective UX judgment requiring Ana's own reaction to confirm.

## What worked well, both runs

Product registration itself (typing a new name, being offered "+ Agregar '...' como producto nuevo," setting a price, seeing an immediate "Mercancía registrada ✓") read as fast and trustworthy both times — Ana specifically contrasted this positively against the photo feature's failures, calling it something she'd keep using without hesitation and would mention to another vendor. The Cantidad review step ("· revisa antes de guardar") also read as the app being careful with her stock numbers, which she cares about.

## Status

Both real (non-tooling) findings are fixed and verified. The two tooling-artifact findings (seeded dev state, native file picker invisible to automation) require no action — they're limits of this testing channel, not the product. Photo-attachment itself (the actual file-selection step) still has no live-verified confirmation that a real photo, once selected by a real human on a real device, renders correctly end-to-end — this remains the natural next confirmation step whenever a real device/manual check is available, same disclosure this project already applies elsewhere when browser automation can't reach a native OS surface.
