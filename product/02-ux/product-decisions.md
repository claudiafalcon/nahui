# Product Decisions

Standing log of open questions classified as **Product Decisions** under the Decision Ownership policy in `company/CLAUDE.md`: questions that change product behavior, user experience, capabilities, or feature scope, and require a Product Owner call — not something Architect can resolve by interpreting the existing `product/00-foundation/`, and not a pricing/commercialization/legal/operations matter.

This file was created by reclassifying entries that previously lived in `product/02-ux/architect-questions.md`, per the new Decision Ownership policy. **Content and status are unchanged from the original entries** — this is a governance move, not a reassessment. Each entry's original Architect finding is preserved verbatim below; it's still the reasoning behind why each item is open, even though the item itself is no longer an Architect Decision.

Entries are never deleted once resolved; mark them Resolved with the outcome instead, so the history of what was ambiguous and why stays intact (same non-deletion rule as `product/99-rfc/`). A resolved Product Decision that changes the domain model, ubiquitous language, or IA should still go through an RFC (`product/99-rfc/`) before `product/00-foundation/` is touched, per existing policy — this log is the queue feeding that process, not a replacement for it.

## Open

### Q24/Q25 — Concurrent multi-seller selling with Event-scoped inventory allocation (unified design, 2026-09-06)

The Product Owner directed these be treated as one coherent design problem (a real prospective merchant's actual use case), designed fully before deciding what ships first. Full architecture pass complete; superseding the two separate, narrower findings this replaces (kept below in "Superseded prior findings" per this log's non-deletion rule).

**Settled architecture (Architect Decision, resolved):**

- **Two new aggregate roots.** `EventAllocation` (Selling context: `businessId`, `eventId`, `productId`, `quantityAllocated`/`quantityRemaining` for manual mode, `allocatedUnitIds` for NFC mode, `status: open | reconciled`, unique on `(eventId, productId)`) — a root, not an internal-only entity nested in Event, correcting the prior Q25 finding: the full lifecycle (reallocation between Events, general-pool availability checks) needs "where is this stock allocated" resolvable independent of any one Event in context, the same test that promoted `Venue` (D20) and `BusinessMembership` (D44) to root status. `Invitation` (Identity context: `businessId`, `phone`, `role`, `status: pending | accepted | revoked | expired`, unique on `(businessId, phone)` while pending) — a root for the same reason: resolving "does this verified phone have a pending invitation" must run before any Business is in context.
- **`AllocationMovement`** — an append-only ledger entity owned by `EventAllocation` (type: `initial_allocation | replenish | reallocate_in | reallocate_out | return_to_general | adjustment`), the same pattern `InventoryEntry`-under-`Lot` already establishes. This is what makes replenish/reallocate/reconcile "just new ledger entries," not new mechanisms.
- **`Sale` gains `performedByMembershipId`** (references `BusinessMembership`, not `User` directly) — the exact field RFC 0007 §3 named and explicitly deferred ("if it's ever wanted, it gets its own explicit Product Decision at that time"). Captured now, not consumed by reporting yet — same restrained pattern as `Sale.claimToken` (D26).
- **No changes to `Session`, `Event`, `Business`, `Product`, `InventoryUnit`, or `Lot`.** Concurrency itself needs almost no new mechanism: `domain-model.md` already states Event doesn't own Session as a write-consistency boundary and Event-level summaries are read-side queries across Sessions sharing an `eventId` — this already structurally permits multiple concurrently-open Sessions per Event. D17 restricts Event-to-Event date overlap, never Session-to-Session concurrency within one Event.
- **Physical-location-exclusivity invariant** (the core rule: the same inventory can't be truthfully available in two places at once) is enforced entirely inside Selling's own bookkeeping — Inventory never learns Events or allocation exist, preserving `architecture-principles.md` #6's one-way dependency direction. NFC mode: a unit ID may appear in at most one `open` `EventAllocation.allocatedUnitIds` at a time, enforced via `InventoryUnit`'s existing `available→reserved` conditional write. Manual mode: an atomically-decremented `quantityRemaining` counter on `EventAllocation`, since manual units are fungible and a pure derived read isn't concurrency-safe with two writers.
- **Allocation lifecycle:** general pool → `EventAllocation` created (open) → concurrent Sales consume against it → `replenish()` any number of times → `reallocate(toEventId)` (a paired, sequenced two-write operation across two `EventAllocation`s, source-decrement-first for a safe failure mode) → Event reaches `closed` **with `EventAllocation.status` unchanged** (deliberately decoupled — same precedent as Session's dormant `reviewed` state, D18) → an explicit, merchant-initiated reconciliation action (`return_to_general` or `reallocate_out`) is what actually closes the allocation. Confirms the Product Owner's instinct: no silent auto-return to general inventory on Event close.
- **Manual vs. NFC — one aggregate, two fields, not two forked models.** NFC populates `allocatedUnitIds` (unit identity already fixed at generation, `commitLot()`'s existing batch-classify-once flow — already built, not a gap, per Architect's finding). Manual populates `quantityAllocated`/`quantityRemaining`. A Product can have both simultaneously at one Event (some units tagged, some not), the same mixed state NFC Readiness already models elsewhere.
- **Concurrency mechanism is a Stage 7 (Backend Integration) requirement**, not buildable/testable in the current no-backend prototype. The prototype can illustrate the *experience* of losing a race (a mocked "otro vendedor ya la vendió" state) without the real compare-and-swap mechanism existing underneath yet.
- **Permission table (OWNER vs. SELLER), reasoned from the Product Owner's stated intent:** OWNER — Business identity/Configuración, Catalog/Product management, Lot receiving/tagging, Event create/edit/pricing, allocate/replenish/reallocate/reconcile, invite/manage staff, business-level Resultados. SELLER — open/close own Session, register Sales, read sellable Products/prices (unchanged, ungated — gating this would violate "never ask twice"), own current-session activity (recommended as an extension of Home's existing Session-scoped state, not a cut-down Resultados variant). Role is a genuinely new third gating axis alongside `registrationMode`/`subscriptionTier` — `information-architecture.md` doesn't name it yet.
- **RFC determination: two RFCs required**, both unambiguously RFC-worthy (two new aggregate roots + a new invariant on an existing write path, same class as RFC 0001/0004/0007) — sequenced together in practice but reviewable independently: **"Membership invitation and concurrent selling"** (extends RFC 0007 — `Invitation`, `Sale.performedByMembershipId`, the permission table, confirms Session/Event already support concurrency) and **"Event-scoped inventory allocation"** (`EventAllocation`/`AllocationMovement`, the exclusivity invariant and its enforcement, the full lifecycle, the Stage 7 concurrency-safety requirement).

**Explicit challenges/corrections the Architect made to the Product Owner's stated approach** (she asked to be challenged, not just encoded):
1. Reallocation between two Events is modeled as two sequenced writes with a documented conservative failure mode, not pretended to be a single atomic cross-aggregate transaction (standard DDD boundary: one transaction per aggregate instance) — flagged for the `knowledge-mentor` consultation below to confirm/strengthen against established Saga/reservation-system practice.
2. A literal reading of the Product Owner's own illustrative example ("20 to Event A, 10 to Event B") could imply two *simultaneously active* Events, which D17 currently forbids. Architect's assessment: the actual requirement (multiple sellers sharing one Event's pool) only needs concurrent *Sessions*, not concurrent *Events* — the 20/10 split works as sequential Events too. Flagged as a real open question below, not silently resolved either way.

**Genuinely new items surfaced, needing Product/Business Decision routing — both now resolved:**
1. **Business Decision, resolved 2026-09-06 (Product Owner): multi-staff/SELLER seats are paid-tier-gated** (`subscriptionTier=paid`), same class as Frequent Customers/segmentation. Logged in `company/business-decisions.md`. Not yet folded into the permission table/`Invitation` design above — an `Invitation` can only be issued while `Business.subscriptionTier=paid`, the check composing with the existing `subscriptionTier` gate rather than adding a new gating dimension.
2. **Product Decision, resolved 2026-09-06 (Product Owner): Nahui needs true *simultaneous* multi-Event operation** (two teams, two bazaars, same weekend) — the Architect's default assumption (sequential-only sufficient) does not hold. **This reopens D17** ("at most one Event per Business may be `scheduled`/`active` with an overlapping date range at a time") and needs its own explicit amendment, dispatched back to `architect` as a follow-up to this design, not resolved here.
3. Two IA-level consequences flagged for `ux-designer`, not decided here: `home.md` §2's "resume open Session" resolution logic needs to resolve per acting Membership, not per Business, once two Sessions can be concurrently open; and a User holding Memberships in more than one Business (D44's own previously-unresolved open item) becomes a real, expected case requiring a Business-switching design, not a silent assumption.

**`knowledge-mentor` consultation complete (2026-09-06)** — the reallocation-transaction mechanism: core shape confirmed (atomic counter, source-decrement-first, "missing" preferred over "double-available" on partial failure all match established inventory-transfer/ledger-transfer practice), but the failure-handling half was thinner than standard practice recommends. Two refinements to fold into the RFC, not yet applied to the design above:
- **`AllocationMovement` should be the explicit, queryable reconciliation vehicle** for a failed reallocation — a `reallocate_out` movement with no matching `reallocate_in` on the destination is a detectable, mechanically-resolvable "in-flight/failed transfer" signal (the same technique Saga/ledger systems build dedicated tables for; Nahui already has the primitive via its existing `InventoryEntry`-under-`Lot` pattern, just not yet described as doing reconciliation-by-query over it).
- **A single local DB transaction spanning both `EventAllocation` rows is a legitimate, simpler alternative** to sequenced-writes-plus-compensation, given same-context/same-database locality at Nahui's actual pilot scale (3 merchants) — `architecture-principles.md` #2's "one aggregate per transaction" is a boundary-sizing heuristic (Vernon), not an absolute prohibition, when both instances share the same store. Worth architect's explicit call in the RFC rather than defaulting to the heavier sequenced-writes design.
- Full Saga/event-sourcing/CQRS adoption is **not indicated** — fails `architecture-principles.md` #8's comparable-cost gate at this scale; the ledger-plus-projection shape already in the domain model gets most of the benefit without the adoption cost.

**D17 amendment complete, 2026-09-06 — logged as `decision-log.md` D53.** Simultaneous multi-Event operation is now supported (D17's single-active-Event restriction is obsolete, not merely relaxed — it existed only to keep `home.md`'s single-actor resolution logic unambiguous, a problem the multi-staff capability itself resolves). Architect-resolvable, no RFC needed for the D17 piece specifically.

**Reallocation mechanism, finalized:** a single local DB transaction spanning both `EventAllocation` rows (source decrement + destination increment + both `AllocationMovement` rows, one commit) is the primary mechanism — architect's explicit recommendation, adopted, since both instances share the same context and (at pilot scale) the same database, making the sequenced-writes-plus-compensation design's partial-failure window structurally unreachable rather than merely conservative. The sequenced-writes design is retained as a documented fallback only, for if `EventAllocation` ever stops sharing one transactional store (a future service split, not needed now). `AllocationMovement` is written unconditionally on every allocation-affecting action regardless of which transactional mechanism is active, giving reconciliation-by-query capability either way.

**Remediation surfaced by the D17 relaxation — both items Resolved, 2026-09-06/07:**
1. **Resolved.** `home.md` §2 steps 2-3 — split into 2a (exactly one qualifying Event, unchanged) / 2b (2+ qualifying Events, new §3.6b "Elegir evento") — no Membership-to-Event assignment added; a SELLER/OWNER picks at Session-open time, per item 3 below.
2. **Resolved.** `events.md` §3.6's entire "Overlap-validation variant (D17)" mechanism was removed outright (not amended); every cross-reference through §2/§4/§8(Q3)/§9/§10/§11 corrected or struck to match, full removed text preserved in `events.changelog.md` per non-deletion discipline.

**Three further product decisions, resolved 2026-09-06 (Product Owner):**
1. **Multi-Business membership: yes, a User may belong to more than one Business.** No invariant restricts this — `architect` confirmed nothing in the Foundation enforces singularity (RFC 0007 §1 deliberately left this open; `authentication.md` §11 is a documentation gap, not an architectural restriction). Every transactional aggregate (`Session`, `Sale`) is already Business-scoped by its own `businessId`, independent of Membership cardinality — no domain-model change needed. The only real gap is a UX signal for "current Business context," deferred to `ux-designer`, not overbuilt until a real multi-Membership case exists.
2. **Removing an accepted SELLER is now part of the membership lifecycle, not deferred.** `BusinessMembership` gains `status: active | revoked` (+ `revokedAt`) — same precedent as `Product.active`/`inactive` (Q21): never deleted, `Sale.performedByMembershipId` keeps resolving unaffected, write-time authorization checks extend to require `status=active`. **Logged directly as `decision-log.md` D55, 2026-09-07** (`reviewer` finding) — this field is not RFC-triggering on its own (no aggregate boundary, no bounded-context edge), so it doesn't need to wait for the larger "Membership invitation and concurrent selling" RFC the way `EventAllocation`/`AllocationMovement`/`Invitation`/`Sale.performedByMembershipId` do — same additive-field class and same standalone-logging precedent as D33/D36/D54. One flagged-not-designed consequence: `(userId, businessId)`'s uniqueness means a future reactivation must flip the same row back to `active`, never insert a second — whether reactivation is ever offered is a small, non-urgent open product-scope question, not resolved here.
3. **SELLER → Event context: session-based selection confirmed sufficient, no OWNER pre-assignment concept added.** A SELLER picks from currently-active Events at Session-open (the same §3.6b mechanism already designed for the general case); once set, `Session.eventId` is immutable for that Session's lifecycle (same "resolved once, upstream" rule already governing `Session.operatingMode`, D23) — every Sale/inventory-consumption within it is deterministically pinned, reusing the exact linkage Price Override resolution already established (Session's `eventId` → which Event's data applies at Sale-write time), not a new mechanism. Residual risk is human mis-selection (not a correctness/architecture risk) — judged disproportionate to add OWNER pre-assignment for at Nahui's actual scale. `ux-designer` may consider a lightweight, non-blocking "Vas a vender en: [Event]" confirmation at selection time as a UX mitigation — not mandatory.

### Q22 — Should the replayed trial Sale (Q19's conversion moment) be classified separately from genuine merchant activity, and how should it appear in Results?

- **Question, raised by the Product Owner (2026-09-03):** Q19's conversion moment replays the pre-auth trial as a genuine, persisted Sale so the merchant doesn't lose the "sale → Results → history" value loop she just experienced. But that Sale happened against sample products, not her real catalog — silently treating it as ordinary business activity risks corrupting her first real financial figures; silently discarding it defeats Q19's whole purpose.
- **`architect` finding:** add an explicit, immutable `Sale.origin: 'genuine' | 'trial'` field, set once at the conversion write, never merchant-editable, never changed afterward — same shape as `SaleItem.pricePaid` (D33), not a mutable capability. Inferring trial status from the seeded Products instead was evaluated and rejected: `Product.active` (Q21) is deliberately general-purpose, not sample-scoped, so a real merchant later deactivating a real product would have her genuine historical sales of it silently misclassified too — a correctness bug worse than the one being solved. Additive field on an existing aggregate, no RFC trigger (same class as D36). The replayed Sale also needs a synthetic wrapping `Session` (schema requires `Sale.sessionId`) — genuinely new, not previously flagged, feeds directly into the eventual Architecture Gap Analysis. Nahui's own internal registration-speed metric (`company/backlog.md` #1) should still count the write regardless of origin — it measures write-path performance, not merchant-facing revenue truth. No second classification needed on `Product`/`InventoryUnit` — Q21 already keeps seeded items off every current selling/reporting surface.
- **`ux-designer` finding:** disclose once, at the conversion moment, that this first sale is now genuinely hers (reusing the disclose-before-the-consequential-moment shape `onboarding.md` §3.4c/§3.6 Variant C already establish, inverted in direction — confirming it's real, not disclaiming it) — never repeated afterward. Recommended against any lasting visible marker, arguing full parity in Results is what actually proves the value loop, and that a permanent badge would reintroduce the "es un ejemplo" framing Q19 exists to eliminate.
- **These two conflict directly, and applying `architect`'s exclusion literally (every `reports.md` aggregation) would leave Results empty right after conversion — recreating the exact problem Q19 was built to avoid.** Resolved by Main, overnight, 2026-09-03, since the Product Owner was unavailable to arbitrate — **flagged explicitly for her review, not a fully confident call:**
  - **Aggregate/summary figures that assert something about her real business performance** — Total histórico, ticket promedio, producto estrella/sales-trend headline statements, Rendimiento por bazar — **filter to `origin = 'genuine'`**. These are exactly the figures where a fabricated first data point does real harm to trust in Nahui's core "real intelligence about her business" premise.
  - **Per-transaction views that only demonstrate the mechanism, not a claim about total business performance** — Historial's session listing, Session/receipt detail ("Por producto" breakdown) — **show the trial Sale as-is, full parity**, satisfying the original goal of letting her explore the complete loop without repeating a sale.
  - `ux-designer`'s one-time disclosure copy/moment is adopted as-is regardless of the above — it's the user-facing acknowledgment; the aggregate/detail split above is a backend correctness question she's unlikely to ever consciously notice.
- **Naming:** `'trial'`, not `'demo'`/`'ejemplo'` — both already reserved for the unrelated "Ver un ejemplo" path (`demo-mode.md`'s own scope note).
- **Named, not resolved:** a low-probability Claim Token edge case (a trial-replay Sale on an already-`paid`-tier conversion would auto-generate a Claim Token like any other Sale, no origin-based exception exists in the domain model) — same class of deferral as Q18, pilot-scale, not a blocker.
- **Status: Superseded, 2026-09-03 (Product Owner).** The Product Owner corrected the underlying premise this entry depended on: the demo/sample experience is explicitly disposable and does *not* need to convert into her real Business/account — no conversion moment exists, so there is no replayed Sale to classify. `Sale.origin`, replay-at-conversion, and the synthetic wrapping Session are all withdrawn, not built. See `product/02-ux/acceso-dm.md` and `decision-log.md` D51 for what actually shipped instead — a disposable, non-convertible entry route reusing the existing "Ver un ejemplo" mechanism, the same class `decision-log.md` D19 already governs. Kept here, unresolved-in-its-original-form but not deleted, per this log's own non-deletion rule.

### Q21 — How does a merchant on the new "Empezar con catálogo de arranque" path remove or replace a pre-seeded sample Product she doesn't want to keep?

- **Question:** Q19's drafted `onboarding.md` amendment (§2.2d) seeds a representative sample Catalog for this path, with a required post-first-sale "Haz que sea tuyo" transition letting her set her real identity and add her own real products. It doesn't address what happens to the *sample* Products already sitting in her Catalog — whether she can delete them, whether they simply coexist indefinitely alongside her real additions, or something else.
- **Why this can't be resolved as a footnote:** verified directly against `inventory.md` in full — no Product-deletion or -replacement mechanism exists anywhere in the current Approved spec. §3.9 "Descartar" only discards an *uncommitted*, in-progress receiving batch, never an already-created Product; §11's future-considerations list doesn't name one either. This is a genuine new capability gap, not an oversight in the Q19 amendment specifically.
- **Not yet resolved:** whether to build Product deletion/archival as a general Inventario capability (benefiting every merchant, not just path-4 entrants), scope it narrowly to sample-Product cleanup only, or leave stale sample rows as an accepted, disclosed cost of the path.
- **Resolution (Product Owner, 2026-08-30):** not deletion — an **active/inactive** state on `Product`. An inactive Product disappears from the selling grid/active Catalog view (so a merchant never sees a stale sample item, or a real item she's discontinued, when trying to sell) but stays fully intact for history, `reports.md`, and every existing `Sale`/`SaleItem` that already references it — no data loss, no broken historical reads. **Scoped as a general Inventario capability, not narrowly to Q19/Q21's sample-cleanup case** — the Product Owner's own framing: this is the normal lifecycle for any merchant retiring a discontinued product, not a Q19-specific fix. Resolves both the sample-data cleanup problem and the general need in one mechanism.
- **Not yet designed:** the actual toggle affordance (where in `inventory.md` a merchant sets a Product active/inactive), whether `reports.md`'s existing figures need any caveat/label change for Sales against now-inactive Products (almost certainly not — historical figures shouldn't change based on a Product's *current* active state), and an `architect` check on whether `active`/`inactive` needs to be a new `Product` field or can derive from something already modeled. Routed to `ux-designer`/`architect`, not designed here.
- **Status:** Resolved in principle (mechanism decided) — build details open, routed to `ux-designer`/`architect`.
- **Amendment, 2026-09-03 — reclassified onto Q19's own critical path, not a side capability.** The Product Owner corrected the relationship: Q21 isn't merely "no longer blocks Q19" — it's the actual mechanism the "Haz que sea tuyo" conversion moment (Q19 §2.2d) depends on. When she converts, the pre-seeded sample Products cannot be deleted (the first demo Sale already references them, and history/`reports.md` must stay intact) — they must be set **inactive**, disappearing from her active selling grid while the Sale record stays whole. Without Q21's active/inactive field, Q19's own conversion step has no way to get the sample catalog out of her way. Treat Q19 + Q20 + Q21 as one coherent value-first onboarding capability, built and reviewed together, not three independently-sequenced items.
