# RFC 0017 — NFC becomes a live, composable selling capability; retires Session-scoped exclusive selling mode and NFC Readiness's threshold/tri-state resolution

**Status:** Accepted (2026-09-18, Product Owner-directed, live production correction)

## The idea

NFC is an additional way to identify a sale, not an alternative selling mode. For a Paid Business with `nfcPerProductEnabled = true`, buttons, barcode scanning, and NFC tag scanning must all be usable in the same active Jornada, simultaneously, for a mixed catalog — with zero close/reopen step the moment a newly-tagged unit becomes sellable.

Triggered by the Product Owner's live-testing finding: a Jornada opened before a unit was tagged never offered NFC scanning for that unit, because `Session.operatingMode` (D23) resolves once at Session-open and NFC Readiness's Ready/Limited Ready/Not Ready threshold (also D23) gates the composed "Leer con NFC" overlay (D71) to the Limited Ready state specifically — both are snapshot/threshold mechanisms that only ever existed to arbitrate an exclusive `buttons`-vs-`nfc` Session mode. D71 already established that NFC composes with `buttons` as a live overlay, the same shape barcode (D65) uses — this RFC removes the remaining session-snapshot/threshold machinery D71 was built on top of but never got to fully supersede.

## What it changes

- **`Session.operatingMode` is removed from `Session`'s schema entirely.** No replacement field. Checked whether `SaleItem`/`Sale` need a new field to record which mechanism (tap/barcode/NFC) resolved a given item, for reporting/traceability: not derivable from the sold unit's identity after the fact, and no real, named need exists today. Per `architecture-principles.md` #5's over-modeling discipline (same restraint as D26's `Sale.claimToken` deferral), no field is added. A real future need for this signal is its own separate, later decision.
- **NFC Readiness (the computed, never-persisted three-state Ready/Limited Ready/Not Ready evaluation, `domain-model.md`) is retired outright**, along with any stored/configured readiness threshold. It is not narrowed or given a new threshold value — no aggregate-coverage computation belongs in this decision under the corrected model. Retired for the identical reason `Session.operatingMode` is: it exists only to arbitrate an exclusive-mode resolution that no longer exists.
- **Selling's surface collapses to one unconditional composition, for every Session, regardless of `Session.operatingMode`'s (now-removed) value:** the buttons grid (always present) + the barcode-scan overlay (`subscriptionTier = paid`, D65, unchanged) + the "Leer con NFC" overlay (`Business.nfcPerProductEnabled === true`, re-evaluated live on every render — no Session-level gate, no threshold). This is the exact shape `home.md` §3.9's existing "Leer con NFC" row already has, minus its third condition ("NFC Readiness currently resolves to Limited Ready specifically") — that clause is deleted; the other two (`Session.operatingMode = buttons` — now moot since there's only one surface, and `nfcPerProductEnabled = true`) collapse to the single remaining live condition.
- **The legacy full-screen `nfc`-only Selling surface (`home.md` §3.10) and its Session-start UI (§3.6a's Ready/Limited Ready/Not Ready/capability-revoked variants) become entirely obsolete**, not merely harder to reach the way D72's one-way escape valve left them. The composable surface is a strict superset of what whole-catalog `nfc` mode offered — no merchant, including the grandfathered/demo population, loses any capability. D72's escape-valve mechanism becomes moot along with it — there's nothing left to escape from.
- **`Business.defaultSellingMode` is fully retired** — traced explicitly, not assumed: its one remaining live reader (D73's own "Honest status" note) was feeding this exact Ready-branch resolution, which this RFC removes. Zero functional readers remain anywhere in the Foundation. Same treatment as `nfcAvailabilityNudgeShown`'s D72 retirement: kept in schema as inert historical data on any already-existing row (never deleted, D25), no code path reads or writes it going forward. Its Settings write actions (§2.3's one-way escape action, §2.6's dead handoff mechanism) retire with it.
- **`registrationMode` / "Selling Mode Capability" is redefined from a set to a boolean.** `buttons` was never actually a gated capability — it was always available — so framing this as "the set of selling modes available to the Business" no longer fits once "mode" itself is gone. The underlying derivation is unchanged (`nfc capability ⟺ subscriptionTier = paid`, D27) — only the ubiquitous-language framing narrows from "a set containing `buttons` (always) and optionally `nfc`" to a single boolean fact, "is NFC available to this Business at all," sitting beneath `nfcPerProductEnabled` as the entitlement layer: (1) tier-derived NFC entitlement (unchanged, load-bearing) → (2) `Business.nfcPerProductEnabled`, the merchant's own opt-in to actually use NFC as an identification method → (3) `Product.nfcTaggingEnabled`, per-Product configuration of which eligible Products use it.
- **`domain-model.md`'s "FIFO allocation (Buttons mode)" Key Mechanism is re-anchored a second time** — from `Session.operatingMode` to the resolution mechanism of the specific add-action (tile tap → FIFO; barcode scan → resolves Product, then FIFO; NFC scan → resolves a specific unit directly, no FIFO) — already true in substance under D71, now universally true rather than true only during the old Limited Ready composition.
- **Bounded-contexts table's Selling "Depends on" cell wording is corrected** — "NFC Readiness's tagged-unit count" becomes a plain description of the live tagged-unit-availability read the "Leer con NFC" overlay's display condition performs. Same dependency edge, same direction, wording only.

## What it does not change

- No new aggregate root, no bounded-context added/removed/rewired — Selling still owns `Session`/`Sale`/`SaleItem`; Inventory still owns `Product`/`InventoryUnit`/`NFCTag`, read-only from Selling. Confirmed explicitly, not assumed.
- `Product.barcode`/`Product.nfcTaggingEnabled` mutual exclusivity (D65/D71) — unchanged, already correctly modeled. Her only complaint here (`inventory.md` §3.4's fifth-zone toggle rendering unlabeled in built code) is a build-vs-spec drift, not a spec gap — the approved spec already carries a label.
- `Business.nfcPerProductEnabled` as the single Business-level capability gate and `Product.nfcTaggingEnabled` as pure per-Product configuration beneath it (D71) — unchanged, already correctly modeled.
- `EventAllocation`'s own NFC scan mechanism at allocation-time (D57/D59/D71's mixed-pile scanner) — a structurally separate, already Product-agnostic mechanism, unaffected.
- The Web NFC hardware-level session/gesture mechanics (D74/D75) — the tap-opens-the-overlay-and-that-tap-is-the-gesture pattern is already correctly built and needs no change; it's orthogonal to this correction, not a constraint on it.

## Architect review

Consulted directly against the full Foundation, `decision-log.md` D10/D23/D27/D46/D71–D75, and the live `product/02-ux/home.md`/`settings.md`/`inventory.md` specs before this RFC was written. `knowledge-mentor` not re-consulted — D74/D75 already established, with live Chromium-source evidence gathered this same project, that no Web NFC platform constraint blocks a fully live/reactive entry-point gate; re-litigating would be redundant, not rigorous.

RFC-worthy on three independent grounds: removes a stored field from a frozen aggregate root (`Session.operatingMode`), redefines/retires four ubiquitous-language terms (Session Operating Mode, NFC Readiness, Default Selling Mode, Selling Mode Capability), and explicitly supersedes/narrows a prior Accepted RFC (0003/D23). No bounded-context edge changes.

Promoted to `product/00-foundation/decision-log.md` D79, superseding/narrowing D23 and touching D27.
