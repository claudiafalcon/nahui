# 0014 — `Invitation.targetHint` becomes required and enforced at acceptance

Status: Proposed. `architect`-drafted (2026-09-15) at Main's request, following a live Product Owner security question during production testing (`product-decisions.md` Q30). **Needs explicit Product Owner sign-off on the tradeoff named in §"Why" below before Accepted** — this reverses a deliberate, named guarantee in an Accepted RFC (0013 §1), and reintroduces real (if smaller) friction than the mechanism it partially reverses.

Supersedes `product/99-rfc/0013-invitation-token-based.md` §1's ruling on `targetHint` specifically ("real, useful, explicitly non-canonical... never matched against, and never promoted to, the accepting `User`'s identity") — on that one point only. The rest of RFC 0013 (token as `Invitation`'s canonical/discoverable identity, the two-write CAS acceptance sequencing, expiry, single-use-by-construction, the decision to reject a channel-type-picker on `Invitation` itself) is untouched and stays fully in force.

## The idea

`Invitation`'s own discoverability mechanism doesn't change: the token, embedded in a shareable link, stays the sole way to find and open the offer, regardless of delivery channel — RFC 0013's central point, unrelitigated here. What changes is a second, independent gate at the moment of acceptance: `targetHint` (today, an OWNER-entered email address) becomes **required** at `create_invitation()` — no more optional field — and **enforced** at `accept_invitation()`: the authenticating User's own resolved `AuthIdentity(type='email')` set must contain a verified match, or acceptance is refused.

This directly answers the security gap the Product Owner raised live: today, a leaked or forwarded invite link lets any stranger who can complete any supported auth method (phone, Google, or email) join her Business as a SELLER, regardless of who the OWNER actually meant to invite. RFC 0013 §4 named this exact risk explicitly and accepted it as a known, low-probability risk at pilot scale ("zero live instances"); the Product Owner's live report tonight is new information changing that calculus, not a reason to relitigate the original ruling.

**Phone is deliberately excluded from this mechanism.** `decision-log.md` D63 records the Product Owner's own explicit instruction: *"phone number must not be the canonical identity of either the invitation or `BusinessMembership`"* and *"it would be inconsistent for an OWNER to need the SELLER's phone number in order to invite them."* Binding acceptance to phone — in any form — would directly contradict an instruction she gave this same day, for the same feature. Email, by contrast, she explicitly reserved room for in that same instruction: *"An email address used to deliver or target an invitation may be useful for security/UX, but please do not assume it must become the canonical identity of the resulting membership."* This RFC uses email as exactly that — a security/UX gate on *acceptance*, never as `BusinessMembership`'s own canonical identity (which stays `userId`, unchanged).

## What it touches

- `domain-model.md` / `ubiquitous-language.md`: `Invitation.targetHint`'s entry — from "optional, advisory-only, structurally never matched" to "required, verified-match enforced at acceptance." No schema addition — the field already exists (RFC 0013).
- `accept_invitation()` (real SQL RPC, `product/02c-high-fidelity-prototype/supabase/migrations/`) — gains a new precondition check, before the existing status CAS, so a mismatched attempt never consumes the token: the authenticating user's resolved `AuthIdentity(type='email', verifiedAt is not null)` must include a row matching `lower(trim(targetHint.value))`. On mismatch, raises a new, distinct error (`invitation_identity_mismatch`), never `invitation_not_available` — the invitation itself is still perfectly valid, just not for this person.
- `create_invitation()` — `p_target_hint` changes from `default null` (optional) to required; reject a null value going forward.
- `regenerate_invitation()` — no change; it never touches `target_hint`.
- `settings.md` §2.7/§3.12 ("Invitar a alguien") — email becomes a required field on the invite-creation form, not optional. New copy needed explaining why (a short, honest line — "para que solo esa persona pueda aceptar").
- `authentication.md` §3.10–§3.13a (Invitation-acceptance flow) — a new mismatch state: the invited person opens a perfectly valid link, authenticates successfully, but her verified email doesn't match what the OWNER entered. Needs a real screen (not silently routing into `invitation_not_available`'s existing dead-end copy, which would misleadingly imply the link itself is broken/expired) — likely something naming the mismatch plainly and suggesting she ask the OWNER to check the email she used, or that the OWNER regenerate/correct it.
- **Not touched:** `Invitation.token`'s own role as the discoverability mechanism, the two-write CAS sequencing, expiry, single-use-by-construction, `BusinessMembership`'s schema, `EventAssignment`, the Owner-creation invariant, `AuthIdentity`'s own two invariants.

## Why

**The security gap is real and freshly confirmed, not hypothetical.** RFC 0013 §4's own risk acceptance was reasoned from "pilot scale, zero live instances" — a probabilistic argument that gets weaker, not stronger, as real usage grows, and the Product Owner is now actively thinking about exactly this exposure while testing the live, real feature. Closing it costs nothing structural: the token stays the universal discovery mechanism RFC 0013 designed; this is a narrower, additive acceptance-time check layered on top, not a redesign.

**Why this specific mechanism doesn't reverse RFC 0013's actual point.** RFC 0013 §1's central finding was that `Invitation`'s *identity* must not be a communication channel — a type-picker on the Invitation itself would force the invited person to authenticate through whichever channel the OWNER happened to guess, which is backwards. This RFC doesn't touch that: the token remains sole and canonical for *finding* the offer. What's added is a second, independent check at the moment of *accepting* it — closer in spirit to RFC 0013 §4's own already-named, already-considered-but-undesigned mitigation ("a post-acceptance soft warning if the authenticated identity's own email doesn't match `targetHint`") than to a reversal. This RFC goes further than that soft-warning idea (a hard block, not just a warning) because a warning alone doesn't actually close the security gap the Product Owner is asking about — it only surfaces it after the fact, by which point the wrong person already has SELLER access.

**Why the tradeoff still needs her explicit sign-off, not just architect's approval.** This is not a free win: it reintroduces real friction. The OWNER must know the SELLER's correct email in advance and enter it accurately — the exact category of friction RFC 0013 existed to remove for phone specifically (RFC 0013's whole premise was decoupling from needing to know a channel in advance). It's a smaller cost than the retired phone-keyed design (email carries none of the Mexican phone-verification/WhatsApp Business Sender friction that motivated D62/D63's move away from phone), but it is not zero, and trading a real security gap for a real (if smaller) friction cost is a product call, not an architecture call.

## Mismatch UX, named explicitly rather than left to a builder to invent

A typo'd or wrong email locks out the real, intended SELLER — she opens a valid, unexpired link, authenticates successfully, and is told she can't accept. This needs a clear, non-alarming explanation (not "this invitation is invalid," which is false — the invitation is fine, it's the wrong person/identity, or the OWNER made a data-entry mistake) and a real repair path: the OWNER can correct `targetHint` on the still-`pending` row via an ordinary `UPDATE` (the existing OWNER-scoped `invitations_update` RLS policy already permits this, no new RPC needed) or regenerate the invitation entirely. Designing this screen is `ux-designer`'s job once this RFC is Accepted, not fixed here — named so it isn't silently dropped as a "just handle the error" afterthought the way a narrower fix might.

## Backward compatibility

Already-`accepted` Invitations (including any accepted tonight) are completely untouched — the new check only runs inside the live acceptance CAS path, never retroactively against history. Any `Invitation` still `pending` with `targetHint = null` at the moment this ships (created before enforcement) is treated as a legacy row exempt from the check — enforcement is null-guarded, not a hard-fail-everything migration. No backfill needed; the OWNER can optionally set a hint on an old pending row to opt it in, or simply let it expire/regenerate normally.

## RFC-trigger test

Reverses a specific, explicitly-stated structural guarantee inside an Accepted RFC (0013 §1: "never required, never treated as identity... structurally never matched against the accepting User's identity") and redefines what `targetHint` *means* in `ubiquitous-language.md` (from a non-canonical delivery aid to an enforced identity precondition) — the same weight class RFC 0013 itself was for RFC 0012 §3. **RFC required**, following the exact template RFC 0013 already used against RFC 0012: a new, numbered RFC that narrowly supersedes one specific ruling in an existing Accepted RFC, leaving everything else in that RFC untouched.

## Decision needed from the Product Owner

Not "should Nahui use email for this" (architect already ruled out phone directly from her own D63 instruction, and recommends email) — the actual open question is narrower: **do you want to trade the friction above (you must know and correctly enter the SELLER's email before they can join) for closing the leaked-link exposure, now, tonight?** If yes: this RFC is Accepted as drafted, `ux-designer` designs the mismatch-repair screen, and it ships through the same build pipeline as everything else tonight. If not yet: this stays Proposed, logged and discoverable, and the risk stays exactly where RFC 0013 §4 already, knowingly, left it.
