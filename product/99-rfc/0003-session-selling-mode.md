# 0003 — Session-scoped selling mode: capability as availability, business default, and inventory-readiness recommendation

Status: Accepted

## The idea

`registrationMode` splits from a single Business-wide scalar into three distinct concepts:

1. **Capability (availability)** — Business-level, `Identity` context. Becomes a set of allowed modes rather than one active value: `buttons` always available; `nfc` an add-on entitlement (subscription/kit-gated, per `company/CLAUDE.md`'s existing NFC-kit framing).
2. **Default** — Business-level, `Identity` context. A new stored field (**Default Selling Mode**, `defaultSellingMode`): the Business's normal operating mode, set via Onboarding (consistent with D19) and read as the fallback value at Session start — readable, but not itself the operative value.
3. **Operating mode** — Session-level, `Selling` context. A new stored field on `Session`, resolved once at Session-open time and immutable for the remainder of that Session's `active` lifecycle.

Between (2) and (3) sits a **computed, never-persisted recommendation**, driven by a three-state NFC-readiness evaluation run at Session-open time against existing Inventory data (available `InventoryUnit`s with vs. without an assigned `NFCTag`):

1. **Ready** — sellable tagged inventory is above the readiness threshold. If `nfc` matches the Business's stored default, the Session starts silently in `nfc` — no UI moment, identical to today's behavior.
2. **Limited Ready** — some tagged inventory exists, but coverage is below the readiness threshold. The system recommends `buttons` via a single lightweight inline nudge at the Session-start action; the merchant may override and continue in `nfc` if her capability set allows it.
3. **Not Ready** — precisely defined: **zero sellable tagged inventory units are available for the Session** (no `available` `InventoryUnit` with an assigned `NFCTag`). This is not a UX restriction or a stricter recommendation — it is an operational impossibility: `nfc` requires a physical tag to scan, and none exists to scan, so `nfc` is not offered as a choice at all for that Session, overridable or otherwise. `buttons` is offered as the primary action (it needs no tag, so it is always operationally possible whenever any sellable inventory exists); "Asignar tags" (Inventario's existing tag-assignment flow) is offered as a secondary, optional setup action. **Selling itself is never blocked** — only the impossible mode is withheld, the same way Home never blocks the nav bar on a load failure (`home.md` §3.14 precedent).

The recommendation is shown **only when it disagrees with the stored default** — Ready-and-matches-default is the common case and stays fully silent, preserving the substance of `architecture-principles.md` #1 ("capabilities resolved once, upstream, never asked mid-flow") even though the literal mechanism is now a per-Session read rather than a single frozen value. The Session's actual operating mode can therefore diverge from the Business's stored default in exactly two ways: an automatic downgrade to `buttons` at Not Ready (no choice involved — nothing to override), or an explicit merchant decision to override a Limited Ready recommendation.

## Explicit decisions this RFC fixes

- **The readiness threshold is a configurable product/business rule, not a value hard-coded into the Foundation.** The Foundation defines the three-state mechanism and where the threshold is read from; it does not fix the number itself.
- **If NFC capability is revoked while a Session is already active** (e.g., a subscription lapse), that Session finishes normally in whatever mode it already resolved. The restriction takes effect starting with the next Session only — an active Session is never destabilized mid-day.
- **Business stores the Default Selling Mode** (new field, `defaultSellingMode`, distinct from the capability set) — its normal operating mode. The Session's actual operating mode may resolve differently, per the readiness evaluation and any explicit merchant override.
- **Session stores the selected, immutable-while-active operating mode** (new field) — this closes a real, previously-identified gap: Session never used to snapshot which mode it ran under, since there was historically only ever one value to read. Surfaced during the Q5 analysis (`company/business-decisions.md`, currently paused), and fixed here as a direct consequence of this model rather than as a separate change.
- **The recommendation is computed at Session start, never stored**, and shown only when it differs from the stored default — never a mode-confirmation step shown on every Session.
- **"Not Ready" means zero sellable tagged inventory units, full stop — not a low-inventory judgment call.** It is the presence or absence of at least one scannable, `available` tagged unit, nothing softer. Below the configurable threshold but above zero is "Limited Ready" (a recommendation, still overridable); exactly zero is "Not Ready" (`nfc` withdrawn from the choice set entirely, because there is nothing it could possibly scan).
- **This does not hard-block sales.** Buttons mode is always available whenever any sellable inventory exists (it needs no tag), so a merchant can always sell, in some mode, at all three readiness states. What's withheld in the Not Ready state is specifically *the operationally impossible mode* — never selling itself.

## Why

Raised when the Product Owner paused Q5 (`company/business-decisions.md`) to consider whether a richer model — separating capability, a Business-level default, and per-Session recommendation — would resolve the same underlying question more cleanly than a direct self-service-editability answer to Q5 alone.

Evaluated jointly by Architect (domain-modeling soundness) and UX Designer (interaction/friction), independently, before any Foundation change was proposed:

- **Architect** confirmed the four-way conceptual split is sound and maps cleanly to three homes (Business capability set, Business default, Session operating mode), with the recommendation itself correctly modeled as computed, not persisted. Confirmed the underlying readiness computation is cheap and answerable entirely from existing Inventory data, with no new bounded-context dependency edge required. Classified this as RFC-worthy (not a plain decision-log entry) because it redefines a ubiquitous-language term and adds a new stored field to a frozen aggregate (`Session`) — the same category as RFC 0002, not D17/D19's direct-entry precedent. Confirmed this resolves, by construction, the Session-snapshot gap identified during the Q5 analysis, and confirmed the subscription-downgrade invariant (revoking NFC never touches existing tagged inventory or historical data) holds structurally, since `NFCTag` assignment and `InventoryUnit.status`-based claim disambiguation (D10) were never modeled as depending on the Business's *current* capability state.
- **UX Designer** confirmed the model is only sound if the recommendation stays silent except on disagreement with the stored default — built as a mode-confirmation shown every Session, it would regress against "never ask twice" and the existing 2-tap Session-start floor (`home.md` §6). Confirmed the readiness computation must fold into the resolution query Home already runs at Session open (no new perceptible delay, no new loading-state convention), and that the threshold itself must stay invisible to Ana as a number — any surfaced recommendation uses plain business language, never a count or percentage.

The Product Owner then refined the model directly with the three explicit readiness states above (Ready / Limited Ready / Not Ready) — distinguishing "recommend but allow override" (Limited Ready) from "operationally impossible, don't offer it" (Not Ready) as two different situations, not one — and confirmed the specific decisions on threshold configurability, mid-Session revocation handling, and the Business/Session storage split now recorded above.

**Terminology refinement, post-approval-in-principle:** the Product Owner approved the overall model but asked that the Business-level stored field be named "Default Selling Mode" rather than "Preferred Selling Mode" (or a better term, if Architect judged one clearer) — the field represents the Business's normal operating mode, used as a fallback the Session may resolve away from based on readiness and an explicit merchant decision, not a subjective preference Ana would need to keep updating. Architect confirmed **"Default Selling Mode"** (`defaultSellingMode`) directly: it fits the shape of the other three terms, matches the field's actual role better than "preferred," and creates no naming collision with the unrelated, lowercase "default" already used in `domain-model.md`'s FIFO-allocation prose (D5) — a different concept in a different context, not to be conflated. The Product Owner also asked that the "Not Ready" state be defined with no ambiguity: it is exactly zero sellable tagged inventory units, an operational impossibility (nothing to scan) rather than a UX-level restriction, with Buttons always remaining available so selling itself is never blocked — both refinements are applied throughout this RFC above.
