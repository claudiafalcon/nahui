# RFCs

This folder is intentionally separate from `product/00-foundation/`.

`00-foundation` is the frozen source of truth — domain model, information architecture, principles, decision log. This folder is the opposite: a staging ground for ideas, experiments, and future proposals *before* they've earned a place there.

## Rules

- **Every significant new idea starts as an RFC.** If it would change or extend the domain model, capabilities, information architecture, or principles, write it down here first — don't edit `00-foundation` speculatively.
- **RFCs may challenge or extend the current foundation.** That's the point. An RFC can propose replacing a frozen decision, not just adding to it.
- **RFCs are not the source of truth.** Nothing here is binding. Code and design should never cite an RFC as justification — only `00-foundation` counts.
- **Only approved decisions are promoted into `00-foundation`.** When an RFC is accepted, update the relevant `00-foundation` doc(s) and add an entry to `00-foundation/decision-log.md` referencing the RFC. The promotion is the thing that makes it real, not the RFC itself.
- **Historical RFCs are never deleted.** Rejected, superseded, or outdated RFCs stay in place — they're design history, not clutter. Don't renumber or remove them either; if a later RFC replaces one, mark the old one `Superseded` and link forward to the new one.

## Workflow

1. Write the idea as a new RFC file.
2. Discuss and refine it in place.
3. Mark its outcome (see Status below).
4. If accepted: update `00-foundation`, add a `decision-log.md` entry that references this RFC, then mark the RFC `Accepted`.
5. If rejected or superseded: mark it accordingly and leave it in place.

## File naming

`NNNN-short-title.md`, numbered sequentially starting at `0001`, e.g. `0001-loyalty-tag-reuse.md`. Numbers are never reused or reassigned, even for rejected RFCs.

## Status labels

Each RFC should state its status near the top: `Proposed`, `Accepted`, `Rejected`, or `Superseded by NNNN`.

- `0012-auth-identity-multi-method.md` — **Accepted** (2026-09-13, `decision-log.md` D62). Introduces `AuthIdentity` (new Identity-context aggregate root): one `User` may hold multiple linked, independently-verifiable authentication credentials (phone; now also email/Google, activated same-day as cold-sign-up methods, D63 — Apple still modeled but not exposed), decoupling `User`'s identity from any single credential. `User.phone`/`phoneVerifiedAt` removed, replaced by a pointer to `AuthIdentity`; the Owner-creation invariant (D44) and Invitation-acceptance invariant (D56) both amended to resolve through `AuthIdentity` (guarantees unchanged, only the field path is corrected). `Invitation` deliberately stays phone-specific in this RFC's own §3 ruling (a reasoned choice, not a default) — **§3's ruling on this point is Superseded by RFC 0013 (D64), the same day.** New AuthIdentity-resolution and linking/duplicate-prevention invariants make "adding a method never creates a second business identity" structural; Invariant C's duplicate-User gap is a knowingly-accepted live risk as of D63, not merely theoretical. Confirms zero UX change to `authentication.md`'s already-Approved phone-OTP flow — a data-layer rewire underneath an unmodified spec, same posture as RFC 0007/0008. `knowledge-mentor`-confirmed against Supabase Auth's own native multi-provider `identities` model. Triggered by the Product Owner's direction not to let phone remain `User`'s fundamental identity, prompted by field feedback that a new Mexican government mobile-line-registration policy is making some prospective merchants reluctant to register a phone number at all.
- `0013-invitation-token-based.md` — **Accepted** (2026-09-13, `decision-log.md` D64). Reworks `Invitation` from phone-keyed to token-keyed: `Invitation.phone` replaced by `token` (a cryptographically random, unguessable, single-use value embedded in a shareable link — the Invitation's canonical identity, `knowledge-mentor`-confirmed against OWASP Forgot Password/Password Storage guidance), plus `expiresAt` (closes a standing gap — `expired` existed in the status enum since D56 with no defined trigger) and an optional `targetHint` (delivery/addressing aid only, structurally never canonical). Invitation-acceptance invariant genuinely reworked, not just re-pathed: the invited person now discovers the Invitation by opening its link *before* authenticating, resolved through two separately idempotency-keyed writes (identity resolution via RFC 0012's unmodified mechanism; then a CAS-guarded `acceptInvitation`). Triggered by D63 (Google/Email activated as cold-sign-up methods, making phone-required SELLER invitations inconsistent) — the Product Owner's own conceptual flow is quoted in full in `decision-log.md` D63. `authentication.md`/`settings.md`'s own amendments and the already-built `product/02c-high-fidelity-prototype/` Slice 12 code's Migration-Workflow pass are both real, not-yet-started follow-on work, not blocking this Foundation promotion. **§1's ruling on `targetHint` specifically is Superseded by RFC 0014 (Proposed), pending Product Owner sign-off.**
- `0014-invitation-target-hint-enforced.md` — **Accepted** (2026-09-15, Product Owner — "I think email is fine," plus her own refinement of the mechanism; promoted to `decision-log.md` D70). Narrowly supersedes RFC 0013 §1's ruling on `targetHint` only (everything else in RFC 0013 — token as canonical identity, the two-write CAS sequencing, expiry, single-use — untouched): `targetHint` (an email) becomes required at `create_invitation()`, and the Invitation-acceptance flow authenticates the invited person specifically through the Email method, pre-filled and locked to that address — not any of the three methods generally, checked afterward. Chosen over a post-hoc any-method match check for a concrete technical reason, not just simplicity: `AuthIdentity(type='google').identifier` is the provider's opaque subject ID, never the real email, so a match check could never pass for a Google sign-in even with the exactly-right account. `accept_invitation()` still defensively re-verifies the match server-side before its status CAS. Phone is deliberately excluded — `decision-log.md` D63 records the Product Owner's own explicit instruction that phone must never become canonical identity for Invitation/Membership. Closes a real leaked-link exposure RFC 0013 §4 knowingly accepted as a risk at pilot scale; trades it for real (smaller than the retired phone-keyed design) friction, accepted explicitly. Routed to `ux-designer` for `authentication.md`'s two new mismatch states and `settings.md`'s now-required invite-email field.
