# 0013 — Token-based `Invitation`: decoupling SELLER-onboarding from any single communication channel

Status: Accepted (Product Owner, via delegated authority, 2026-09-13) — promoted into the Foundation, `decision-log.md` D64. `reviewer` found and closed 2 Important + 3 Suggestions across two rounds before promotion (a missing citation for the Product Owner's own quoted instruction, now recorded in full in `decision-log.md` D63; a missing note on the already-built `product/02c-high-fidelity-prototype/` code needing its own Migration-Workflow pass; three smaller accuracy/terminology fixes). `authentication.md`/`settings.md`'s own amendments (§6) and the prototype rebuild are separate, not-yet-started follow-on work, not blocking this Foundation promotion.

Supersedes `product/99-rfc/0012-auth-identity-multi-method.md` §3's "kept `Invitation` phone-specific" ruling, on that one point only — the rest of RFC 0012 (the `AuthIdentity` aggregate itself, the Owner-creation invariant's amendment, the AuthIdentity resolution/linking invariants) is untouched and stays fully in force. Per `product/99-rfc/README.md`'s own non-deletion/supersession discipline (historical RFCs are never edited in place, only superseded by a later one — the same convention `decision-log.md` already applies to itself, e.g. D53 superseding D17, D61 superseding D48/D51/D52), RFC 0012 §3's text is marked `Superseded by RFC 0013`.

Triggered by `decision-log.md` D63 (Product Owner, 2026-09-13): Google and Email are now genuine cold first-time sign-up methods, no phone required. That directly breaks RFC 0012 §3's own reasoning for keeping `Invitation` phone-specific — a reasoning that assumed phone was the only way to become a `User` at all. D63 names this consequence explicitly and routes it here rather than patching it ad hoc.

## The idea

`Invitation.phone` was never really about phone as a channel — it was standing in for "the specific person this offer is for." Under phone-only sign-up that distinction never mattered, because a verified phone number *was* the only identity a person could hold. Now that identity is multi-method (`AuthIdentity`, RFC 0012/D62) and a brand-new `User` can be created cold via phone, email, or Google (D63), `Invitation` needs its own real identity — one that doesn't presuppose which authentication method the invited person will eventually use.

This RFC replaces `Invitation.phone` with `Invitation.token` — a cryptographically random, unguessable, single-use value embedded in a shareable link — as the Invitation's canonical identity. An optional `targetHint` (today: an OWNER-entered email address) rides alongside it, purely as a delivery/addressing aid, explicitly never matched against, and never promoted to, the accepting `User`'s identity. This directly implements the Product Owner's own conceptual flow, quoted in full in `decision-log.md` D63: **OWNER creates invitation → invited person opens invitation → authenticates/signs up using any supported method → authenticated Nahui User accepts invitation → `BusinessMembership` is created for that User.**

Five things follow, developed in full below:

1. **`Invitation`'s canonical identity becomes its `token`, not a channel value.** A "secure invitation link" and an "email invitation" aren't competing designs — the link *is* the universal mechanism; email is one optional way of getting that link in front of someone. `targetHint` is real, useful, and explicitly non-canonical.
2. **The Invitation-acceptance invariant is genuinely reworked, not merely re-pathed** (unlike RFC 0012's own treatment of the same invariant, which only corrected a field-resolution path). The sequencing inverts: the invited person now discovers the Invitation *before* authenticating, not as a side effect of authenticating. Two separately idempotency-keyed writes replace one — identity resolution (unchanged, RFC 0012's own mechanism) and Invitation consumption (new).
3. **Every other Foundation decision touching `Invitation`/`BusinessMembership` is checked individually** — `BusinessMembership` itself, `EventAssignment`, the Owner-creation invariant, `Sale.performedByMembershipId` — all confirmed unaffected, for stated reasons, not by assertion.
4. **Security mechanics are named explicitly**: token entropy/format, expiry (closing a standing gap — `Invitation.status`'s `expired` value has existed in the schema since D56 with no trigger ever defined), single-use-by-construction, and the forwarded/leaked-link risk, with an explicit accepted-risk posture at current pilot scale.
5. **Genuine new UX is required** — checked directly against `authentication.md`'s and `settings.md`'s actual current text, not asserted. This is the opposite finding from RFC 0012, which confirmed zero UX change; this RFC cannot make that claim and doesn't try to.

## Why

### 1. `Invitation`'s identity becomes a token, not a channel value

**The structural problem with generalizing to `(identifierType, identifier)`, the option RFC 0012 §3 itself named and rejected.** A type-picker (`phone` | `email`) on `Invitation` would reintroduce exactly the coupling the Product Owner is now explicitly asking to remove: it would make the Invitation's identity *still* a communication channel — just a wider menu of them — and it would force the invited person to authenticate through the *same* channel the OWNER happened to pick when creating the Invitation, or the match fails. That's backwards for a world where the invited person can now authenticate via phone, email, or Google independently of which one the OWNER thought to use. The Product Owner's own conceptual flow makes this explicit: the OWNER creates a standing right to join; *how* the invited person later proves who she is is her own choice, made at acceptance time, not predetermined by the OWNER at invite time.

**The token is the only field that can play this role without smuggling a channel back in.** A cryptographically random, unguessable value has no channel of its own — it's addressed to "whoever holds this specific value," which is exactly the shape a bearer token (a security-jargon term, deliberately not this Foundation's capitalized **Capability** concept — see the disambiguation note in the Ubiquitous-language section, below, which extends the same collision-avoidance discipline this RFC already applies to the Claim-Token distinction) needs: possession of the token *is* the authorization to view-and-potentially-accept this specific offer. This is the same class of mechanism already well-established in web authentication practice — password-reset links, email-verification links, OAuth authorization codes — confirmed against OWASP's own guidance, not a novel invention (`knowledge-mentor`, see §7).

**`targetHint` — real, useful, explicitly non-canonical, exactly as instructed.** An optional field, `{ type: 'email', value: <address> }` today (closed set of one hint type, extensible later the same way `AuthIdentity.type` is — not a build decision made here). Two legitimate uses, both named explicitly so neither is silently assumed: (a) lets Nahui optionally deliver the link by email automatically, and (b) gives the OWNER a memory aid in her own "Tu equipo" pending-invitations list ("sent to ana@..."). **What it is never used for:** matched against the accepting `User`'s resolved `AuthIdentity` at acceptance time. Per the Product Owner's own instruction (`decision-log.md` D63), stated here as a structural guarantee, not a convention: the acceptance write (§2) never reads `targetHint` at all. If the OWNER wants assurance that a *specific* known person accepted (not "whoever got the link"), that assurance is operational — she shares the link through a channel she trusts reaches that person (a direct WhatsApp DM, a hand-off in person) — never structural. This is named explicitly in §4 rather than left implicit, the same discipline D63 applied to its own accepted risk.

**Evaluating the Product Owner's two named options directly, as instructed.** (a) *Email-delivered invitation* and (b) *secure shareable link* are not mutually exclusive, and treating them as competing designs would be a false choice: (b) is the structurally required universal mechanism (every Invitation has a token, always), and (a) is one optional delivery method for getting that link in front of someone — the OWNER can always fall back to sharing the raw link through any channel (WhatsApp, SMS, in person) even if Nahui never builds real transactional email sending at all. This mirrors, deliberately, the exact operational lesson D63 just taught: WhatsApp Business Sender verification (`company/business-decisions.md` Q19) turned out to be real infrastructure friction gating a whole sign-up path — building email-sending infrastructure now, before it's validated as needed, risks the identical trap. **Resolved (Main, on the Product Owner's delegated authority, 2026-09-13): ship the token/link mechanism as the one required capability; treat "Nahui sends the email automatically" as a separable, optional enhancement** that can land later without changing the domain model at all, since `targetHint` already exists to support it whenever it does.

### 2. The Invitation-acceptance invariant, reworked — the sequencing inverts, and two writes replace one

**The old mechanism discovered the Invitation as a side effect of authenticating** (`Invitation.phone` happened to match the number she just verified). **The new mechanism discovers the Invitation first, from the URL, before authentication runs at all** — this is the direct, load-bearing consequence of the Product Owner's own conceptual flow (`decision-log.md` D63: "invited person opens invitation → authenticates"), not a free architectural choice; the two-write sequencing and CAS mechanics below are `architect`'s own synthesis of that instruction, not themselves quoted from it. Mechanically:

1. Invited person opens `https://nahui.app/invite/<token>` (exact route shape is a `ux-designer`/`ui-designer` decision, not fixed here).
2. Client resolves the `Invitation` by `token` alone — the same "resolvable before any other aggregate is in context" test that already justified `Venue`/`BusinessMembership`/old-`Invitation`/`EventAssignment` as roots, applied one level differently: previously resolvable by phone *before any Business was in context, at OTP-verification time*; now resolvable by token *before either a Business or a User is in context, at link-open time*. Still fails the internal-only-entity test (`architecture-principles.md` #4) the identical way — stays a root, no reclassification.
3. If `status = pending` and not expired (§4): show the offer (Business name, what a SELLER can do — content `ux-designer` can carry forward largely as-is from the existing §3.10 copy, per §6). One deliberate confirming tap, matching every other real-commitment convention this Foundation already holds itself to (`authentication.md §3.10`'s own "a real commitment costs one deliberate tap, never zero, never two").
4. That one tap is the entire commitment — there is no second confirm after authentication. If a valid session already exists on the device, the acceptance write (step 6, below) runs immediately. If not, she's routed into authentication, through whichever method she chooses — the existing, entirely unmodified `AuthIdentity` resolution invariant (RFC 0012 §4: first-ever-credential creation, additive linking, or a plain read of an already-linked credential — this RFC introduces no fourth shape) resolves her to a `userId`.
5. The token must survive the authentication sub-flow the same way any other in-progress work in this product already survives an app close/backgrounding/interruption (`authentication.md §3.8`'s existing guarantee, generalized to also carry this one additional piece of context — not a new guarantee, an extension of one that already exists).
6. Once a `userId` is resolved (by whatever path), a **second, separately idempotency-keyed write** — `acceptInvitation(token, userId)` — runs: atomically creates `BusinessMembership(userId, businessId, role=SELLER, status=active)` and flips `Invitation.status: pending → accepted`, conditioned on `status` still being `pending` at write time.

**Why two separately-keyed writes, not one three-way mega-transaction spanning identity creation, is the right shape — not just precedent-matching.** The Owner-creation invariant already establishes the pattern: verification is a precondition satisfied by a prior write, and the Business/Membership-creation write only ever touches an already-verified `User`. The reason to keep the same separation here is concrete, not just consistent: a cold sign-up can complete through three structurally different technical triggers (OTP confirm, an email-verify link click, an OAuth callback) — coupling Invitation-consumption into each of those would mean every one of them needs its own bespoke "was this triggered from a pending-invitation flow" branch. Keeping them decoupled means **any** successful identity resolution, however it happened, arrives at a plain `userId`, and the exact same `acceptInvitation(token, userId)` write runs identically regardless of method. This is a real reduction in surface area, not a restatement of precedent for its own sake.

**Idempotency and replay — two distinct guarantees, not one, per `architecture-principles.md` #7/D30.** (a) The idempotency key (generated once at the confirming tap, reused on retry) protects against **the same person's own retried attempt** producing a duplicate `BusinessMembership` or an ambiguous accept state — identical class of guarantee every other retryable write in this Foundation already carries. (b) The conditional write on `Invitation.status = pending` (a compare-and-swap, the same class of conditional write `AuthIdentity`'s global uniqueness and `EventAllocation`'s physical-exclusivity guard already use) protects against **two different people racing the same token** — a forwarded/leaked link opened by two people near-simultaneously. These are genuinely different failure modes and need both mechanisms; an idempotency key alone would not stop a second, different actor's *first* attempt from succeeding. Naming this distinction explicitly is the same discipline D59 already modeled when it corrected a counter-based CAS that looked sufficient but wasn't.

**This is also what makes the token single-use by construction, with no separate "consume" step needed** — the CAS on `status` *is* the single-use mechanism, reusing machinery already established elsewhere in this Foundation rather than inventing new machinery for it.

**The old design's "more than one pending Invitation, most-recent wins" tie-break (old `authentication.md §2.2a` step 2) is eliminated, not carried forward.** It existed only because phone-matching could surface more than one pending Invitation simultaneously for the same verified phone. A token always identifies exactly one Invitation — there is no ambiguity left to tie-break. Simplification, not a gap.

**The old design's per-device decline-memory marker (old `§2.2a` step 6) is also eliminated, not carried forward.** It existed to stop an already-declined offer from resurfacing automatically on every subsequent app open, because the old mechanism *did* automatically resurface it (phone-matching runs on every session-resume check). The new mechanism never auto-surfaces anything — an Invitation is only ever seen by explicitly opening its link. If she declines, she simply doesn't reopen the link; nothing needs to be remembered. A real structural simplification, named here so it isn't mistaken for an oversight when `ux-designer` finds the old mechanism gone.

### 3. Every other Foundation decision touching `Invitation`/`BusinessMembership`, checked individually — the same discipline RFC 0012 §3 modeled

**`BusinessMembership` (D44, D55, D56) — confirmed unaffected, schema unchanged.** Still references `userId`, never a credential value of any kind, directly or indirectly. Its own uniqueness (`userId, businessId`) already protects against a double-accept producing two rows for the same User/Business pair even before the CAS above is considered — a belt-and-suspenders confirmation, not a new mechanism.

**`EventAssignment` (D60) — confirmed genuinely unaffected, checked directly against its schema, not assumed.** `EventAssignment.membershipId` references `BusinessMembership` by ID only (`domain-model.md`'s own text: "same pattern as `Sale.performedByMembershipId`"). No field, join, or resolution path anywhere in `EventAssignment` ever touches `Invitation` in any form, phone-keyed or token-keyed. Zero change.

**The Owner-creation invariant (D44, amended RFC 0012/D62) — confirmed unaffected, no further change needed.** It governs a person creating her *own* Business through Onboarding — an entirely separate mechanism from SELLER-onboarding-via-Invitation, sharing no field, write path, or resolution logic with `Invitation` at all. RFC 0012's own amendment (verified `AuthIdentity` of any type, not phone-specific) already stands complete and correct; this RFC touches nothing here.

**`Sale.performedByMembershipId` (D58) — confirmed unaffected**, for the identical reason RFC 0012 §3 already gave: it references `BusinessMembership` by ID only, populated from already-resolved authorization context. Neither `Invitation`'s old phone-keying nor its new token-keying was ever visible to Selling in any form.

**`authentication.md`'s and `settings.md`'s actual current text — checked directly, and genuinely stale, not merely field-path-corrected.** See §6 — the one place this RFC's findings diverge sharply from RFC 0012's own "zero UX change" conclusion.

### 4. Security mechanics, named explicitly

**Token format — confirmed, `knowledge-mentor`, §7.** A cryptographically random value, minimum 128 bits of entropy, CSPRNG-generated, URL-safe encoding — the same class of guarantee any bearer-token-URL/magic-link mechanism requires, now checked against OWASP's own Forgot Password Cheat Sheet rather than left as unconfirmed judgment. **Tokens must be stored hashed at rest, never raw** — a leaked database must never yield a usable token (OWASP Password Storage Cheat Sheet, confirmed §7). The token-lookup endpoint must be rate-limited per IP against enumeration attempts. Exact generation library/encoding stays an implementation detail below this RFC's abstraction level, flagged for the eventual Architecture Gap Analysis.

**Expiry — closes a standing gap, doesn't just add a new field, and carries a real tension surfaced by `knowledge-mentor` (§7).** `Invitation.status`'s `expired` value has existed in the closed set since D56 (`domain-model.md`: "`pending` | `accepted` | `revoked` | `expired`") with **no trigger ever defined for it** — a gap the old phone-based design could tolerate indefinitely (a pending Invitation costing nothing to leave open, since accepting it still required possessing the specific verified phone it named — a strong natural guard with no time pressure behind it). A bare link changes this: mere possession of the URL is now sufficient to view (though not yet accept) the offer, so time-boxing becomes a real security property, not housekeeping. This RFC adds `expiresAt` (set at creation, `createdAt` + a default window). **`architect`'s original recommendation ("days, not minutes," reasoned from real-world delivery delay) sits in real tension with general security practice for URL-embedded secrets, which favors minutes-to-hours specifically because of the leakage vectors named in §7** (referrer headers, access logs, analytics, browser history — all of which stay exposed for the entire expiry window). Neither consideration wins outright: `ux-designer` sets the exact number at spec time, but must weigh both explicitly rather than defaulting to "days" as risk-free — e.g., a window closer to hours, paired with an easy one-tap "reenviar/generar otro enlace" affordance for the OWNER, may resolve the tension better than a long-lived single link. `expired` itself stays a **read-time derivation** (`status = pending AND now > expiresAt`), never a written value — the identical "derived, not stored" discipline D59 already established for `EventAllocation.quantityRemaining`, reused rather than reinvented.

**Single-use, not reusable-until-revoked.** An Invitation represents, in the Product Owner's own words (`decision-log.md` D63), "the right for a person to join a Business with a specific role" — singular. Making it reusable (many people able to accept the same token) would blur it into a public sign-up link, which is a different capability with no product basis yet. Single-use is enforced by construction via the `pending → accepted` compare-and-swap already described in §2 — no separate mechanism needed.

**Forwarded/leaked link — an accepted risk at current pilot scale, named explicitly rather than silently absorbed, the same posture D63 already set for `AuthIdentity` linking Invariant C.** If a SELLER forwards her invite link to someone else, that someone can complete authentication and accept it — Nahui's domain model has no structural way to verify that the person who authenticates is the specific person the OWNER intended, since `targetHint` is deliberately non-canonical (§1). This is a real, named gap, not an oversight: mitigations exist (a post-acceptance soft warning if the authenticated identity's own email doesn't match `targetHint`, requiring the OWNER's own re-confirmation before the write finalizes) but building any of them now, with zero live instances and zero evidence Nahui's actual pilot scale (a handful of merchants) has ever produced this case, would be exactly the kind of pre-building `architecture-principles.md` #5/D26 already argues against. Accepted as-is at current scale, the same posture as D63's own Invariant C acceptance.

### 5. Why RFC 0013, not an amendment to RFC 0012

RFC 0012 is already Accepted and promoted (`decision-log.md` D62) — the RFC folder's own rule (`99-rfc/README.md`) is that historical RFCs are never edited in place, only superseded by a later one, the identical discipline `decision-log.md` already applies to itself throughout (D53 superseding D17, D61 superseding D48/D51/D52). Editing RFC 0012's own text would violate that.

Beyond that procedural point, this genuinely crosses this Foundation's own RFC triggers on their merits, independent of RFC 0012's status: `Invitation`'s **schema changes substantially** (`phone` removed; `token`/`expiresAt`/`targetHint`/`acceptedByUserId` added; its uniqueness constraint changes shape entirely, from `(businessId, phone)` to global `token`). Its **ubiquitous-language definition is redefined**, not merely clarified — "an OWNER's standing offer for a specific phone number" becomes "an OWNER's standing offer addressed to whoever holds a secure token," a real change in what the term means, one of `domain-model.md`'s own named RFC triggers. And, unlike RFC 0012, this RFC **cannot claim zero UX change** (§6) — squarely the same weight class as RFC 0007/0008/0009/0010/0011/0012, not the plain-decision-log-entry class of D33/D36/D54/D55/D58.

### 6. UX-impact confirmation — checked directly, genuinely different UX required

**Checked against `authentication.md`'s actual current text (read in full, not summarized), section by section:**

- **§2.1's device-level check** — the 2026-09-07 sub-check added for Q24/Q25 ("zero `BusinessMembership` anywhere AND a pending Invitation exists → route to §2.2a") becomes unnecessary and should be removed. Invitations are no longer discoverable via an implicit session/phone match at all — only by opening a link. The rest of §2.1 (the ordinary session-resume logic) is untouched.
- **§2.2's four-way branch, case 0** ("fresh OTP confirm + pending Invitation") — superseded entirely; there is no longer a case where confirming an OTP code silently surfaces an unrelated Invitation. Cases 1–3 stay conceptually intact.
- **§2.2a (Invitation-acceptance resolution logic)** — the core shape (re-check status fresh, not a cached value; accept writes atomically; decline touches nothing) carries forward, but keyed by `token` now, not `phone`; step 2 (multi-pending tie-break) and step 6 (decline-memory marker) are both eliminated, per §2 above — genuine simplifications, not oversights if `ux-designer` finds them gone.
- **§3.10–§3.13a wireframes** — the screen *content* (Business name, what a SELLER can do, the single confirming tap, the "ya no disponible" defensive state) is largely reusable, but the **sequencing inverts** (offer-before-authentication, not after), and at least one genuinely new screen is needed: a link-landing/routing state that reads the token from the URL and resolves pending/expired/revoked *before* authentication ever starts, plus whatever state-carrying mechanism threads the token through the chosen authentication method.

**This is real Product Definition/UX Flow Review work, not an Architecture Gap Analysis alone** — the opposite finding from RFC 0012, and stated as plainly. Characterized as an *amendment cycle to an existing designed capability* (the same shape D53/D59/D60 each used to correct a settled mechanism with real new UX), not a from-scratch New-Feature Workflow — the underlying capability (SELLER-onboarding-via-invitation) already exists and is being corrected, not invented.

**`settings.md` §2.7/§3.11–§3.14 ("Tu equipo") also needs real rework, checked directly against its actual text.** §3.12's phone-entry screen explicitly states it "reuses `authentication.md` §3.3's exact mechanism" — that mechanism is phone-specific and no longer fits. The OWNER-side invite-creation flow needs to become: generate a link (always), optionally attach an email `targetHint`, and offer a share mechanism (native share sheet / copy link) for the link-only path. §3.11's pending-row display ("Invitación enviada" for that number) needs new copy since there generally is no number. `settings.md §8` items 11/12 (the standing "cancel pending Invitation" gap) become a natural, low-cost bundle to close alongside this rework, given `revoked` already exists in the status enum — flagged as a good opportunity, not mandated here.

**Second consumer checked, per the discipline RFC 0012 §6 modeled for `settings.md §2.5/§3.3a`:** no other document in `product/02-ux/` reads `Invitation.phone` — grep-confirmed. **Correction (`reviewer`-caught, 2026-09-13):** a third document, `events.md` §3.26 (EVT-M5), also references `Invitation` — an empty-state check for a pending Invitation's mere existence, never `.phone`. Substantively unaffected either way (a `status=pending` existence check is unchanged by phone→token), but named accurately here rather than the original, incorrect "only two documents" claim.

### 7. `knowledge-mentor` consultation — completed 2026-09-13

**Trigger.** This RFC introduces a new interaction-architecture pattern to Nahui — a bearer-token-URL/magic-link mechanism (an unguessable, time-limited, single-use token embedded in a shareable link) — which `architect`'s own consultation-trigger criteria name explicitly as a case warranting external-evidence consultation, not just internal Foundation-consistency checking.

**Tier check, run by `knowledge-mentor` itself:** Project Foundation (`decision-log.md`, `architecture-principles.md`, `domain-model.md`) doesn't address token-based bearer-token-URL security — genuinely new territory, Tier 1 doesn't resolve this. `Knowledge/` (Tier 2) has no web-security/AppSec domain registered — empty, not silently skipped. Resolved at Tier 3.

**Findings (External Sources, individually sourced — see full citations below):**
- **The mechanism is well-founded.** OWASP's Forgot Password Cheat Sheet describes the identical shape — a random, single-use, short-lived, hashed bearer token — as the standard pattern for password-reset and magic-link flows. RFC 0013's design (CAS-based single-use, `expiresAt`, unguessable token as canonical identity) matches this pattern structurally.
- **Entropy/generation:** minimum 128 bits of entropy, CSPRNG-generated, URL-safe encoding (OWASP Forgot Password Cheat Sheet) — confirms §4's preliminary figure.
- **Storage: tokens must be stored hashed, never raw** (OWASP Password Storage Cheat Sheet) — a leaked database must never yield usable tokens. Now a confirmed requirement, not provisional judgment.
- **URL-embedded-secret leakage vectors, all real and none fully eliminable while the token lives in a GET URL:** referrer leakage to third-party resources on the landing page (mitigate: `Referrer-Policy: no-referrer`, consume/redirect the token server-side before any outbound-linked content loads); server access logs capturing full request URLs by default; analytics tools' pageview auto-capture; browser history, client-side, indefinitely. The practical mitigation is minimizing the *exposure window* (short expiry, immediate single-use consumption) and excluding the route from logging/analytics capture — not eliminating the vector, which isn't possible for a GET-URL-embedded secret.
- **Rate limiting:** the token-lookup/verification endpoint should be rate-limited per IP regardless of entropy, to blunt enumeration attempts.

**A real tension surfaced, not present in `architect`'s original draft — corrected here rather than silently carried forward.** §4's "expiry" reasoning recommended an expiry window "on the order of days, not minutes," reasoned from product needs (an Invitation must survive real-world delay before a SELLER checks WhatsApp). General security practice for URL-embedded secrets (the leakage vectors above) favors **minutes-to-hours**, specifically because a longer-lived URL-embedded secret has a longer exposure window across all four leakage vectors. This is a genuine practice-vs-product-need tension, not a Tier 1 Foundation conflict — the exact default number is still `ux-designer`'s call (§8, Business/Product Decisions), but it should be made with this tension named explicitly, not by treating "days" as risk-free the way the original draft implicitly did.

OAuth authorization-code conventions (RFC 6749 — very short, minutes-scale lifetimes) cited as Model Knowledge, reinforcing the same External-Sources pattern, not itself an External Source.

## Key mechanisms (for `domain-model.md`, additions and amendments)

> **Invitation-acceptance invariant (amended, RFC 0013 — supersedes RFC 0012/D62's phone-keyed field-path correction and D56's original text; the guarantee — no SELLER `BusinessMembership` without a consumed `Invitation` — is unchanged, but the resolution mechanism is now structurally different, not merely re-pathed).** The only write path that can create a `SELLER` `BusinessMembership` is: (1) resolving the invited person's `userId` via the existing, unmodified `AuthIdentity` resolution invariant (RFC 0012 §4 — any of its three shapes), reached after she opens a still-`pending`, not-yet-expired `Invitation` by its `token` and chooses to proceed; then (2) a separate, independently idempotency-keyed write, `acceptInvitation(token, userId)`, that atomically creates `BusinessMembership(userId, businessId, role=SELLER, status=active)` and flips `Invitation.status: pending → accepted`, conditioned on `status` still being `pending` at write time (a compare-and-swap, the mechanism that makes the token single-use by construction and guards against two different actors racing the same leaked link — a distinct guarantee from the idempotency key, which guards only against one actor's own retried attempt). See `decision-log.md` D64.

> **`Invitation`'s discoverability mechanism (amended, RFC 0013).** Previously resolvable by `phone` alone, before any Business was in context, at OTP-verification time. Now resolvable by `token` alone, before either a Business or a User is in context, at link-open time — the identical internal-only-entity-test failure (`architecture-principles.md` #4) that already kept `Invitation` a root, satisfied through a different key.

> **`Invitation` expiry (new, RFC 0013 — closes a standing gap: `expired` has existed in `Invitation.status`'s closed set since D56 with no defined trigger).** `expired` is a read-time derivation (`status = pending AND now > expiresAt`), never a written value — the same "derived, not stored" discipline D59 already established for `EventAllocation.quantityRemaining`. `revoked` stays a real, explicitly-written status (unchanged from D56).

## Ubiquitous-language additions/amendments (for `ubiquitous-language.md`'s Identity context section)

> **Invitation** — an OWNER's standing, single-use offer for a specific role (today: `SELLER`, closed set of one value) on her Business, addressed to whoever holds its secure `token` — never to a phone number, email address, or any other communication channel (corrected, RFC 0013 — supersedes RFC 0012 §3's ruling). Carries `businessId`, `token` (a cryptographically random, unguessable value, ≥128 bits of entropy, stored hashed at rest, never raw — the Invitation's real identity, embedded in a shareable link, `knowledge-mentor`-confirmed against OWASP guidance, §7), `role`, `status` (`pending` | `accepted` | `revoked` — closed set; `expired` is a derived read-time state, `status=pending AND now > expiresAt`, never itself written), `expiresAt`, an optional `targetHint` (`{ type: 'email', value }` — an OWNER-entered delivery/addressing aid *only*; never matched against, and never becomes, the accepting `User`'s identity), and `acceptedByUserId` (nullable, set once on acceptance, historical record only — no downstream write depends on it). Unique on `token`, globally — resolvable by token alone, before any Business or User is in context, at link-open time (the same structural test that already promoted `Venue`/`BusinessMembership`/`EventAssignment`/old-`Invitation`, one level generalized). Consumed, not merely referenced, on acceptance — the accepting `User`'s identity is resolved independently, through the ordinary `AuthIdentity` resolution invariant, before the acceptance write ever runs. `decision-log.md` D56, amended RFC 0012/D62, superseded on channel-specificity by RFC 0013 (see `decision-log.md` D64).

> **Disambiguation note (new, RFC 0013):** `Invitation.token` is structurally similar to, but a distinct concept from, `Sale`'s own Claim Token (an opaque, signed artifact a Paid-tier Sale generates for the Loyalty-claim customer-facing flow, D22/D40). Both are unguessable tokens embedded in a shareable artifact, but they belong to different bounded contexts and resolve entirely different things — `Invitation.token` (Identity) resolves a right to join a Business; `Sale`'s Claim Token (Selling/Loyalty-claim) resolves a Customer↔SaleItem link. Never conflate the two in code, copy, or future design. **Separately: "bearer token" (this RFC's own reasoning prose, §1) is unrelated security terminology, not this Foundation's capitalized `Capability` concept** (a Business-level setting like `registrationMode`/`subscriptionTier`, `domain-model.md#business-capabilities`) — the lowercase/jargon usage never appears in promoted schema or UI copy, confined to architectural reasoning only.

## Business/Product Decisions flagged and resolved (Main, on delegated authority, 2026-09-13)

1. **Whether Nahui builds real transactional email delivery for `targetHint`, and when.** Resolved: ship the link/token mechanism as the one required capability now; treat automated email delivery as a separable, optional enhancement for later, per architect's recommendation and the same lesson learned from the WhatsApp Business Sender verification friction (`company/business-decisions.md` Q19) — don't gate a sign-up path on infrastructure that isn't validated as needed yet.
2. **The default `expiresAt` window** — delegated to `ux-designer` to set at spec time, weighing the real tension `knowledge-mentor` surfaced (§4/§7): product need favors days (real-world delivery delay), general security practice for URL-embedded secrets favors minutes-to-hours (leakage-window exposure). No default number fixed here.
3. **Whether a post-acceptance soft warning (authenticated identity's email doesn't match `targetHint`) is worth designing now** — delegated to `ux-designer`, a UX-quality call, not an architecture requirement.
4. **Whether `Invitation.acceptedByUserId` is worth adding** — approved as proposed (a small, low-cost audit-trail field with clear rationale, no required downstream consumer forcing complexity).
5. **Whether `settings.md §8` items 11/12's standing "cancel a pending Invitation" gap gets closed alongside this RFC's own UX rework** — delegated to `ux-designer`/Main sequencing, a natural bundling opportunity, not mandatory.
