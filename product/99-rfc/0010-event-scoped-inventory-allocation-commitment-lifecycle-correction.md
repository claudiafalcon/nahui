# 0010 — Event-scoped inventory allocation: commitment lifecycle correction

Status: Proposed. Corrects `product/99-rfc/0009-event-scoped-inventory-allocation.md` §3(b) specifically — the manual/quantity-mode allocation mechanism, and only that mechanism. Every other part of RFC 0009 (§1 `EventAllocation` as a new Selling-context aggregate root; §2 `AllocationMovement` as an internal-only ledger entity and its `counterpartEventAllocationId` correction; §3(a) NFC allocation-time exclusivity via `InventoryUnit`'s existing `available→reserved` conditional write; §4 the single-local-transaction reallocation mechanism; §5 `Session.eventId` resolution; §6 Selling-only bounded-context placement; §7 the sibling-RFC scope boundary; §8 ubiquitous-language additions) remains in force, unmodified, not rewritten here. `decision-log.md` D57 (RFC 0009's promotion record) is likewise unaffected in every respect this RFC doesn't name explicitly.

## The idea

RFC 0009 named two independent mechanisms enforcing the physical-location-exclusivity invariant: (a) NFC allocation-time exclusivity, a real conditional write flipping the specific scanned `InventoryUnit` from `available` to `reserved`; (b) manual/quantity-mode consumption exclusivity, a compare-and-swap on a disconnected counter, `EventAllocation.quantityRemaining`, that never touches `InventoryUnit.status` at all.

This asymmetry is a confirmed defect in the built Slice 12 prototype code (`product/02c-high-fidelity-prototype/`), not a hypothetical — reproduced by the Product Owner on the deployed prototype, not merely traced in the abstract. A merchant reserved 10 units for a future Event; the same-day Quick Sale sold into that reserved stock, because Quick Sale's FIFO logic reads `InventoryUnit.status = available` and had no reason to know a counter elsewhere claimed 10 of those units were spoken for. The counter only protects the one write path that explicitly checks it — it never actually removes committed units from the shared pool every other consumption path reads from. (This prototype is deliberately pre-backend per D41–D43 and `product/02c-high-fidelity-prototype/CLAUDE.md` — RFC 0009 itself names the real compare-and-swap as a Stage 7/Backend Integration requirement. The defect is real and confirmed at the prototype-code layer; this RFC's correction targets that same layer, not a claim about a live backend system that doesn't yet exist.)

The correction generalizes mechanism (a) to manual mode instead of leaving (b) as a counter: manual/quantity-mode commitment becomes a real, row-level `InventoryUnit` status flip, the same class of write NFC allocation already performs. This closes the exact class of bug the confirmed prototype defect exposed, and it does so without touching RFC 0009's aggregate boundary, bounded-context placement, or reallocation-transaction mechanism — none of which caused or need to change to fix this.

This RFC also separates soft planning intent from hard commitment (`quantityPlanned` vs. `commitAllocation()`), corrects the Event-close release behavior RFC 0009's original draft got wrong for NFC-tagged stock specifically, and states a standing modeling invariant (logical vs. physical identity) that the correction depends on but that outlives this RFC's own mechanics.

Gains a new operation, `commitAllocation()`.
  - **`AllocationMovement` schema (`domain-model.md`'s "Not aggregate roots" entry)** — `unitIds` becomes populated on every row, not only NFC-mode rows. Gains a new field, `unitSource: scan | fifo_assignment`.
  - **`NFCTag`** — gains a new field, `assignedAt` (`ubiquitous-language.md`'s NFCTag entry and `domain-model.md`'s entity-relationships diagram annotation both need this addition; `domain-model.md` carries no separate NFCTag schema block today to diff against beyond that annotation).

## Why

### 1. Root cause, restated precisely: a disconnected counter, not a row-level reservation

RFC 0009 §3(b) reads `EventAllocation.quantityRemaining` as "the actual selling gate," decremented via `UPDATE EventAllocation SET quantityRemaining = quantityRemaining - 1 WHERE id=? AND quantityRemaining > 0`. This write is a genuine, correct compare-and-swap — on the wrong object. It gates future reads of `quantityRemaining` itself, but it never writes `InventoryUnit.status`, so every other consumption path (Quick Sale's FIFO, another Event's own manual commitment) that reads `InventoryUnit.status = available` directly sees ten fully "available" units the counter alone believes are spoken for. A counter only protects paths that explicitly check it; it was never capable of removing committed units from the shared pool other paths read from. This is the confirmed, reproduced failure mode this RFC exists to close, not a hypothetical hardening pass.

### 2. `quantityPlanned` (new field) vs. hard commitment — `commitAllocation()`

`EventAllocation` gains `quantityPlanned` (integer, optional, default `0`) — soft intent, freely settable or adjustable at any time, with zero effect on the shared `InventoryUnit` pool. An Owner planning six months ahead for a future Event can state "I expect to bring 20 Hoodies" without locking a single physical unit — nothing about that number touches `InventoryUnit.status`, and it participates in no read-time gate, no FIFO exclusion, no compare-and-swap. It exists purely so the Owner can record and revise intent before committing.

Actual hard commitment is a new operation, `commitAllocation(eventAllocationId, quantity)`. It performs a FIFO-ordered conditional flip of `N` `InventoryUnit` rows matching `available AND untagged` (i.e., `status='available' AND tagId IS NULL`, ordered by the owning Lot's receipt date — the same FIFO ordering D5 already establishes) to `reserved`, inside one local transaction that also appends the specific flipped unit IDs to `EventAllocation.allocatedUnitIds`, increments `quantityAllocated` by the actual number flipped (which may be less than `N` if available stock is insufficient — the same partial-fulfillment shape ordinary FIFO consumption already tolerates), and writes one `AllocationMovement` row (`unitSource = fifo_assignment`, `unitIds` = the flipped set). The `untagged` filter is deliberate, not incidental: it keeps manual/FIFO commitment out of the pool NFC allocation earmarks for scan-based consumption specifically — RFC 0009 §3(a)'s own "the tagged/allocated units are earmarked for scan-based consumption specifically, the untagged units remain FIFO-eligible" reasoning, reused unmodified, now also protecting `commitAllocation()`'s own pool from double-claiming a tagged unit.

This is a direct generalization of mechanism (a), not a parallel new mechanism. RFC 0009 §3(a) already established the pattern (a conditional `available→reserved` write, zero-rows-affected meaning "already sold, mid-Sale, or allocated elsewhere," no new field or status value on `InventoryUnit`, Inventory's own schema staying completely unaware of *why* a unit is `reserved`); `commitAllocation()` is that identical pattern with a new caller and a FIFO `LIMIT N` instead of a single scanned ID.

### 3. Retiring `quantityRemaining` as a stored field

`quantityRemaining` stops being written at all. It becomes a read-time derivation: the count of `EventAllocation.allocatedUnitIds` entries whose referenced `InventoryUnit.status` is still `reserved`. This closes the exact class of bug the confirmed prototype defect exposed — a cached counter that can drift from the real committed set, because nothing forces it to stay in sync with the row-level truth once more than one write path exists. Once `allocatedUnitIds` is the one real committed set (§4, below) and every unit in it is `reserved` for exactly as long as it's genuinely held, `quantityRemaining` is always correct by construction — there is no longer a second, independently-writable number that can disagree with reality.

This also simplifies what "the selling gate" means: it is no longer a number checked by a bespoke compare-and-swap at all. The gate is the ordinary `available`-status filter every consumption path (FIFO, NFC scan) already applies — the same filter mechanism (a) always used. `commitAllocation()`'s job is entirely upstream of that: making sure committed units genuinely stop being `available` the moment they're committed, so the existing filter does the rest correctly, for every consumer, not just the one that remembers to check a counter.

### 4. Extending `allocatedUnitIds` to both modes

Today only the NFC path populates real unit IDs into `allocatedUnitIds`; manual/FIFO commitment must populate the identical array with the specific units `commitAllocation()` flipped. This is what makes §3's derivation well-defined and what makes both modes share one real, row-level committed set per `EventAllocation` — not two structurally different bookkeeping mechanisms wearing the same aggregate. Two modes composing on the same Product row (RFC 0009's own "the two compose on the same Product row, never a forced choice," `ubiquitous-language.md`'s existing `EventAllocation` entry) now also means they compose on the same underlying array of real committed units, not a shared row alongside an independent, disconnected counter.

### 5. `NFCTag.assignedAt`

A new field on `NFCTag`, recording when a tag's physical attachment window to its `InventoryUnit` began. `ubiquitous-language.md`'s current NFCTag definition ("a physical tag's UID, attached 1:1 to an InventoryUnit... Consumable — it leaves with the customer after the sale") carries no timestamp today; this RFC adds the one this correction's own invariant (§6, below) depends on. In the currently-Approved UX, tags are consumable and not detached/reassigned — `assignedAt` is written once, at the scan that attaches the tag, and stays fixed for that tag's lifetime under this RFC's own scope. The field is stated generally (through "detachment or reassignment") because it names a standing invariant, not a mechanism scoped only to what's built today; no detachment/reassignment write path is introduced or assumed built by this RFC.

### 6. `AllocationMovement` correction — `unitIds` unconditional, `unitSource` added

RFC 0009 §2's schema carries `unitIds` only for "NFC-mode movements," `null` for quantity-based ones. Since §4 above makes both modes populate real unit IDs, every `AllocationMovement` row must always carry the specific `unitIds` it affected — a manual/FIFO `commitAllocation()` write is no longer a quantity delta with no row-level trace; it's the same kind of discrete, unit-identified action an NFC scan already produces. `quantityDelta` is retained as a convenience/audit figure (its sign and magnitude derivable from `unitIds.length` and the movement `type`), not removed, but it stops being the only record of what a manual-mode movement actually did.

A new field, `unitSource: scan | fifo_assignment` (closed set), records how each specific unit entered `allocatedUnitIds` via that movement. This is the field the Event-close release logic (§8, below) filters on. Without it, a single `EventAllocation` row that has accumulated both scanned and FIFO-assigned units into one shared `allocatedUnitIds` array (exactly the outcome §4 intentionally produces) has no way to release only the FIFO-assigned portion — `EventAllocation` itself carries no per-unit provenance, only the flat array; `AllocationMovement`'s own ledger, one row per discrete write action (RFC 0009 §2's own "written unconditionally, one row per discrete write action" discipline, unmodified), is where that provenance actually lives. Since each unit enters a given `EventAllocation`'s `allocatedUnitIds` via exactly one originating movement (the `initial_allocation`/`replenish`/`reallocate_in` write that added it), the close-time release logic resolves a unit's `unitSource` by looking up its originating `AllocationMovement` row — a join against the ledger, not a new field on `EventAllocation` or on `InventoryUnit` itself. This keeps `InventoryUnit`'s schema exactly as untouched as RFC 0009 §3(a) already insisted on ("Inventory's own schema stays completely unaware of *why* a unit is `reserved`") — provenance is Selling-internal ledger data, never leaked onto the Inventory-owned row.

### 7. Logical vs. physical identity invariant

Every `InventoryUnit` has logical identity unconditionally, from the moment it's received — this is already true today (the `Lot → InventoryEntry → InventoryUnit` traceability chain, `domain-model.md`'s existing "Key point"), not a new mechanism this RFC introduces. Verified *physical* identity — the system's ability to say with certainty "this exact physical garment was in the merchant's hand at this moment" — exists only during an `NFCTag`'s attachment window: from `assignedAt` (§5, above) through whenever that tag is later detached or reassigned, if ever.

This is stated here as a standing modeling invariant, not merely a fact this RFC's own mechanics happen to rely on. Any movement or allocation that occurred *before* a unit was tagged must never be presented, to the merchant or to any downstream reasoning, as physically verified — a unit's logical existence in inventory is never sufficient grounds to claim the system knows where it physically is. This is precisely what makes §8's split release behavior, below, correct rather than arbitrary: a FIFO-assigned (untagged) unit never carried a physical claim in the first place, so releasing it asserts nothing false; a scanned (tagged) unit did carry one, so releasing it without the merchant's own confirmation would assert something the system cannot actually verify has become true again.

### 8. Event close: split release behavior by commitment mode, not uniform

**This section is contingent on Open Item 4, below, not yet settled.** The already-Approved `events.md` §3.16 architecture states, unconditionally, "no silent auto-return to general inventory on Event close" — the Product Owner's own "must never happen silently" instinct, applied without a manual/NFC distinction. The design below introduces exactly a silent auto-release for manual/`fifo_assignment`-sourced allocations specifically. That's architecturally sound (see "Why," below) and closes a real correctness gap, but it's also a product-behavior change from what's currently Approved — not something this RFC can settle unilaterally by drafting it with confidence. Treat this section as the recommended design pending that confirmation, the same posture RFC 0011 §0 uses for its own reopened decision, not as already-settled the way §1–§7 are.

Uniform auto-release for all committed inventory at Event close was considered and rejected. It was reconciled against `knowledge-mentor` evidence and against `events.md` §3.16/§3.25's own already-Approved design, and found to reintroduce, for NFC-tagged stock specifically, the exact physical-location risk this whole mechanism exists to prevent — see "Why," below. The correction splits release behavior by `unitSource` (see `AllocationMovement` correction, §6, above), not by `EventAllocation` as a whole:

**Manual/untagged entries (`unitSource = fifo_assignment`) — auto-release, same transaction as the close write.** At the moment `Event.status` transitions `active → closed` (automatic, date-driven, unchanged), the same commit flips every remaining `fifo_assignment`-sourced unit in that Event's open `EventAllocation`s from `reserved` back to `available`, and sets `status = reconciled` once none remain. No merchant action, no persistent reconciliation-section row for these entries. Safe because no physical claim was ever attached to a FIFO-assigned unit — nothing verified where it is, so nothing false is asserted by releasing it.

**NFC-tagged entries (`unitSource = scan`) — unchanged, explicit tap required, exactly as `events.md` §3.25 already specifies today.** The Event's `active → closed` transition does not touch these rows. They remain `reserved`, the `EventAllocation` stays `open` if any remain, and `events.md`'s existing persistent reconciliation section keeps rendering for them until the merchant explicitly taps "Regresar a inventario general" or "Mover a otro evento" — the same single-tap, no-confirmation, no-re-scan mechanism already Approved, unmodified by this RFC.

**Why the split, not uniform auto-release.** A scanned unit carries a verified physical claim — the merchant had it in hand at allocation time. Nothing about an Event's calendar window closing verifies she's since returned it to general circulation; she may be carrying it straight to her next Event. Auto-releasing it to `available` would make it immediately eligible for FIFO consumption in manual/buttons mode at an unrelated location, risking exactly the double-commitment / wrong-physical-location failure `EventAllocation` exists to prevent — caused this time by the release write itself, not the original counter gap. A FIFO-assigned unit carries no such claim, so releasing it asserts nothing false. Retaining the explicit tap for the NFC case is also not a new architectural safeguard invented here — it's `events.md` §3.16/§3.25's own already-Approved behavior, driven by the Product Owner's explicit "must never happen silently" requirement; uniform auto-release would have silently overridden that decision rather than correcting a domain-model gap, which is not this RFC's authority.

**Mechanism, not scope, changed.** The single-transaction, same-commit-as-the-close-write shape is unchanged from the original draft. What changed is the trigger condition: it now filters by `unitSource` within a shared `allocatedUnitIds` array rather than firing uniformly across the whole `EventAllocation` row.

### 9. Row-level reservation over counter-based CAS — the standing lesson

Flipping actual shared `InventoryUnit` rows is strictly more correct under concurrent multi-path consumption than a counter guard, because a counter only protects paths that explicitly check it — every other path that reads the same underlying resource by a different route stays completely unaware the counter exists. This is not a hypothetical tradeoff argued in the abstract: it is the exact, concrete mechanism the confirmed prototype defect proved. `EventAllocation.quantityRemaining`'s compare-and-swap was itself internally correct — the write genuinely couldn't go below zero — but it protected only the one call site written to check it; Quick Sale's FIFO logic, reading `InventoryUnit.status` directly, had no path through which that protection could ever reach it. A row-level flip has no such blind spot, because every consumer of that resource already reads the same field the flip writes — there is no second, parallel channel for the guarantee to fail to reach. This RFC's correction (§2, generalizing mechanism (a) to manual mode) is the applied form of this lesson; this section states it as the general principle, not scoped to `EventAllocation` alone, for future aggregate-boundary or concurrency-guard decisions to weigh against a counter-based shortcut before choosing one.

### 10. Slice A / Slice B implementation split

**Slice A** — the pure correctness fix: the schema changes above (§2–§7), the FIFO/reservation rewrite (`commitAllocation()`), the symmetric decrease operation (§11, below), and the split release logic (§8). Zero new screens, zero new merchant-facing UX. This is the fix for the confirmed prototype defect specifically, and nothing more.

**Slice B** — the fuller planned/committed two-state UX: surfacing the `quantityPlanned` vs. hard-committed distinction (§2, above) to the merchant visually, so an Owner can actually see and act on the difference between "I'm planning to bring 20" and "12 are actually locked." This needs `ux-designer` first — out of scope for this RFC's own implementation, named here as the next step, not designed here.

### 11. The symmetric decrease operation — `releaseAllocation()`

§2 specified `commitAllocation()` for the increase path but left the decrease path unaddressed. This is a real gap, not a deferred nicety: `events.md` §3.21's already-Approved stepper is bidirectional (floor 0, ceiling "Disponible en general"), and its own copy states plainly, "Lo que no asignes se queda disponible para tus otros eventos." Under §3's correction, `quantityRemaining` is a pure derivation from real `reserved` units — so a "Guardar cambios" commit that lowers the staged manual quantity has no defined write to actually free the corresponding units. Left unaddressed, decreasing an allocation would leave those units silently stuck `reserved`, reproducing — via the one write path this RFC didn't yet touch — the exact class of phantom-commitment defect §1 exists to close.

**`releaseAllocation(eventAllocationId, quantity)`.** Candidate units are drawn only from `EventAllocation.allocatedUnitIds` entries whose `InventoryUnit.status` is currently `reserved` **and** whose originating `AllocationMovement` (resolved via the same per-unit ledger lookup §6 established) carries `unitSource = fifo_assignment`. Scan-sourced units are categorically excluded from this operation's candidate pool — not conditionally filtered, never reachable by it at all. This is the same split §8 already applies at Event close, for the same reason stated in §7's logical/physical identity invariant: a `scan`-sourced unit carries a verified physical claim the system cannot re-assert was relinquished without the merchant's own explicit tap; only the existing, unmodified `events.md` §3.25 "Regresar a inventario general" / "Mover a otro evento" mechanism may release one. A manual quantity-decrease via the stepper must never touch an NFC-tagged commitment — the same boundary `commitAllocation()`'s own `untagged` filter draws on the way in, drawn here on the way out.

**Ordering: most-recently-committed-first, not commit's own FIFO-forward order.** `commitAllocation()`'s oldest-Lot-first ordering exists to serve D5's fairness/aging concern over the *shared, cross-Event* pool of `available` stock — it answers "which units should this claim take from everyone else's pool." Release answers a different question: "which of *this EventAllocation's own* already-committed units should re-enter that pool." No aging-fairness concern applies there — a released unit's own Lot-receipt-date travels with it regardless of release order, so D5's ordinary FIFO still governs its next consumption correctly no matter which specific unit is chosen. Applying commit's FIFO-forward rule to release by blind symmetry would arbitrarily release the *oldest*-standing commitment first — the one Ana is least likely to be mentally revising — instead of undoing the most recent staged change, which is what "Guardar cambios" on a lowered stepper value actually represents to her. It is also the cheaper, more directly correct implementation: it requires only this `EventAllocation`'s own `AllocationMovement` ledger, filtered `unitSource = fifo_assignment`, ordered by `createdAt` descending (ties broken by a stable secondary key), popping `unitIds` until `quantity` is satisfied — no join against `Lot`/`InventoryEntry` receipt dates at all, unlike commit's own selection.

**Write mechanics — the identical shape `commitAllocation()` established, run in reverse.** For each selected candidate, in the order above: `UPDATE InventoryUnit SET status='available' WHERE id=? AND status='reserved'` — a conditional write, zero-rows-affected meaning the unit already left `reserved` by some other path (sold, or released concurrently), tolerated the same way commit tolerates insufficient stock. All of this happens inside one local transaction. `EventAllocation.allocatedUnitIds` is **not pruned** — the array remains the cumulative record of every unit ever committed, exactly as `commitAllocation()`'s own append-only behavior already implies and exactly what makes `quantityRemaining`'s derivation need a live-status check ("entries whose referenced unit is *still* reserved") rather than a bare array length. `EventAllocation.quantityAllocated` is likewise unchanged — it is documented as monotonic, a hard-committed lifetime total, not a live count. The transaction writes exactly one `AllocationMovement` row: `type = adjustment`, `unitIds` = the actual released set (may be fewer than the requested `quantity` under the same partial-fulfillment tolerance commit already has), `unitSource = fifo_assignment`, `quantityDelta` = the negative count (retained convenience/audit figure per §6), `counterpartEventAllocationId = null`. `EventAllocation.status` is untouched by this operation — it stays `open`.

**`adjustment` already fits; no new `AllocationMovement.type` value is needed.** `events.md` §3.21's own already-Approved copy states that a "Guardar cambios" commit resolves invisibly to one of exactly three movement types: `initial_allocation` (first-ever nonzero commit), `replenish` (an increase on top of an already-nonzero commitment), or `adjustment`. By elimination, `adjustment` is already the type this Approved UX text reserves for the one remaining case a stepper commit can produce — a decrease. This RFC's `unitSource = fifo_assignment` tag on that row (§6) is the only new information `releaseAllocation()` requires; the type vocabulary itself needs no schema change.

**Naming.** `releaseAllocation()`, not `returnAllocation()` or a generalized reuse of `return_to_general`'s own verb — deliberately, to avoid conflating this ordinary, in-life stepper decrease (Ana's own routine "I'm bringing less than I staged" edit, mid-planning or mid-selling) with `return_to_general`'s distinct semantics: an explicit, Event-closed-specific reconciliation action with its own trigger, its own screen (`events.md` §3.25), and its own movement type already reserved for that purpose. The two are symmetric in mechanism (both flip `reserved→available`) but distinct in when and why they fire; reusing one name for both would blur that distinction the same way the original counter conflated two structurally different guards.

## Key mechanisms (for `domain-model.md`'s Key Mechanisms, once promoted)

> **Physical-location-exclusivity invariant (amended).** A unit of stock can only ever be committed to one open Event at a time. Both enforcing mechanisms are now the same shape: (a) NFC allocation-time exclusivity (unchanged from RFC 0009 §3(a)) — a conditional `available→reserved` write on the scanned unit. (b) Manual/quantity-mode commitment (corrected) — `commitAllocation()` performs the identical class of conditional write, FIFO-ordered across `N` `available AND untagged` units, inside one transaction that also updates `EventAllocation.allocatedUnitIds`/`quantityAllocated` and appends one `AllocationMovement` row (`unitSource = fifo_assignment`); the symmetric decrease, `releaseAllocation()`, reverses only `fifo_assignment`-sourced units, most-recently-committed-first. `EventAllocation.quantityRemaining` is no longer written — it is derived at read time as the count of `allocatedUnitIds` entries whose unit is still `reserved`. Reconciliation reverses either mechanism the same way (`reserved → available`), governed now by the split release logic below rather than uniformly. See `decision-log.md` (this RFC's eventual promotion entry).

> **Logical vs. physical identity.** Every `InventoryUnit` carries logical identity unconditionally from receipt. Verified physical identity exists only during an `NFCTag`'s attachment window (`assignedAt` through detachment/reassignment, if any). No movement or allocation predating tagging may be presented as physically verified. Standing invariant, not scoped to this RFC's own mechanics. See `decision-log.md` (this RFC's eventual promotion entry).

> **Event close: allocation release (new, corrected).** At `Event.status`'s automatic `active → closed` transition, every `fifo_assignment`-sourced unit still held by that Event's open `EventAllocation`s auto-releases to `available` in the same commit, with `EventAllocation.status` set `reconciled` once none remain — no merchant action. `scan`-sourced units are untouched by the close transition; they remain `reserved`, the `EventAllocation` stays `open`, and `events.md` §3.16/§3.25's existing persistent reconciliation section keeps rendering until the merchant explicitly resolves them (unchanged from RFC 0009/Approved UX). See `decision-log.md` (this RFC's eventual promotion entry).
