# Decision Log

Chronological. Each entry: the decision, why it was made, and what it superseded if anything. Don't edit past entries when a decision changes later — add a new entry that supersedes it, so the reasoning trail stays intact.

## D1 — Registration mode is a Business capability, not a selling-screen choice
The original validation prototype (`product/01-validation/registro.html`) exposed Buttons/NFC as a tab the seller switches live while selling. This was correct for validating registration *speed* (the actual hypothesis under test) but is wrong as a permanent interaction model. `registrationMode` now lives on Business, resolved once at Session start. The selling screen never asks.

## D2 — Product is independent of Lot
Initial framing treated a Lot as if it were tied to a single product ("a Pajama Lot arrived"). Corrected: a Lot is a receiving event that can contain many different Products. Products persist in the Catalog independent of stock, so a sold-out Product doesn't disappear — she'll likely restock it.

## D3 — Full traceability requires unit-level inventory, not batch-level
Initial domain pass modeled Lot → InventoryEntry (a line-item: Product + quantity + cost). This was insufficient: the requirement is that every physical unit's originating Lot is always knowable, even when two Lots of the same Product have different costs. Resolved by generating individual InventoryUnit records from each InventoryEntry — the merchant still just types a quantity, the platform expands it.

## D4 — NFCTag attaches to InventoryUnit, not Product
Originally assumed tags were durable, reusable, and assigned per Product type (matching the validation prototype's flat `uid → producto` map). Corrected: each physical unit gets its own tag at receiving time, so a scan identifies the exact unit (and therefore exact Lot) sold.

## D5 — Buttons-mode inventory allocation defaults to FIFO by Lot receipt date
NFC mode gets unit-level precision for free (the scan says which unit). Buttons mode has no physical identifier, so the system must decide which InventoryUnit a tap consumes. Default: oldest available unit first, fully automatic. Directly follows the principle "every repeated decision should become automation" — this is not a decision the merchant should ever be asked to make.

## D6 — Session does not require an Event
Selling must never require scheduling first — it would add a step in front of the exact friction point (registration speed) already validated as the top priority (`company/backlog.md` #1). Session carries an optional `eventId`; "Iniciar Sesión Rápida" always works with zero setup.

## D7 — Sale is its own aggregate root, not nested inside Session
Considered nesting Sale inside Session's aggregate boundary. Rejected: the <3s speed requirement means Sale writes need to be independent and cheap to append, not mediated through a shared Session-level lock.

## D8 — Bazaar renamed to Event; Event is a light root, not a strict parent of Session
Generalizes beyond bazaars (Expo, Pop-up, Festival, Market, Office Sale) without a schema change later. Event does not own Session as a strict aggregate — "analyze the Event as a whole" is a read-side query across Sessions sharing an `eventId`, not a write-consistency requirement, per DDD guidance to keep aggregates small.

## D9 — Supplier and purchase cost included in schema from v1, deliberately unused
The one sanctioned exception to "build only what's validated." Avoids a future migration once margin analysis / Open Finance features are prioritized. Must stay structurally present and completely invisible (no menu, no screen) until backlog calls for it — see `architecture-principles.md` #5.

## D10 — Loyalty-claim is an independent future module, customer-facing, zero merchant IA presence
The person scanning a sold tag post-sale is the customer, on their own device — not Ana. Modeled as a separate bounded context that only reads `InventoryUnit.status` (must be `sold`) and writes a Customer↔SaleItem link. The dual-purpose tag scan (sale-time vs. claim-time) is disambiguated entirely by `InventoryUnit.status`, so no explicit mode/intent has to be asked of anyone. This is also what guarantees a customer scan can never overwrite or create a Sale — the merchant's finalized Sale remains the sole source of truth structurally, not just by convention. **Wording refined — see D21**: this entry's "zero merchant IA presence" phrasing was later found to be imprecise and was clarified, not reversed.

## D11 — NFC tags are consumable; reframed as a recurring investment, not a one-time kit
`company/CLAUDE.md` originally noted the NFC kit as "likely bundled once, not recurring." That's now superseded: tags are attached per InventoryUnit and leave with the customer permanently (they become part of the loyalty journey, D10). This makes them a recurring consumable — the starter kit is a one-time onboarding item, but merchants buy additional tag packs as they keep selling. This is a business-model decision, not an architectural one; the domain model (D4) already supports either resolution. `company/CLAUDE.md` was updated to match. Positioning: an investment that unlocks customer relationships and analytics, not a recurring cost/burden.

## D32 — No canonical-journey artifact; the recurring cross-journey leak is a Medium-Fidelity node-classification gap, not a missing design layer
A fresh, real observation (the Product Owner walked "Empezar gratis" again after D31's remediation round and still reached the NFC experience) raised whether `product/02-ux/`'s experience-organized specs (as opposed to journey-organized ones) structurally permit journey leakage, and whether a canonical-journey artifact is missing. `architect` determined the Foundation/IA question and the artifact-structure question have different owners: `information-architecture.md` is sufficient as-is (precedent: D28 already established IA's journey descriptions are deliberately loose, not exhaustive contracts — the real per-branch commitment lives in each `02-ux` doc), while whether a first-class journey artifact should exist is `ux-designer`'s/`ui-designer`'s call, not architect's. Both independently verified rather than ratified: `ux-designer` traced every cited incident (the Guardar-mercancía hijack, Findings 8/9/10, JOURNEY2-MAJ1) to Figma-layer node reuse against specs that were already unambiguous at the screen-state level — confirmed directly by finding `inventory.md`'s own §2/§4 already branching the exact shared state that caused the hijack, unprompted. `ui-designer` tested and confirmed the underlying mechanism via direct screenshot comparison: in the clearest incidents, the shared node's *content* was genuinely identical across journeys and only its *navigation* needed to diverge — with one incident (Finding 9) showing a second, distinct risk: a correctly-triggered content clone can still use the wrong template for its specific context. A `knowledge-mentor` consultation on whether Figma's more "elegant" caller-owned mechanisms (per-instance interaction overrides, Variables-based conditional routing) should replace cloning found both carry a real, documented silent-failure mode reproducing the exact bug class (state-dependent overrides, per-journey variable-setup discipline) — cloning has no equivalent runtime precondition, confirming it as the correct mechanism for this tool specifically, not merely the expedient one.
**Resolution:** no canonical-journey artifact, no further `product/02-ux/CLAUDE.md` §4 extension — neither is supported by the evidence, and both were explicitly evaluated and rejected rather than assumed unnecessary. `.claude/agents/ui-designer.md`'s existing caller-audit rule (D31) is sharpened: node-reuse classification (content-identical? navigation-identical?) now triggers at the moment a node is first identified as needing a second journey/caller, not only reactively before a rewrite — closing the gap that let a node explicitly self-labeled "Journey 1: buttons-only" still get silently reused. Does not reopen D31 or D28; sharpens the rule D31 already produced.

## D31 — Wiring originates in the Low-Fidelity spec; wireflows are not a separate pipeline stage
A recurring class of Figma wiring bugs (a shared node silently reused across an incompatible journey, a destination never verified before being trusted) raised the question of whether navigation/screen-transition wiring should be authored earlier in the design process — as its own upstream "wireflow" artifact — rather than resolved during Medium-Fidelity/Figma work. `architect` determined this wasn't a Foundation/domain-model question and routed it to `ux-designer`/`ui-designer`, each independently grounded via a `knowledge-mentor` consultation against curated UX/UI industry material (`Knowledge/UX-UI/`) plus external sources (NN/Group, Figma's own documentation). Resolved: naming (which destination each branch, error, and interruption resolves to) belongs at Low-Fidelity and is now an enforced rule (`product/02-ux/CLAUDE.md` §4), not an unwritten convention. Wiring (making a transition clickable, resolving Figma's one-destination-per-reaction constraint, cloning shared nodes for diverging journeys) is conventionally, and correctly, resolved at Medium-Fidelity — no established UX/UI practice treats this as upstream work, and the specific bugs found were not preventable by moving it earlier, since the constraint being violated doesn't exist as a concept until a prototyping tool is involved. `ui-designer` gained a companion process rule (a caller/destination audit before rewiring any shared node). No aggregate, bounded context, or ubiquitous-language term is affected — this is a pipeline-organization decision, same class as D24, not a domain-model change.

## D30 — Client-initiated retries must be idempotent/keyed; new `architecture-principles.md` #7

Surfaced during the same Architect build-readiness review as D29, ahead of the Product Validation Sprint. Every "Reintentar" action documented across the Approved `02-ux` specs (`home.md` §3.8a/§3.8d/§3.14's Sale-finalization and tap-to-add retries, `inventory.md`'s receiving-save retry, `settings.md`'s capability-save retry, and their equivalents elsewhere) promises the merchant no data loss on retry — but nothing in `architecture-principles.md` #1–#6 states what happens in the genuinely ambiguous case: the original write actually succeeded server-side, but the client never received confirmation (a dropped response, not a dropped request), and Ana taps "Reintentar" anyway. Without an explicit rule, a naive retry implementation risks silently producing a second Sale, SaleItem, Lot, Event, or capability-change record for the exact same action she believes she only took once — the opposite of what every one of those specs promises her.

Classified as a plain decision-log entry adding a new architecture principle, not RFC-worthy — it changes no aggregate boundary, adds no bounded-context dependency edge, and redefines no ubiquitous-language term; it states a technical constraint on how writes already described elsewhere in the Foundation (Sale/SaleItem, D7; Lot/InventoryEntry, D2/D3; Event, D8; capability changes, D25) must be implemented — the same category of addition D5's/D10's "how the platform disambiguates" rulings already are, just phrased as a standing principle rather than a per-mechanism ruling since it applies uniformly across every aggregate with a client-facing write.

**Ruling:** every write exposed to a client-initiated retry must be idempotent or keyed, so a genuinely ambiguous network failure (request succeeded, confirmation was lost) can never produce a duplicate record when the merchant retries. Concretely: the client attaches a stable idempotency key to the write attempt, generated once at the moment the action is first taken and reused unchanged on every retry of that same attempt — never regenerated on "Reintentar." The server treats a repeat of an already-seen key as "already done," returning the original result rather than creating a second record. This applies to every write named in a "Reintentar" affordance across the approved specs — Sale finalization, SaleItem registration, Lot/InventoryEntry receiving, Event creation/scheduling, and capability-change writes (`subscriptionTier`/`loyaltyEnabled`/`defaultSellingMode`, D25/D27) alike — not only Sale, even though Sale's <3s speed requirement (`architecture-principles.md` #2) makes it the write most likely to actually be exercised under real network conditions.

**Applied:** new `architecture-principles.md` #7 (see below). No change to `domain-model.md`, any bounded-context table, or `ubiquitous-language.md` — this is a write-mechanism constraint, not a structural one.

## D29 — Two new Business-level "shown once" boolean fields: NFC-availability discoverability nudge, and pending-change-landed acknowledgment

Surfaced during an Architect build-readiness review ahead of the Product Validation Sprint. Two already-Approved specs now depend on persisted once-only-notification semantics `domain-model.md` has no field for: `home.md` §3.6a's fourth Session-start variant (the one-time "Ready, tags now sufficient" discoverability nudge toward `nfc`, closing D27-CROSS-M1 — explicitly "shown once ever, not once per occurrence," §3.6a's own design note) and `settings.md` §2.4 (the one-time landing acknowledgment shown "the first time Configuración's main view is opened after a pending change's effective date has passed"). Both specs state the once-only behavior as settled UX; neither can actually be built as specified without somewhere to persist "has this already been shown."

Classified as a plain decision-log entry, not RFC-worthy — same test as D26/D27: no aggregate boundary changes (both fields attach to the existing Business aggregate, already the sole holder of Business Capabilities and self-service-mutability state per D25), no bounded-context dependency edge is added (see below), and no ubiquitous-language term is redefined or introduced — these are internal-only stored fields, never named or exposed to the merchant, governed by the same discipline `architecture-principles.md` #4 applies to InventoryEntry/InventoryUnit: if either of these ever needed its own screen or menu entry to explain, it would stop being internal-only and this ruling would need revisiting.

**1. `settings.md` §2.4 — `acknowledged` flag, added to `subscriptionTier` and `loyaltyEnabled` only.** Extends the pending-value + effective-date pair D25 already added to these two capabilities (`domain-model.md`'s Business Capabilities table, "Self-service mutability" paragraph) with one more field of the identical shape: `acknowledged: boolean`, default `false`. Set `true` the first time Configuración's main view (`settings.md` §3.3) renders that capability's landing-acknowledgment line after its effective date has passed; never reset by that acknowledgment itself, but reset back to `false` whenever a *new* pending change is set for that capability, so a subsequent landed change gets its own independent acknowledgment rather than inheriting a stale `true`. Not added to `defaultSellingMode` — that field carries no pending-value pair at all (D27: immediate-only, no billing-cycle implication), so there is no "landing" moment for it to acknowledge. Write ownership stays entirely inside Identity: Configuración is the same Identity-owned surface that already writes `subscriptionTier`/`loyaltyEnabled`'s own values and their pending-value pairs (D25) — this is one more field on a write path that already exists, not a new one.

**2. `home.md` §3.6a's fourth variant — `nfcAvailabilityNudgeShown` boolean, a new Business-level field, not a Business Capability.** Deliberately *not* added as a row to the Business Capabilities table — it gates nothing about what the merchant can do (it isn't a capability), it only records whether a one-time informational nudge has already been shown. Added instead as its own short paragraph on the Business aggregate, immediately following the Business Capabilities table (before "Key mechanisms"): `nfcAvailabilityNudgeShown: boolean`, default `false`. Set `true` the first time `home.md` §3.6a's fourth variant ("Ya tienes prendas con tag suficientes...") renders for that Business; never reset — matching §3.6a's own stated discipline, "shown once ever, not once per Session-start occurrence... repeating an FYI about a discretionary choice she may not want to change would itself violate ['never ask twice']" (`global-principles.md`).

**Dependency-edge check, stated explicitly because this one is less obvious than #1 above.** Reading `nfcAvailabilityNudgeShown` to decide whether to render the nudge is no new edge — it's the same Selling→Identity read-only dependency `domain-model.md`'s bounded-context table already grants Home for every other §3.6a variant (reading `defaultSellingMode`, `subscriptionTier`-derived `registrationMode`, per D23/D27). Writing it back to `true` is the part that needs care: this must be modeled as Identity's own self-mutation of its own Business aggregate, dispatched at the moment Home renders that screen — the same precedent D13 already established for Settings itself ("Settings hangs off the session-controls affordance already specified in `home.md` §3.7... capability management gets a surface, not a destination"). Home is the UI surface that triggers the write; Identity remains the sole writer of Business's stored shape. This is not a new Selling-writes-to-Identity dependency edge — it's the identical shape Onboarding (D19) and Settings already use, reached via a different part of the Home UI shell. If a future implementation instead routes this write through Selling/Session-start code directly mutating Business fields, that would be a real new edge and should come back through this log — flagged here so `builder` doesn't default into that shape by accident.

**Applied:** `domain-model.md`'s Business Capabilities table's "Self-service mutability" paragraph gains the `acknowledged` boolean for `subscriptionTier`/`loyaltyEnabled`. A new short paragraph is added directly after the Business Capabilities table (and before "Key mechanisms") documenting `nfcAvailabilityNudgeShown` as a Business-level, non-capability stored field. No change to any aggregate boundary, bounded-context table, or `ubiquitous-language.md`.

**Applied:** `information-architecture.md` Journey 3's wording corrected to "one tap to reach the selling screen in every case," removing the literal-reading ambiguity. Additive/corrective wording fix, same category as D21 — no navigation structure, aggregate, or ubiquitous-language term changes; Information Architecture v1 stays frozen in substance.

## D27 — NFC capability is derived from `subscriptionTier`, not an independently stored/toggled entitlement; welcome tag package is fulfillment-only; `defaultSellingMode` becomes merchant-self-service-editable

Resolves the remaining ambiguity D19/D25 left open about how the NFC entitlement is granted, per the Product Owner's full resolution: **NFC Selling is included in the Paid tier, full stop.** It is not a separately purchasable add-on and the welcome tag package does not grant it — the package is fulfillment logistics only (a box of tags mailed after subscribing), never a capability-granting mechanism. Free tier → `buttons` only. Paid tier → `buttons` and `nfc`. A merchant may use independently purchased compatible tags once on the Paid tier, without waiting for the welcome package to arrive. Classified as a plain decision-log entry, not RFC-worthy: no aggregate boundary changes, no bounded-context dependency edge is added, and no ubiquitous-language term is redefined — this corrects a write-mechanism assumption inside an already-frozen capability and extends existing self-service editability (D25) to one additional field, the same category of change D19 and D25 themselves were.

**1. Supersedes D19's "Activate NFC Starter Kit" framing.** D19 recorded the initial-onboarding path as "confirmation of an already-obtained physical kit (e.g. an activation code)" — correct that it was zero in-app payment, wrong that possessing a kit was ever the thing being confirmed as capability-granting. Corrected mechanism: the welcome tag package is a fulfillment/logistics artifact only. It grants nothing. `nfc` capability is derived entirely from `subscriptionTier = paid`; nothing about tag possession, activation codes, or kit confirmation enters into whether `nfc` is available to a Business. D19's "zero payment processing in the product" guarantee is unaffected and restated here: activating the Paid tier (`settings.md`'s "Activar plan de pago") still confirms a payment arranged outside the app, never processes one in-app.

**2. Clarifies D25 — `registrationMode`'s `nfc` entry is a read-time derivation, not an independently stored/toggled field.** D25 listed `registrationMode`'s `nfc` entitlement as one of three independently self-service-toggleable capabilities, parallel to `subscriptionTier` and `loyaltyEnabled`. That's now wrong: `nfc` has no independent existence to toggle — it only ever changes as a side effect of `subscriptionTier` changing. **Ruling: `registrationMode`'s `nfc` membership becomes a pure read-time derivation, not a stored field** — `nfc ∈ registrationMode ⟺ subscriptionTier = paid`, computed fresh wherever `registrationMode` is read (Inventory's tag-assignment gating, Session-open's NFC Readiness/`defaultSellingMode` resolution per D23), never persisted as its own value. `buttons` remains implicitly always-available and needs no storage either — `registrationMode` as a whole is now entirely derivable from `subscriptionTier` plus the `buttons`-always-included constant, so no part of it needs its own storage slot on Business.

This is the cleaner resolution against `architecture-principles.md`, not the alternative the Product Owner's phrasing also left open (keep it a stored field, written only as a side effect of `subscriptionTier` changes). A stored-but-derived field is a second copy of the same business truth (`subscriptionTier`) that must be kept in permanent lockstep by every writer, forever — exactly the dual-write consistency risk `global-principles.md`'s "capture business truth once, reuse it forever" exists to rule out, and there is no independent history/audit requirement here that would justify paying that cost (contrast `Session.operatingMode`, which *must* persist because it freezes a resolution in time for an already-immutable Session lifecycle — `registrationMode` has no analogous need to freeze anything; it's evaluated fresh every time, exactly like NFC Readiness's own "computed, never-persisted" precedent, D23). Derivation, not storage, is the pattern already established elsewhere in this Foundation for exactly this shape of value.

**Consequence for D25's self-service list:** D25's "fully self-service, bidirectional, at any time" resolution now applies directly to exactly two capabilities — `subscriptionTier` and `loyaltyEnabled`. `registrationMode`'s `nfc` availability still changes bidirectionally and still never deletes historical data (unchanged from D25's invariant — an already-assigned NFCTag stays inert-but-intact on a Paid→Free transition, same as before), but it does so *only* as a consequence of `subscriptionTier` moving, never as its own directly-invoked action. The pending-value/effective-date structure D25 introduced for `nfc` specifically is now redundant and is removed — a pending `nfc` change is nothing but a read of `subscriptionTier`'s own pending-value/effective-date pair; storing a second one would be the identical duplication problem above, one level up. `company/business-decisions.md` Q11's "six directions across three capabilities" framing narrows to four directions across two capabilities (`subscriptionTier`, `loyaltyEnabled`) — `nfc`'s timing is no longer a separate question, it rides `subscriptionTier`'s.

**3. `defaultSellingMode` gains a self-service edit surface — touches `domain-model.md`, not purely a UX-scope change.** `settings.md` §8 item 5 explicitly scoped this out ("D25/Q5 resolve exactly three capabilities; `defaultSellingMode`... this resolution never named"), correctly, at the time. That's now superseded: the Product Owner's resolution explicitly grants it a Settings edit surface, constrained to whichever modes are currently available (i.e., always `buttons`; `nfc` only while `subscriptionTier = paid`). This is a Foundation-level change, not only a UX one — `domain-model.md`'s Business Capabilities table and self-service-mutability paragraph, and `ubiquitous-language.md`'s Default Selling Mode entry, both currently state or imply it's Onboarding-set only (D19/D23) and need updating to record it as self-service-editable thereafter.

Its field description does **not** need any change to its operative meaning: "not itself the operative value for any given Session" (D23) stays exactly true — `Session.operatingMode` is still resolved at Session-open from `defaultSellingMode` plus NFC Readiness (D23), unchanged by who's allowed to edit the fallback or how often. Unlike `subscriptionTier`/`loyaltyEnabled`, this field carries no pending-value/effective-date structure — it isn't a commercial/billing capability, so D25's deferred-timing rationale never applies to it; an edit here takes effect immediately, at the next Session-open, the same way any other read of a Business-level fallback field already behaves. A merchant editing `defaultSellingMode` to `nfc` while `subscriptionTier = free` is simply not offered `nfc` as an option in the first place, per the same "constrained to modes available to her" wording the Product Owner used — no new validation mechanism is needed beyond the derivation in point 2, since Session-open's existing D23 resolution logic already only ever offers `nfc` when it's in the (now-derived) `registrationMode` set.

**4. D23's "Default," not "Preferred," naming stays — the load-bearing half of the original rationale is unaffected.** D23 rejected "Preferred" on two grounds stated together: the field is "an operational fallback the Session may resolve away from," and "not a subjective disposition Ana would need to keep updating." The second clause is now literally false — she may update it repeatedly, in Settings, whenever she likes. The first clause is unaffected and remains the actually load-bearing reason: `defaultSellingMode` still never guarantees a Session's outcome — NFC Readiness can still silently override it (Limited Ready nudge, Not Ready withdrawal, D23), regardless of how often or how deliberately she set the fallback. "Preferred" would misrepresent that relationship whether set once at Onboarding or edited weekly — it implies a value that wins, when the actual architecture is a fallback that can lose to a per-Session readiness check. Keeps the existing name and field (`defaultSellingMode` / "Default Selling Mode") — no rename, no ubiquitous-language redefinition. `domain-model.md`/`ubiquitous-language.md`'s citation of the now-outdated "wouldn't need to keep updating" clause is trimmed to the operational-fallback reasoning alone, since only that half of the original justification still holds — a wording correction, not a term change.

**5. The welcome tag package, going forward.** Fulfillment/logistics only: a package of physical NFC tags shipped to a merchant after she subscribes to the Paid tier. It grants no capability, sets no field, and gates nothing — a Business's `nfc` availability is already `true` the moment `subscriptionTier` flips to `paid`, independent of whether or when the package ships or arrives. It does not appear anywhere in `domain-model.md`'s Business Capabilities table, `ubiquitous-language.md`, or the bounded-context ownership table, and should not — it is a `company/`-level fulfillment/operations concern (mailing logistics), not a domain concept. `company/CLAUDE.md`'s existing "NFC kit" description (a starter set of tags bundled with onboarding, consumable, D11) already frames it this way and needs no change; only `settings.md`/`onboarding.md`'s UX mechanics that currently model the kit as something confirmed via an activation code (`onboarding.md` §3.4–§3.4b, `settings.md` §2.3/§3.8) are now built on the superseded assumption and need a UX remediation pass — routed to `ux-designer`, not performed by this entry.

**Applied:** `domain-model.md`'s Business Capabilities table — `registrationMode` row corrected to describe `nfc` as read-time-derived from `subscriptionTier`, never independently stored; self-service-mutability paragraph narrowed to `subscriptionTier`/`loyaltyEnabled` and extended to note `defaultSellingMode`'s new, differently-shaped (no pending/effective-date) self-service editability. `ubiquitous-language.md`'s Selling Mode Capability and Default Selling Mode entries updated to match. `company/business-decisions.md` Q11 narrowed from six directions/three capabilities to four directions/two capabilities. `company/CLAUDE.md`'s NFC kit description needs no change. `product/02-ux/settings.md` (§2.2's six-action table, §2.3's dedicated NFC-activation path, §3.8/§3.8a/§3.8b, §8 item 5) and `product/02-ux/onboarding.md` (§3.4–§3.4b's activation-code mechanism) both went through a UX remediation pass against this corrected model — see `product/02-ux/CLAUDE.md`'s status log.

## D26 — Sale-level Claim Token (D22) is Stage 2 schema scope, not pre-built dormant like Supplier (D9)

No change to `domain-model.md`'s Sale schema or D22's own target-design description — this entry only resolves a build-sequencing ambiguity D22 left open, the same way D19 resolved a *when-is-this-set* question without touching the capability table it was about.

## D25 — Business Capabilities are fully self-service, bidirectional, at any time — subject to business-rule-governed timing, never deleting historical data
Resolves Q5 (`company/business-decisions.md`) — the last open item from the original Q1–Q10 set, and the one D19/D23 both explicitly left for later ("assumes a Business's capability set can change post-onboarding... without itself deciding the general self-service-editability mechanism"). Classified as a plain decision-log entry, not an RFC — closer to the RFC threshold than D17/D19 (it does add a small stored structure to a frozen aggregate), but it changes no aggregate boundary, adds no bounded-context dependency edge, and redefines no ubiquitous-language term; it completes a gap D19/D23 already named, rather than reopening or contradicting either.

**Resolution (Product Owner):** Merchants may self-service activate *or* deactivate the three named commercial capabilities, at any time: `subscriptionTier` (Free ↔ Paid), `loyaltyEnabled` (Loyalty Enabled ↔ Disabled), and `registrationMode`'s `nfc` entitlement (NFC Enabled ↔ Disabled). Two invariants apply to all three, in both directions:
- **Never delete historical data.** Confirmed already structurally guaranteed by the existing model, not something requiring a new mechanism: every Business Capability in this system is a read-time display/availability gate, never a condition on a write path or a cascade-delete rule (`architecture-principles.md` #6). Disabling `loyaltyEnabled` stops future Claim Tokens and hides segmentation display; it doesn't touch existing Claims (owned entirely by Loyalty-claim, D22). Removing `nfc` from `registrationMode` doesn't affect already-assigned NFCTags or their unit/Lot traceability (D4) — they simply become inert for *future* Sessions, per D23's own already-general wording. Downgrading `subscriptionTier` to `free` reverts Resultados' display choice, not the underlying Sale/Session/Lot/Claim history. This was true before this decision; it had just never been exercised in the deactivate direction until now — stated here explicitly as an invariant, the same discipline D23 applied to its own bounded-context table.
- **Business rules determine *when* the change takes effect — immediate or deferred, not always immediate.** This is the one place this decision adds real structure: for a merchant-facing deferred change (e.g., a Paid→Free downgrade landing at a future point) to ever be honestly displayable in `settings.md`, the fact that a change was requested — target value and effective date — has to live in the domain, not only inside an external scheduler's internal state (`global-principles.md`, "capture business truth once, reuse it forever"). Applied identically to all three: `subscriptionTier`, `loyaltyEnabled`, and `registrationMode`'s `nfc` entitlement each gain an optional pending-value + effective-date pair alongside their current value (the common "change lands at period end" shape). The mechanism that actually flips the field at the right time (a scheduled job, a billing-webhook handler) stays correctly external to the domain model; only the fact that a pending change exists, and when it lands, is domain data.

**What's explicitly not resolved here, and why:** the *specific* per-transition rule (which of the six directions is immediate vs. deferred, and what "deferred" concretely means for each) is a business/pricing-policy question, not a domain-modeling one — and it can't actually be pinned down yet, because it presupposes a billing-cycle concept that doesn't exist anywhere in this Foundation. `company/CLAUDE.md`'s business model direction is explicit that pricing is "not final," and payments/checkout stays a stated non-goal. Treating the Product Owner's own illustrative example ("Paid→Free may become effective at the end of the current billing period") as a settled rule would mean inventing a billing-cycle concept nothing else in the Foundation supports yet. Tracked as its own open item in `company/business-decisions.md`, explicitly dependent on the pricing model being designed — same separation RFC 0002/`company/backlog.md` #2 already established between a Foundation-level vision and its own implementation-sequencing detail.

**Timing interaction with `Session.operatingMode` (D23):** no change needed to D23's existing guarantee. `Session.operatingMode` is resolved once, at Session-open, from whatever `registrationMode`/`defaultSellingMode` currently read *at that instant* — Session-open has no visibility into a pending, not-yet-effective change either way. Once a deferred change's effective date arrives and the field actually flips, this is indistinguishable from any other capability change, already covered by D23's own generalized wording ("that Session finishes normally... the restriction takes effect starting with the next Session only"). `subscriptionTier` and `loyaltyEnabled` never touch `Session.operatingMode` at all — they're per-action gates (Resultados render, Sale-finalization Claim Token generation), not Session-snapshotted — so this question was never in their scope to begin with.

**Applied:** `domain-model.md`'s Business Capabilities table gains the pending-value/effective-date structural note for all three capabilities, and the "never delete historical data" invariant is now stated explicitly rather than true only by omission. `company/business-decisions.md` Q5 moved to Resolved; a new, narrower open item records the still-undetermined per-transition timing table, explicitly blocked on the pricing/billing-cycle model. `settings.md` is now unblocked — six merchant-facing actions (three capabilities × two directions), a reusable "pending change, takes effect on [date]" indicator pattern, and a way to cancel a pending change before it lands, tracked as its own UX design task.

## D23 — Session-scoped selling mode: capability as availability, a Business-level default, and a per-Session inventory-readiness recommendation
Resolves `product/99-rfc/0003-session-selling-mode.md` (Accepted). Raised when the Product Owner paused Q5 (`company/business-decisions.md`) to consider whether a richer model would resolve the underlying question — how selling mode actually gets decided — more cleanly than a direct self-service-editability answer to Q5 alone. `registrationMode` splits from a single Business-wide scalar into three distinct concepts, evaluated jointly by Architect (domain-modeling soundness) and UX Designer (interaction/friction) before any Foundation change was proposed, then refined directly by the Product Owner:

- **Selling Mode Capability** (`registrationMode`, Business-level, Identity context) — now a *set* of available modes, not one active value: `buttons` always included; `nfc` an add-on entitlement. Governs *availability* only, never which mode a given Session actually runs in.
- **Default Selling Mode** (`defaultSellingMode`, Business-level, Identity context) — a new stored field: the Business's normal operating mode, set via Onboarding (D19) and read as the fallback at Session start. Not itself the operative value. Named "Default," not "Preferred," on Architect's confirmation: the field represents an operational fallback the Session may resolve away from, not a subjective disposition Ana would need to keep updating — and creates no collision with the unrelated, lowercase "default" already used in the FIFO-allocation passage below (D5), a different concept in a different context.
- **Session Operating Mode** (`Session.operatingMode`, Session-level, Selling context) — a new stored field, resolved once at Session-open time, immutable for the remainder of that Session's `active` lifecycle. This closes a real, previously-identified gap: Session never used to snapshot which mode it ran under, since historically there was only ever one value to read. Fixed here as a direct consequence of this model, not a separate change.
- **NFC Readiness** — a computed, never-persisted, three-state evaluation run at Session-open time against sellable tagged inventory (`available` `InventoryUnit`s with an assigned `NFCTag`):
  - **Ready** — coverage above the readiness threshold. If `nfc` matches `defaultSellingMode`, the Session opens silently in `nfc` — no UI moment.
  - **Limited Ready** — some tagged inventory exists, but below threshold. `buttons` is recommended via a single lightweight inline nudge; the merchant may override toward `nfc` if her capability set allows it.
  - **Not Ready** — precisely zero sellable tagged inventory units exist. This is not a UX restriction or a stricter recommendation — it is an operational impossibility: `nfc` requires a physical tag to scan, and none exists, so `nfc` is withdrawn from the choice set entirely, overridable or otherwise. `buttons` is always available (it needs no tag), so selling itself is never blocked — only the impossible mode is withheld.

The recommendation is shown **only when it disagrees with `defaultSellingMode`** — the common case (Ready, matching the default) stays fully silent, preserving the substance of `architecture-principles.md` #1 ("capabilities resolved once, upstream, never asked mid-flow") even though the literal mechanism is now a per-Session read rather than a single frozen value. The readiness threshold itself is a configurable product/business rule, not a value hard-coded into the Foundation. If NFC capability is revoked while a Session is already active (e.g., a subscription lapse), that Session finishes normally in whatever mode it already resolved — the restriction applies starting with the next Session only.

Classified as RFC-worthy (not a plain decision-log entry) because it redefines a ubiquitous-language term and adds a new stored field to a frozen aggregate (`Session`) — the same category as D22/RFC 0002, not D17/D19's direct-entry precedent. No new bounded-context dependency edge was required — the readiness computation is answerable entirely from Inventory data Selling already reads (read-only, per the existing `architecture-principles.md` #6 direction).

**Relationship to other open items — deliberately not resolved here:**
- **Q5 (`company/business-decisions.md`) stays open.** This decision assumes a Business's capability set can change post-onboarding (e.g., `nfc` revoked by a subscription lapse) without itself deciding the general self-service-editability mechanism Q5 asks about (can a capability change post-onboarding, and by what mechanism — self-service in-app, or backend/support-mediated). That remains a separate, still-open Business Decision, narrower now than before this RFC only in that the *domain* question ("can the value change at all, without breaking anything") is settled; the *business/mechanism* question is not.
- **Q2 (`product/02-ux/product-decisions.md`) is unaffected, not superseded.** Q2 resolved a different, narrower scenario: an already-open `nfc`-mode Session encountering one specific untagged unit mid-Session (no data-model exception, redirect to Asignar Tags). This decision operates one level up, at Session-*start*, evaluating aggregate tagged-inventory coverage before a Session ever opens — it reduces how often Q2's scenario is reached (a Not Ready Session never even offers `nfc`), but doesn't replace Q2's own resolution for the residual case where overall coverage is fine yet one particular product's units happen to lack tags. Q2's own flagged UX design gap (`home.md` §3.10's redirect affordance) remains a separate, still-undesigned task.

**Applied:** `domain-model.md` (Business Capabilities table, entity-relationships diagram, Key Mechanisms), `architecture-principles.md` #1 (wording refresh), `ubiquitous-language.md` (new terms), `information-architecture.md` (Assign-Tags gate condition), `product/02-ux/home.md` and `product/02-ux/inventory.md` (UX updates per the RFC's scope) — full design pass (`ux-designer` → `ux-critic` → `reviewer`) tracked in `product/02-ux/ux-critic-findings.md`.

## D22 — Customer Segmentation is a core capability; Claim generalizes to multiple resolution mechanisms; Intelligence consumes only Derived Customer Intelligence
Resolves Q8 (`company/business-decisions.md`), after a three-round joint Planner (business-impact) and Architect (domain-implications) analysis. Product Owner chose the complete-capability design (previously "Path (a)") over narrowing Customer Segmentation to something identity-free ("Path (b)"), on the explicit grounds that Customer Segmentation is a core product capability from the start — not an artifact of which `registrationMode` a merchant happens to use.

**The complete target design, described here in full regardless of build order** (see `product/99-rfc/0002-loyalty-claim-complete-capability.md` for the full RFC):
- **Claim is one business capability** (`loyaltyEnabled`), resolvable through multiple mechanisms: the existing NFC tag scan (D4/D10, unit-level — one Claim per scanned tag), a new Sale-level **Claim Token** (Selling-owned, generated at Sale finalization whenever `loyaltyEnabled = true`, independent of `registrationMode`, displayed to the customer as e.g. a QR code so she can start the Loyalty-claim flow on her own device), and future mechanisms following the same pattern. All converge on the identical terminal write: one or more Customer↔SaleItem Claim links. A single Claim Token scan resolves into N independent SaleItem-level Claims for a multi-item Sale — architecturally identical in shape to how a multi-item NFC Sale already produces N independent claims via N separate tag scans (Architect's definitive ruling). No new "Sale-level Claim" concept was introduced — `ubiquitous-language.md`'s Claim definition stays structurally the same, generalized only in how it's triggered.
- **`registrationMode` determines which mechanism a given Sale uses, never whether the capability exists.** Customer Segmentation is gated only by `subscriptionTier=paid` and `loyaltyEnabled=true`.
- **Customer Identity belongs exclusively to the Loyalty platform.** The Merchant Application never performs identification and never reads a raw Customer or Claim record.
- **The Merchant Application consumes only Derived Customer Intelligence** — an anonymized, aggregate signal (e.g., counts of frequent vs. occasional buyers) that Loyalty-claim computes from its Claims and exposes read-only to Intelligence. No name, no contact info, no per-Claim drill-down ever reaches the merchant app.
- **New bounded-context dependency edges** (`domain-model.md`'s table): Loyalty-claim gains a read-only dependency on Selling (to resolve a Sale's SaleItem set for the Claim Token mechanism); Intelligence gains a read-only dependency on Loyalty-claim (Derived Customer Intelligence only). Selling itself gains no new dependency and stays completely unaware either context exists — the Claim Token is a field Selling generates and owns, the same shape NFCTag already has relative to Loyalty-claim (D4).
- **Claim Token security**: must be an opaque, signed reference, never the raw Sale ID — the same "customer scan can never affect a Sale" reasoning from D10 extends to "must not be guessable" for a token that can be scanned by anyone who sees it.

**Routed through `product/99-rfc/0002-loyalty-claim-complete-capability.md`** — this changes the bounded-context dependency graph (two new read edges) and generalizes a ubiquitous-language term (Claim), both explicit RFC triggers, same precedent as D20's Venue RFC.

**Implementation sequencing is explicitly not decided here.** Per the Product Owner's instruction, this entry and the RFC describe the complete target vision only; staged build order (which mechanism ships first) is tracked separately in `company/backlog.md` #2, not in the Foundation.

**Applied**: `reports.md` §3.6/§3.12/§3.13 ("Tus clientes") was redesigned as a real spec against this resolved architecture — gated by `subscriptionTier=paid` and `loyaltyEnabled=true` together, consuming only Derived Customer Intelligence — and went through its own full design pass (`ux-designer` → `ux-critic` → `reviewer`, zero Blockers/unresolved Majors). See `product/02-ux/ux-critic-findings.md`'s "Customer Segmentation (Q8) resolution cycle" entry for the full review record.
