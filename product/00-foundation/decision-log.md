# Decision Log

Chronological. Each entry: the decision, why it was made, and what it superseded if anything. Don't edit past entries when a decision changes later — add a new entry that supersedes it, so the reasoning trail stays intact.

## D1 — Registration mode is a Business capability, not a selling-screen choice
The original validation prototype (`product/01-validation/registro.html`) exposed Buttons/NFC as a tab the seller switches live while selling. This was correct for validating registration *speed* (the actual hypothesis under test) but is wrong as a permanent interaction model. `registrationMode` now lives on Business, resolved once at Session start. The selling screen never asks.

## D2 — Product is independent of Lot
Initial framing treated a Lot as if it were tied to a single product ("a Pajama Lot arrived"). Corrected: a Lot is a receiving event that can contain many different Products. Products persist in the Catalog independent of stock, so a sold-out Product doesn't disappear — she'll likely restock it.

## D3 — Full traceability requires unit-level inventory, not batch-level
Initial domain pass modeled Lot → InventoryEntry (a line-item: Product + quantity + cost). This was insufficient: the requirement is that every physical unit's originating Lot is always knowable, even when two Lots of the same Product have different costs. Resolved by generating individual InventoryUnit records from each InventoryEntry — the merchant still just types a quantity, the platform expands it.

## D4 — NFCTag attaches to InventoryUnit, not Product
Originally assumed tags were durable, reusable, and assigned per Product type (matching the validation prototype's flat `uid → producto` map). Corrected: each physical unit gets its own tag at receiving time, so a scan identifies the exact unit (and therefore exact Lot) sold.

## D5 — Buttons-mode inventory allocation defaults to FIFO by Lot receipt date
NFC mode gets unit-level precision for free (the scan says which unit). Buttons mode has no physical identifier, so the system must decide which InventoryUnit a tap consumes. Default: oldest available unit first, fully automatic. Directly follows the principle "every repeated decision should become automation" — this is not a decision the merchant should ever be asked to make.

## D6 — Session does not require an Event
Selling must never require scheduling first — it would add a step in front of the exact friction point (registration speed) already validated as the top priority (`company/backlog.md` #1). Session carries an optional `eventId`; "Iniciar Sesión Rápida" always works with zero setup.

## D7 — Sale is its own aggregate root, not nested inside Session
Considered nesting Sale inside Session's aggregate boundary. Rejected: the <3s speed requirement means Sale writes need to be independent and cheap to append, not mediated through a shared Session-level lock.

## D8 — Bazaar renamed to Event; Event is a light root, not a strict parent of Session
Generalizes beyond bazaars (Expo, Pop-up, Festival, Market, Office Sale) without a schema change later. Event does not own Session as a strict aggregate — "analyze the Event as a whole" is a read-side query across Sessions sharing an `eventId`, not a write-consistency requirement, per DDD guidance to keep aggregates small.

## D9 — Supplier and purchase cost included in schema from v1, deliberately unused
The one sanctioned exception to "build only what's validated." Avoids a future migration once margin analysis / Open Finance features are prioritized. Must stay structurally present and completely invisible (no menu, no screen) until backlog calls for it — see `architecture-principles.md` #5.

## D10 — Loyalty-claim is an independent future module, customer-facing, zero merchant IA presence
The person scanning a sold tag post-sale is the customer, on their own device — not Ana. Modeled as a separate bounded context that only reads `InventoryUnit.status` (must be `sold`) and writes a Customer↔SaleItem link. The dual-purpose tag scan (sale-time vs. claim-time) is disambiguated entirely by `InventoryUnit.status`, so no explicit mode/intent has to be asked of anyone. This is also what guarantees a customer scan can never overwrite or create a Sale — the merchant's finalized Sale remains the sole source of truth structurally, not just by convention. **Wording refined — see D21**: this entry's "zero merchant IA presence" phrasing was later found to be imprecise and was clarified, not reversed.

## D11 — NFC tags are consumable; reframed as a recurring investment, not a one-time kit
`company/CLAUDE.md` originally noted the NFC kit as "likely bundled once, not recurring." That's now superseded: tags are attached per InventoryUnit and leave with the customer permanently (they become part of the loyalty journey, D10). This makes them a recurring consumable — the starter kit is a one-time onboarding item, but merchants buy additional tag packs as they keep selling. This is a business-model decision, not an architectural one; the domain model (D4) already supports either resolution. `company/CLAUDE.md` was updated to match. Positioning: an investment that unlocks customer relationships and analytics, not a recurring cost/burden.

## D22 — Customer Segmentation is a core capability; Claim generalizes to multiple resolution mechanisms; Intelligence consumes only Derived Customer Intelligence
Resolves Q8 (`company/business-decisions.md`), after a three-round joint Planner (business-impact) and Architect (domain-implications) analysis. Product Owner chose the complete-capability design (previously "Path (a)") over narrowing Customer Segmentation to something identity-free ("Path (b)"), on the explicit grounds that Customer Segmentation is a core product capability from the start — not an artifact of which `registrationMode` a merchant happens to use.

**The complete target design, described here in full regardless of build order** (see `product/99-rfc/0002-loyalty-claim-complete-capability.md` for the full RFC):
- **Claim is one business capability** (`loyaltyEnabled`), resolvable through multiple mechanisms: the existing NFC tag scan (D4/D10, unit-level — one Claim per scanned tag), a new Sale-level **Claim Token** (Selling-owned, generated at Sale finalization whenever `loyaltyEnabled = true`, independent of `registrationMode`, displayed to the customer as e.g. a QR code so she can start the Loyalty-claim flow on her own device), and future mechanisms following the same pattern. All converge on the identical terminal write: one or more Customer↔SaleItem Claim links. A single Claim Token scan resolves into N independent SaleItem-level Claims for a multi-item Sale — architecturally identical in shape to how a multi-item NFC Sale already produces N independent claims via N separate tag scans (Architect's definitive ruling). No new "Sale-level Claim" concept was introduced — `ubiquitous-language.md`'s Claim definition stays structurally the same, generalized only in how it's triggered.
- **`registrationMode` determines which mechanism a given Sale uses, never whether the capability exists.** Customer Segmentation is gated only by `subscriptionTier=paid` and `loyaltyEnabled=true`.
- **Customer Identity belongs exclusively to the Loyalty platform.** The Merchant Application never performs identification and never reads a raw Customer or Claim record.
- **The Merchant Application consumes only Derived Customer Intelligence** — an anonymized, aggregate signal (e.g., counts of frequent vs. occasional buyers) that Loyalty-claim computes from its Claims and exposes read-only to Intelligence. No name, no contact info, no per-Claim drill-down ever reaches the merchant app.
- **New bounded-context dependency edges** (`domain-model.md`'s table): Loyalty-claim gains a read-only dependency on Selling (to resolve a Sale's SaleItem set for the Claim Token mechanism); Intelligence gains a read-only dependency on Loyalty-claim (Derived Customer Intelligence only). Selling itself gains no new dependency and stays completely unaware either context exists — the Claim Token is a field Selling generates and owns, the same shape NFCTag already has relative to Loyalty-claim (D4).
- **Claim Token security**: must be an opaque, signed reference, never the raw Sale ID — the same "customer scan can never affect a Sale" reasoning from D10 extends to "must not be guessable" for a token that can be scanned by anyone who sees it.

**Routed through `product/99-rfc/0002-loyalty-claim-complete-capability.md`** — this changes the bounded-context dependency graph (two new read edges) and generalizes a ubiquitous-language term (Claim), both explicit RFC triggers, same precedent as D20's Venue RFC.

**Implementation sequencing is explicitly not decided here.** Per the Product Owner's instruction, this entry and the RFC describe the complete target vision only; staged build order (which mechanism ships first) is tracked separately in `company/backlog.md` #2, not in the Foundation.

**Applied**: `reports.md` §3.6/§3.12/§3.13 ("Tus clientes") was redesigned as a real spec against this resolved architecture — gated by `subscriptionTier=paid` and `loyaltyEnabled=true` together, consuming only Derived Customer Intelligence — and went through its own full design pass (`ux-designer` → `ux-critic` → `reviewer`, zero Blockers/unresolved Majors). See `product/02-ux/ux-critic-findings.md`'s "Customer Segmentation (Q8) resolution cycle" entry for the full review record.

## D21 — Loyalty-claim's merchant-app boundary, corrected wording
Surfaced during the Q8 (`company/business-decisions.md`) joint Planner/Architect analysis: D10's and `information-architecture.md`'s original phrasing — "no entry point anywhere in the merchant app" / "zero merchant IA presence" — proved genuinely misleading once a concrete Buttons-mode claim mechanism (a QR code displayed by the merchant app at Sale finalization) was considered. Planner correctly flagged that literal wording as ambiguous: does the merchant app *displaying* an artifact the customer then scans count as an "entry point," even though the customer performs the actual identification/claim action on their own device? The original wording never anticipated this case clearly enough to answer it.

Product Owner corrected the rule to be precise rather than reversing the underlying boundary, which was always correct in substance:
- The Merchant Application never participates in customer identification or the Loyalty flow.
- Customer Identity is owned exclusively by the Loyalty platform.
- The Merchant Application may display artifacts (an NFC tag, a QR code, a receipt, or a future claim mechanism) that let the customer start the Loyalty experience on their own device.
- The Loyalty experience always runs independently from the Merchant Application.

This resolves the ambiguity Planner raised: displaying a passive artifact (tag, QR, receipt) is explicitly permitted and was never what D10 intended to forbid — what's forbidden is the merchant app performing identification, running any part of the Loyalty experience, or ever seeing Customer/Claim data. No bounded context, aggregate, or dependency edge changes — this is a wording clarification only, applied to `information-architecture.md` and `domain-model.md`'s bounded-context table. D10 itself is left unedited per this log's convention of not rewriting history; this entry supersedes only its imprecise phrasing, not its substance.

## D20 — Venue introduced as a new aggregate root, owned by Selling; replaces Event's freeform Nombre/Lugar
Raised as Q9 in `product/02-ux/product-decisions.md`: `reports.md`'s "Rendimiento por bazar" could only group by exact-string match on Event's freeform `Nombre`, risking silent fragmentation from typos/renaming across visits. Product Owner resolved to introduce a lightweight Venue entity now (`id`, `businessId`, `displayName`, optional address/notes, `active`) rather than deferring — see `product/02-ux/product-decisions.md` Q9 for the full shape. Architect classification: Venue is a new aggregate root, following the same independent-identity pattern as Product (D2) — own id, referenced by ID from Event (never embedded), many Events may share one Venue, own lifecycle (`active`) independent of any single referencing Event. Owned by Selling, not Inventory — Venue's only consumer is Event (mirroring how Supplier's sole consumer, Lot, keeps Supplier in Inventory), and Venue has no relationship to merchandise/Catalog/Lot; placing it in Selling also avoids an unforced new Selling→Inventory dependency edge. Event.venueId is a required reference (not nullable) — resolved via an inline create-or-select picker mirroring Inventario's Product picker. Event's previous freeform Nombre field is retired: Venue.displayName is now the sole identity/display label; repeat Events at one Venue are already distinguished by date range in every existing wireframe, so no information is lost. Event's optional Lugar field is also retired: Venue's own optional address/notes is the single durable location record, inherited by every Event referencing that Venue, rather than risking per-Event drift. Routed through `product/99-rfc/0001-venue-entity.md` before promotion here — the first new aggregate root added since Domain Model v1 froze, and it retires fields in two already-Approved UX specs (`events.md`, `reports.md`), unlike D17's same-entity validation tweak. **Applied**: `events.md` (new Elegir lugar picker, §3.7; every screen updated to `Venue.displayName`) and `reports.md` (Rendimiento por bazar regrouped by `venueId`) were run through their own full design pass (`ux-designer` → `ux-critic` → `reviewer`) and are Approved with the Venue aggregate root in place — see `product/02-ux/ux-critic-findings.md`'s "Venue aggregate root cycle" entry for the review record.

## D19 — Initial Business capabilities are set as a consequence of an Onboarding path, never as an isolated toggle
Raised as Q4 in `company/business-decisions.md`: who/what sets a Business's initial `registrationMode` (and other capabilities) on first run. Product Owner resolved: the merchant chooses how she wants to start with Nahui (e.g., "Empezar gratis," "Activar kit NFC," a demo path) — `registrationMode`/`subscriptionTier` follow as a consequence of that choice, never surfaced as a raw technical setting. Directly required by `global-principles.md`'s "business language before technical language" and "never ask twice"; structurally consistent with `architecture-principles.md` #1 and D13's existing Onboarding sequencing. No change to `domain-model.md`'s Business Capabilities table — it correctly only ever described read-time behavior, never the write/set mechanism.

**Payments/checkout boundary, recorded explicitly:** the "Activate NFC Starter Kit" path is confirmation of an already-obtained physical kit (e.g. an activation code), not an in-app purchase — zero payment processing in the product. Any future in-app purchase flow would reverse `company/CLAUDE.md`'s explicit "Payments/checkout — out of scope" non-goal and needs its own Business Decision; it does not arrive implicitly via this onboarding path. Does not reopen D11 (D11 is silent on purchase channel).

**Demo profile:** no new domain modeling — a demo Business is an ordinary Business with seeded data, contingent on demo profiles never needing behaviorally-distinguishable treatment anywhere downstream (no expiry, no reporting exclusion, no conversion migration). If that contingency is ever violated, it needs its own small decision-log entry (e.g. a `Business.isDemo` flag) at that time, not a silent addition now.

This resolves *how the initial value is set*; whether a capability can ever change after onboarding (self-service vs. support-only) remains open as the narrowed Q5 in `company/business-decisions.md`.

## D18 — Session's `reviewed` state stays dormant; no trigger designed
Raised as Q10 in `product/02-ux/product-decisions.md`: `domain-model.md`'s Session lifecycle includes `closed → reviewed`, but nothing sets it, and `reports.md`'s "Review" journey never designed a mechanic that would (Resultados/Intelligence is read-only over Selling per `architecture-principles.md` #6, so it can't flip the status directly). Product Owner resolved: leave it unused for now — no merchant-facing "mark as reviewed" action, no UX design work. Documented as reserved for a possible future reporting/reconciliation workflow, to be revisited only once there's a real merchant need and a defined, Selling-owned trigger. No Foundation change beyond this note; `reports.md` already correctly avoided designing a write path here.

## D17 — At most one Event per Business may be active/scheduled with an overlapping date range at a time
Raised as Q3 in `product/02-ux/product-decisions.md`: `home.md`'s resolution logic assumed at most one Event is ever `active`, but nothing in the frozen model prevented a Business from scheduling two overlapping Events. Rather than add automatic tie-break logic to Home (e.g., earliest-start-wins), Product Owner resolved to remove the ambiguous state entirely: a Business may not create or activate an Event whose date range overlaps an already-scheduled-or-active Event. Architect confirmed this is additive (Event's "light root" description was silent on Event-to-Event concurrency, not permissive of it) and requires no RFC — it's a same-context, same-entity uniqueness validation, not a cross-bounded-context concern. This makes `home.md` §2's single-active-Event assumption correct by construction; no change to `home.md` is needed. `events.md`'s "Nuevo Evento" flow will need a new blocked-save/validation error state for the overlap check — a UX design task, not designed as part of this decision. Explicitly scoped as an MVP simplification, not a permanent limit: supporting concurrent Events belongs to a future multi-employee capability (multiple sellers under one Business account) — noted as a genuinely different kind of "multi-user" problem than backlog #3's cross-tenant bazaar-recommendation feature, since it needs no cross-tenant data and could be built whenever prioritized, not blocked on a data source the way backlog #3 is.

## D16 — Event `type` stays a closed, fixed list for the current phase
Raised as Q6 in `product/02-ux/product-decisions.md` during Eventos UX review: `ubiquitous-language.md`'s trailing ellipsis on Event type didn't settle whether the list (Bazaar, Expo, Pop-up, Festival, Market, Office Sale) was closed or merchant-extensible like Product names. Product Owner resolved: closed for now — simpler to build and validate, and no domain logic currently branches on Event type in a way that requires openness. New types can be added later via a product update if real usage calls for it; this is a deliberate MVP scope choice, not a permanent constraint. `events.md` §3.7's picker (no "add new type" affordance) already matched this decision, so no UX spec change was required — only the open-question status closes.

## D15 — "Día N" is computed by distinct calendar date, not raw Session count
Raised as Q1 in `product/02-ux/product-decisions.md` during Home UX design: whether reopening a Session the same calendar day under an Event (e.g. a lunch-break resume) increments "Día N" or not. Product Owner resolved: "Día N" counts distinct calendar dates with at least one Session under the Event, not raw Session instances — a same-day reopen does not increment the day number. This matches Session's own naming intent ("one working day of selling," `ubiquitous-language.md`) more literally than a raw-count reading would. Applied to `domain-model.md`'s "Key mechanisms" section as the canonical computation rule; every UX doc that displays "Día N" (`home.md`, `events.md`, `reports.md`) already reuses one shared computation rather than deriving it independently, so this closes the ambiguity everywhere at once, not per-document.

## D13 — Onboarding and Settings are sequencing/affordance facts, not fifth/sixth nav tabs
Raised when Onboarding and Settings needed to be scoped for `product/02-ux/` documentation despite neither appearing in the frozen four-tab `information-architecture.md`. Architect confirmed both are genuine gaps but each resolves cleanly without adding a tab: Onboarding is a first-run flow that precedes all four tabs (a Business and its initial capabilities must exist before Home's resolution logic has anything to resolve) and is never revisited once complete; Settings hangs off the session-controls affordance already specified in `home.md` §3.7 (the header's "▾"), consistent with "selling is a state, not a navigation destination" — capability management gets a surface, not a destination. What remains genuinely unresolved (Business Decisions, not architectural ones, logged in `company/business-decisions.md` as Q4 and Q5): who/what sets `registrationMode` on first run, and whether any Business Capability is ever merchant-self-service-editable after onboarding.
