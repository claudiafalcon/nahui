## D48 — `demo-mode.md` fits neither D13/D45's class nor D38's — a third, narrower category: validation-campaign infrastructure, co-located in `product/02-ux/` for pipeline/deploy convenience only

Raised when `demo-mode.md`'s own §8 flagged a placement ruling as needed, but the doc's draft had already asserted its own answer ("same class as D13/D45") without an actual `architect` check — caught before that assertion was treated as settled.

**Ruling: it fails D13/D45's test at the premise, and it isn't D38's class either.** D13 and D45 both resolved the same narrow question — is this a nav tab, or does it resolve out of that question while remaining genuine, permanent Merchant Application content that ships to every real merchant, every time? `demo-mode.md` fails that at the premise: by its own text, it "has no code path at all in a real, shipped build... not merely hidden, structurally absent." D13/D45 never had to reason about a screen that cannot exist in production at all — that axis (ships-in-production vs. build-variant-only) is one they never anticipated. Sharper evidence: `demo-mode.md §1`'s own Scope boundary states, in its own words, "validation/testing infrastructure, not a merchant-application capability" — the identical self-exclusion shape D38 relied on when `customer-loyalty-registration.md §0` disclaimed Merchant Application membership. A document can't credibly claim D13/D45-class membership in its front matter while its own body disclaims that same membership.

It isn't D38's class either. D38's decisive test was whether the artifact is actually part of the same deploy target/audience as the rest of `product/02-ux/` — Loyalty-claim failed that on structural grounds (a genuinely separate deploy target, `domain-model.md`'s own module-boundaries note; a structurally distinct domain role, Customer, never modeled as an authenticated identity, D44). `demo-mode.md` passes that same test cleanly: same codebase, same build artifact (`product/02c-high-fidelity-prototype/`), same audience class — a real bazaar vendor, not a structurally distinct role. Its "validation-campaign participant, not Ana-as-ongoing-merchant" framing is a persona distinction, not an audience-*class* distinction. No new bounded context, no new module, no new deploy pipeline is implied. Standing up a new folder for one disposable, campaign-scoped document would repeat the organizational overkill D41 already reasoned against when it rejected inventing new structure where existing structure fits well enough — and `01-validation/`'s "throwaway, speed over quality" charter is an equally poor fit for a fully-speced, Product-Owner-approved-in-concept, `brand-guardian`-reviewed document headed for real implementation.

It's a third, narrower category: validation-campaign infrastructure, co-located here for pipeline/deploy-artifact convenience, explicitly excluded from the "designed Merchant Application experiences" status family `product/02-ux/CLAUDE.md` tracks.

Non-blocking to Architecture Review proceeding — a classification correction, not a redesign; nothing in the document's own decision logic, wireframes, or flow changes.

## D47 — `Claim` schematized with an explicit field table

`ubiquitous-language.md` defined **Claim** only in prose ("the act of linking a Customer to an already-sold SaleItem... resolvable through multiple mechanisms... all converging on the identical terminal write") — every other aggregate/entity in the domain model has an explicit field table except this one, a real gap surfaced by `architect`'s Gap Analysis ahead of `product/02c-loyalty-prototype/`'s first build (the Customer Loyalty Registration React implementation, `product/02-ux-loyalty/customer-loyalty-registration.md`).

**Schema:** `Claim { id, businessId, customerId, saleItemId, claimedAt }`. `businessId` is denormalized for query convenience, matching the same Business-scoping discipline every other aggregate root in this model already carries (D35) — not a new requirement, just naming what was already implied. One Claim per SaleItem, per `ubiquitous-language.md`'s own definition; a Sale's SaleItems become individually claimable as Claims are created against them (this is what makes `customer-loyalty-registration.md` §2 step 2's "already-claimed" check — some SaleItems claimed, some not — coherent).

**Not RFC-worthy** — same class as D37's own dedup-rule/`loyaltyRewardThreshold` additions: no new aggregate, no bounded-context edge, no ubiquitous-language redefinition, just a field table for a concept the Foundation already named and reasoned about in prose.

## D46 — Tag-assignment auto-entry gates on merchant intent (`defaultSellingMode = 'nfc'`), not mere capability (`nfc ∈ registrationMode`)

Raised by the Product Owner directly, testing the just-shipped Asignar Tags/NFC Selling slices: a Paid merchant who registers merchandise is unconditionally auto-routed into the Asignar Tags queue the moment `Guardar mercancía` succeeds, regardless of whether she has any intention of ever using `nfc` as her selling mode — `inventory.md`'s own auto-continuation trigger (§2 step 2, §3.14, §9) reads `nfc ∈ registrationMode` (Selling Mode Capability, i.e. `subscriptionTier = 'paid'`), not `defaultSellingMode = 'nfc'` (her actual chosen mode).

**This is a genuine, previously-unnoticed contradiction between two already-Approved documents' own reasoning, not a new preference invented here.** `onboarding.md` §2.3 explicitly reasons that `defaultSellingMode` stays `buttons` at Onboarding precisely because *"she may be subscribing purely for the future segmentation value, with no intention of using tags yet."* `inventory.md`'s auto-tagging trigger ignores that exact distinction it was written to respect — capability (billing tier) and intent (selling-mode choice) are two different Business Capabilities (D23), and only D27's read-time derivation (`nfc ∈ registrationMode ⟺ subscriptionTier = 'paid'`) was ever meant to collapse into `subscriptionTier`; `defaultSellingMode` was never meant to collapse into it too.

**Ruling: three genuinely distinct facts, kept distinct, exactly as D23 originally separated them — this decision restores that separation where `inventory.md`'s auto-entry trigger had silently blurred it:**
- **NFC availability** (`nfc ∈ registrationMode`) — a pure Business Capability, `subscriptionTier = 'paid'`-derived (D27). Unchanged.
- **Merchant intent to use NFC** (`Business.defaultSellingMode = 'nfc'`) — her own self-service choice (`settings.md`'s "Cambiar a vender con tags"). Unchanged as a field; **now the correct auto-tagging gate.**
- **NFC Readiness** (tagged-vs-total sellable inventory, `home.md` §2/§3.6a) — a live, computed ratio. Unchanged.

**New trigger rule, replacing the old capability-gated one:**
1. After `Guardar mercancía` succeeds, auto-enter Asignar Tags **only if `defaultSellingMode === 'nfc'`** (not merely `nfc ∈ registrationMode`).
2. Immediately after a merchant switches `defaultSellingMode` from `buttons` to `nfc` in Configuración, auto-enter Asignar Tags if untagged inventory already exists.
3. If she switches to `nfc` with zero inventory registered yet, she is guided to register merchandise first — an empty tagging queue is never shown as the landing state.

A Paid merchant who never switches to `nfc` mode is never auto-routed into tagging, at any point, for any reason.

**Not RFC-worthy** — same class as D23/D27: a resolution-logic/trigger-condition correction reusing existing fields (`defaultSellingMode`, `registrationMode`, `InventoryUnit.tagId`), no new aggregate, bounded context, or ubiquitous-language term.

**Applied:** `onboarding.md`, `inventory.md`, `settings.md`, `home.md` (wherever any of the three facts above or the old trigger condition is referenced) cascade through the standard Governance Rollout Cascade (`company/CLAUDE.md`) before this is considered adopted; the React implementation (`product/02c-high-fidelity-prototype/`) is re-cascaded to match once the specs are re-Approved.

## D44 — RFC 0007 promoted: `User` and `BusinessMembership` schematized as new aggregate roots; Business creation gains a structural Owner-Membership invariant

**Promotes `product/99-rfc/0007-user-and-business-membership.md` (Status: Accepted) in full, as drafted — no amendments.** Product Owner decision: the first verified User creates the Business during onboarding and becomes its OWNER, atomically; additional Users join an existing Business later through a separate, future invitation flow with a SELLER-role `BusinessMembership`, not built in this slice. Activates the concern D17 already named and deliberately deferred (*"a future multi-employee capability (multiple sellers under one Business account)... could be built whenever prioritized, not blocked on a data source"*).

**`User`** — new aggregate root, Identity context. The first authenticated-identity concept anywhere in this Foundation (`Customer` is explicitly defined as *not* one). Global, not Business-scoped — the one deliberate exception to this Foundation's `businessId`-scoping pattern, justified against the exact 1:1-vs-1:N test RFC 0004 already established for `Customer`: a User's relationship to a Business is genuinely 1:N (one Business, many Users, via future invitations) and structurally N:M-capable, unlike Customer's 1:1-by-construction relationship to its one Business. Schema: `id`, `phone` (required, globally unique identity credential), `phoneVerifiedAt` (nullable timestamp), `createdAt`. No personal display-name field — not fabricated, a named gap.

**`BusinessMembership`** — new aggregate root, Identity context, not an entity nested inside Business. Fails `architecture-principles.md` #4's internal-only-entity test the same way `Venue` did (D20): resolving "which Businesses can this User act in, and with what role" requires querying by `userId` alone, independent of any single Business — the exact question a login has to answer. Schema: `id`, `userId`, `businessId`, `role` (`OWNER` | `SELLER` — closed set, same not-merchant-extensible treatment as `Event.type`, D16), `createdAt`. Unique on `(userId, businessId)`, the same class of dedup invariant D37 established for `Customer`.

**Owner-creation invariant, structural not conventional.** The only write path that creates a `Business` row (`onboarding.md` §3.5's existing "Creando tu negocio" write) is gated by a new precondition — the acting `User.phoneVerifiedAt` must be non-null — and atomically produces the new `Business` together with `BusinessMembership(userId, businessId, role=OWNER)` in the same transaction. No `Business` row can exist without a corresponding `OWNER` Membership, enforced by there being exactly one write path capable of creating a Business at all. Direct one-level-up extension of D19's onboarding-consequence pattern (*"capabilities are set as a consequence of an Onboarding path, never an isolated toggle"*) applied to Business existence itself. Inherits `architecture-principles.md` #7/D30's idempotency-key discipline, since it extends an already retry-exposed write (`onboarding.md` §3.5a).

**No new bounded-context dependency edge.** `User`/`BusinessMembership` are added to Identity's existing "Owns" cell alongside `Business, Capabilities`. Confirmed explicitly that Selling does not gain a dependency on them — "which User ran this Sale" is a genuinely new capability (attribution/audit) nothing in this Foundation names a need for; if ever wanted, it's its own future Product Decision, the same restraint D26 already applied to `Sale.claimToken`.

**Explicitly out of scope, confirmed unreachable by construction, not merely deferred:** invitations/acceptance flow (no `Invitation` concept modeled); any code path that could create a `SELLER` Membership (the only Membership-creating write always assigns `OWNER`); SELLER-role permission enforcement (moot — no `SELLER` Membership exists yet to enforce against); real SMS/OTP delivery infrastructure (a build-layer/authentication-provider concern, not domain — the domain model only needs `phoneVerifiedAt` to end up non-null through whatever mechanism produces it); any real authentication/session/token mechanism (login persistence, request-level auth enforcement).

**RFC-trigger test.** Two new aggregate roots + two new ubiquitous-language terms — unambiguously RFC-worthy, same class as RFC 0001 (Venue) and RFC 0004 (Customer).

**Applied:** `domain-model.md`'s Aggregate roots gains `User` and `BusinessMembership` entries (owned by Identity); bounded-context table's Identity "Owns" cell updated; Key Mechanisms gains the "Owner-creation invariant" subsection; Entity relationships diagram gains the minimal `User → BusinessMembership → Business` addition. `ubiquitous-language.md` gains `User` and `BusinessMembership` entries in the Identity context section. `product/02-ux/authentication.md` (the phone+OTP UX spec this RFC makes implementable) proceeds through its own standard review cycle separately — this entry promotes the domain shape only, not that document's UX content.

**Left open, not resolved here (see `product/02-ux/architect-questions.md` Q17, `product-decisions.md` Q18):** whether a single User may later found/own more than one Business; whether Ana ever needs a personal display-name field; what happens when an already-verified phone re-verifies from a session-less device already tied to an existing Business (Q18) — deferred, non-blocking at pilot scale.

## D43 — Two distinct React-adoption workflows: a Migration Workflow for journeys with an already-Approved Medium-Fidelity UX spec, and D42's full 7-stage workflow reserved for genuinely new features

Clarifies D42, which is left unedited per this log's own convention — this entry narrows how D42 applies, it doesn't reverse anything in it. Raised when the Product Owner, reviewing the proposed Onboarding slice, distinguished two cases D42's own text didn't separate: a journey that already has an Approved Medium-Fidelity UX specification (six of them exist — Hoy, Inventario, Eventos, Resultados, Onboarding, Configuración, per `product/02b-medium-fidelity/CLAUDE.md`'s own now-dormant tracking) versus a genuinely new feature with no prior spec at all. D42's full 7-stage workflow (Product Definition → UX Flow Review → Architecture Review → High-Fidelity React → Review Pipeline → Product Approval → Backend Integration) was written for the second case; applying its Stage 1/2 in full to the first case would mean re-litigating UX work that's already Approved and settled, which is exactly the "endless polish cycle" this project has repeatedly had to correct itself out of.

**Ruling — two workflows, not one:**

**Migration Workflow** (for any journey with an already-Approved Medium-Fidelity spec — currently: Eventos, Resultados, Onboarding, Configuración; Hoy/Inventario already migrated as Slice 1):
```
Approved UX Specification (product/02-ux/*.md, already Approved — treated as the implementation contract)
        ↓
Architecture Gap Analysis (architect — implementation-readiness only, see below)
        ↓
High-Fidelity React Implementation (ui-designer, product/02c-high-fidelity-prototype/)
        ↓
Review Pipeline (ux-critic → reviewer → merchant-user-tester)
        ↓
Approved Slice
```

The already-Approved `product/02-ux/*.md` document is the implementation contract, not a draft to reopen. `architect`'s Architecture Gap Analysis identifies implementation gaps only — domain-model fields the spec needs but the current `src/domain/` doesn't yet have, write-path strategy, scope boundaries against other not-yet-built slices — it does not redesign or re-evaluate the approved UX. Product or UX discussions are not reopened during a migration slice unless `architect` (or any later reviewer) surfaces a genuine contradiction, a missing requirement, or a real implementation blocker requiring Product Owner input — named explicitly and routed through Decision Ownership like any other escalation, not silently resolved by relitigating the spec.

**New-Feature Workflow** (D42's full 7 stages, unedited) — reserved for a feature with no prior Approved spec at all. Becomes Nahui's *default* process only once every existing Medium-Fidelity journey has been migrated through the workflow above — until then, the Migration Workflow is what Main actually runs for each item in `product/02c-high-fidelity-prototype/BACKLOG.md`.

**Validation:** Slice 1 (Home/Inventario/Selling/Receipt) is confirmed, retroactively, as the first successful instance of the Migration Workflow — it built directly on `home.md`/`inventory.md`'s already-Approved specs, and `reviewer`'s Blocker/`ux-critic`'s Major findings during that slice were implementation-correctness findings against the approved contract, not UX redesigns. This is the precedent the Migration Workflow generalizes.

**Applied:** `company/CLAUDE.md`'s "Product Backlog Ownership" section (D42-adjacent) gains a description of the two workflows and when each applies. `product/02c-high-fidelity-prototype/CLAUDE.md` and `BACKLOG.md` updated to name the Migration Workflow as what actually runs for each remaining known journey.

## D1 — Registration mode is a Business capability, not a selling-screen choice
The original validation prototype (`product/01-validation/registro.html`) exposed Buttons/NFC as a tab the seller switches live while selling. This was correct for validating registration *speed* (the actual hypothesis under test) but is wrong as a permanent interaction model. `registrationMode` now lives on Business, resolved once at Session start. The selling screen never asks.

## D2 — Product is independent of Lot
Initial framing treated a Lot as if it were tied to a single product ("a Pajama Lot arrived"). Corrected: a Lot is a receiving event that can contain many different Products. Products persist in the Catalog independent of stock, so a sold-out Product doesn't disappear — she'll likely restock it.

## D3 — Full traceability requires unit-level inventory, not batch-level
Initial domain pass modeled Lot → InventoryEntry (a line-item: Product + quantity + cost). This was insufficient: the requirement is that every physical unit's originating Lot is always knowable, even when two Lots of the same Product have different costs. Resolved by generating individual InventoryUnit records from each InventoryEntry — the merchant still just types a quantity, the platform expands it.

## D4 — NFCTag attaches to InventoryUnit, not Product
Originally assumed tags were durable, reusable, and assigned per Product type (matching the validation prototype's flat `uid → producto` map). Corrected: each physical unit gets its own tag at receiving time, so a scan identifies the exact unit (and therefore exact Lot) sold.

## D5 — Buttons-mode inventory allocation defaults to FIFO by Lot receipt date
NFC mode gets unit-level precision for free (the scan says which unit). Buttons mode has no physical identifier, so the system must decide which InventoryUnit a tap consumes. Default: oldest available unit first, fully automatic. Directly follows the principle "every repeated decision should become automation" — this is not a decision the merchant should ever be asked to make.

## D6 — Session does not require an Event
Selling must never require scheduling first — it would add a step in front of the exact friction point (registration speed) already validated as the top priority (`company/backlog.md` #1). Session carries an optional `eventId`; "Iniciar Sesión Rápida" always works with zero setup.

## D7 — Sale is its own aggregate root, not nested inside Session
Considered nesting Sale inside Session's aggregate boundary. Rejected: the <3s speed requirement means Sale writes need to be independent and cheap to append, not mediated through a shared Session-level lock.

## D8 — Bazaar renamed to Event; Event is a light root, not a strict parent of Session
Generalizes beyond bazaars (Expo, Pop-up, Festival, Market, Office Sale) without a schema change later. Event does not own Session as a strict aggregate — "analyze the Event as a whole" is a read-side query across Sessions sharing an `eventId`, not a write-consistency requirement, per DDD guidance to keep aggregates small.

## D9 — Supplier and purchase cost included in schema from v1, deliberately unused

## D35 — Customer as a Business-scoped aggregate root; Loyalty Participation Record, a new allowlisted identification edge alongside Derived Customer Intelligence

**Promotes `product/99-rfc/0004-customer-loyalty-participation-record.md` (Status: Accepted) in full.** Resolves the Frequent Customers MVP identity question the Product Owner narrowed explicitly: *"Merchant-visible customer identity is limited to loyalty participation. The merchant may see: email or masked email, age range, gender, purchase count, lifetime spend, reward-cycle progress. The merchant may not see: phone, address, payment credentials, unrelated personal data, cross-business customer identity, or customer activity outside that merchant's own Business."*

**`Customer` is schematized for the first time**, as a real aggregate root, **Business-scoped, not global** — carries `businessId`, so the same physical person shopping at two Nahui-powered Businesses produces two independent, unlinked Customer records. Chosen over a global-root-plus-per-Business-internal-entity shape because every other aggregate root in this model is already Business-scoped (Product, Lot, Event, Session, Sale, Venue), because the internal-entity indirection has no genuine 1:N relationship to model once Customer itself is scoped, and because it makes "no cross-Business customer identity" structural rather than access-controlled — there is no data structure anywhere connecting two Businesses' view of the same person. Schema: `id`, `businessId`, `email` (required, captured at first Claim), `ageRange`/`gender` (optional), `purchaseCount`, `lifetimeSpend`, `currentCycleProgress`, `completedCyclesCount` — all four counters stored, incrementally updated at the moment each Claim resolves (D33's `SaleItem.pricePaid` pattern, not D27's derive-don't-store pattern — this is Loyalty-claim mutating its own owned aggregate in response to its own domain event, the same self-mutation shape D29 already established). `maskedEmail` is a read-time derivation, not a stored field (D27 precedent). A reward threshold is a named, explicitly unresolved gap — it belongs on Business (a loyalty-program-level setting), not Customer, and Business's config for it doesn't exist yet.

**Confirmed against the Product Owner's own, later, more precise clarification** (the customer is not an authenticated platform user in this MVP — no login, no roles, no global account; identity is scoped as Business + email; the same email may hold independent relationships with multiple Businesses; the QR/Claim flow is identification, not authorization) — `architect`'s reasoning above and this clarification converged independently on the identical model.

**New bounded-context read edge**: Intelligence gains a second, narrower grant into Loyalty-claim, additive to its existing Derived Customer Intelligence grant (D22, unchanged) — a fixed, explicit allowlist field projection (`email`/masked email, `ageRange`, `gender`, `purchaseCount`, `lifetimeSpend`, `currentCycleProgress`, `completedCyclesCount`), scoped to Customers belonging to the reading Business. **Selling is explicitly not granted this edge** — confirmed by the Product Owner directly: *"Selling should remain independent from Loyalty/Customer identification. Ana does not need to identify or look up customers during the live Sale flow."* Preserves `domain-model.md`'s named guarantee that Selling never gains a dependency on Loyalty-claim/Intelligence.

**New ubiquitous-language term, "Loyalty Participation Record"** — the one allowlisted, identified (non-anonymized) view of a Customer the Merchant Application may read, alongside and never replacing Derived Customer Intelligence, whose existing absolute definition ("no name, no contact information, no per-Claim drill-down — ever") stays exactly as-is. Placed immediately after it in `ubiquitous-language.md`'s "Future: Loyalty-claim context" section.

**Structural (not conventional) denylist enforcement.** Phone, address, payment credentials, and other unrelated personal data are structurally absent from Customer's schema, not filtered out of a broader read — the edge's contract is an explicit allowlist projection, default-deny/explicitly-allow. Cross-Business identity is structurally impossible, a direct consequence of Customer carrying `businessId`. Raw Claim data / per-Claim drill-down and customer authentication of any kind are unaffected/out of scope by construction — the QR/Claim flow (D22) remains identification only, never authorization, for either the customer or Ana.

**Applied:** `domain-model.md`'s Aggregate roots gains a `Customer` entry (owned by Loyalty-claim); bounded-context table's Intelligence row gains the second Loyalty-claim grant, stated separately from D22's existing one. `ubiquitous-language.md`'s Customer entry expanded from placeholder to full schema; "Loyalty Participation Record" added. Not touched: `information-architecture.md` (no new nav destination), Claim Token mechanics (D22, unaffected), `reports.md`/any `product/02-ux/` doc (future `ux-designer` task, gated per D34 below), any authentication/login concept for either Ana or the customer.

**Sequencing, restated, not silently dropped:** this entry describes target schema/edge design only, same posture RFC 0002/D22 already took. It does not unblock implementation — see D34 below for the corrected gating and the backlog #1/#2 sequencing finding.

## D30 — Client-initiated retries must be idempotent/keyed; new `architecture-principles.md` #7

Surfaced during the same Architect build-readiness review as D29, ahead of the Product Validation Sprint. Every "Reintentar" action documented across the Approved `02-ux` specs (`home.md` §3.8a/§3.8d/§3.14's Sale-finalization and tap-to-add retries, `inventory.md`'s receiving-save retry, `settings.md`'s capability-save retry, and their equivalents elsewhere) promises the merchant no data loss on retry — but nothing in `architecture-principles.md` #1–#6 states what happens in the genuinely ambiguous case: the original write actually succeeded server-side, but the client never received confirmation (a dropped response, not a dropped request), and Ana taps "Reintentar" anyway. Without an explicit rule, a naive retry implementation risks silently producing a second Sale, SaleItem, Lot, Event, or capability-change record for the exact same action she believes she only took once — the opposite of what every one of those specs promises her.

Classified as a plain decision-log entry adding a new architecture principle, not RFC-worthy — it changes no aggregate boundary, adds no bounded-context dependency edge, and redefines no ubiquitous-language term; it states a technical constraint on how writes already described elsewhere in the Foundation (Sale/SaleItem, D7; Lot/InventoryEntry, D2/D3; Event, D8; capability changes, D25) must be implemented — the same category of addition D5's/D10's "how the platform disambiguates" rulings already are, just phrased as a standing principle rather than a per-mechanism ruling since it applies uniformly across every aggregate with a client-facing write.

**Ruling:** every write exposed to a client-initiated retry must be idempotent or keyed, so a genuinely ambiguous network failure (request succeeded, confirmation was lost) can never produce a duplicate record when the merchant retries. Concretely: the client attaches a stable idempotency key to the write attempt, generated once at the moment the action is first taken and reused unchanged on every retry of that same attempt — never regenerated on "Reintentar." The server treats a repeat of an already-seen key as "already done," returning the original result rather than creating a second record. This applies to every write named in a "Reintentar" affordance across the approved specs — Sale finalization, SaleItem registration, Lot/InventoryEntry receiving, Event creation/scheduling, and capability-change writes (`subscriptionTier`/`loyaltyEnabled`/`defaultSellingMode`, D25/D27) alike — not only Sale, even though Sale's <3s speed requirement (`architecture-principles.md` #2) makes it the write most likely to actually be exercised under real network conditions.

**Applied:** new `architecture-principles.md` #7 (see below). No change to `domain-model.md`, any bounded-context table, or `ubiquitous-language.md` — this is a write-mechanism constraint, not a structural one.

## D27 — NFC capability is derived from `subscriptionTier`, not an independently stored/toggled entitlement; welcome tag package is fulfillment-only; `defaultSellingMode` becomes merchant-self-service-editable

Classified as a plain decision-log entry, not RFC-worthy: no aggregate boundary changes, no bounded-context dependency edge is added, and no ubiquitous-language term is redefined — this corrects a write-mechanism assumption inside an already-frozen capability and extends existing self-service editability (D25) to one additional field, the same category of change D19 and D25 themselves were.

**1. Supersedes D19's "Activate NFC Starter Kit" framing.** D19 recorded the initial-onboarding path as "confirmation of an already-obtained physical kit (e.g. an activation code)" — correct that it was zero in-app payment, wrong that possessing a kit was ever the thing being confirmed as capability-granting. D23's "Default," not "Preferred," naming stays — the load-bearing half of the original rationale is unaffected.** D23 rejected "Preferred" on two grounds stated together: the field is "an operational fallback the Session may resolve away from," and "not a subjective disposition Ana would need to keep updating." ## D25 — Business Capabilities are fully self-service, bidirectional, at any time — subject to business-rule-governed timing, never deleting historical data
Resolves Q5 (`company/business-decisions.md`) — the last open item from the original Q1–Q10 set, and the one D19/D23 both explicitly left for later ("assumes a Business's capability set can change post-onboarding... without itself deciding the general self-service-editability mechanism"). Classified as a plain decision-log entry, not an RFC — closer to the RFC threshold than D17/D19 (it does add a small stored structure to a frozen aggregate), but it changes no aggregate boundary, adds no bounded-context dependency edge, and redefines no ubiquitous-language term; it completes a gap D19/D23 already named, rather than reopening or contradicting either.

**Resolution (Product Owner):** Merchants may self-service activate *or* deactivate the three named commercial capabilities, at any time: `subscriptionTier` (Free ↔ Paid), `loyaltyEnabled` (Loyalty Enabled ↔ Disabled), and `registrationMode`'s `nfc` entitlement (NFC Enabled ↔ Disabled). Two invariants apply to all three, in both directions:
- **Never delete historical data.** Confirmed already structurally guaranteed by the existing model, not something requiring a new mechanism: every Business Capability in this system is a read-time display/availability gate, never a condition on a write path or a cascade-delete rule (`architecture-principles.md` #6). Disabling `loyaltyEnabled` stops future Claim Tokens and hides segmentation display; it doesn't touch existing Claims (owned entirely by Loyalty-claim, D22). Removing `nfc` from `registrationMode` doesn't affect already-assigned NFCTags or their unit/Lot traceability (D4) — they simply become inert for *future* Sessions, per D23's own already-general wording. Downgrading `subscriptionTier` to `free` reverts Resultados' display choice, not the underlying Sale/Session/Lot/Claim history. This was true before this decision; it had just never been exercised in the deactivate direction until now — stated here explicitly as an invariant, the same discipline D23 applied to its own bounded-context table.
- **Business rules determine *when* the change takes effect — immediate or deferred, not always immediate.** This is the one place this decision adds real structure: for a merchant-facing deferred change (e.g., a Paid→Free downgrade landing at a future point) to ever be honestly displayable in `settings.md`, the fact that a change was requested — target value and effective date — has to live in the domain, not only inside an external scheduler's internal state (`global-principles.md`, "capture business truth once, reuse it forever"). Applied identically to all three: `subscriptionTier`, `loyaltyEnabled`, and `registrationMode`'s `nfc` entitlement each gain an optional pending-value + effective-date pair alongside their current value (the common "change lands at period end" shape). The mechanism that actually flips the field at the right time (a scheduled job, a billing-webhook handler) stays correctly external to the domain model; only the fact that a pending change exists, and when it lands, is domain data.

**What's explicitly not resolved here, and why:** the *specific* per-transition rule (which of the six directions is immediate vs. deferred, and what "deferred" concretely means for each) is a business/pricing-policy question, not a domain-modeling one — and it can't actually be pinned down yet, because it presupposes a billing-cycle concept that doesn't exist anywhere in this Foundation. `company/CLAUDE.md`'s business model direction is explicit that pricing is "not final," and payments/checkout stays a stated non-goal. Treating the Product Owner's own illustrative example ("Paid→Free may become effective at the end of the current billing period") as a settled rule would mean inventing a billing-cycle concept nothing else in the Foundation supports yet. Tracked as its own open item in `company/business-decisions.md`, explicitly dependent on the pricing model being designed — same separation RFC 0002/`company/backlog.md` #2 already established between a Foundation-level vision and its own implementation-sequencing detail.

**Timing interaction with `Session.operatingMode` (D23):** no change needed to D23's existing guarantee. `Session.operatingMode` is resolved once, at Session-open, from whatever `registrationMode`/`defaultSellingMode` currently read *at that instant* — Session-open has no visibility into a pending, not-yet-effective change either way. Once a deferred change's effective date arrives and the field actually flips, this is indistinguishable from any other capability change, already covered by D23's own generalized wording ("that Session finishes normally... the restriction takes effect starting with the next Session only"). `subscriptionTier` and `loyaltyEnabled` never touch `Session.operatingMode` at all — they're per-action gates (Resultados render, Sale-finalization Claim Token generation), not Session-snapshotted — so this question was never in their scope to begin with.

**Applied:** `domain-model.md`'s Business Capabilities table gains the pending-value/effective-date structural note for all three capabilities, and the "never delete historical data" invariant is now stated explicitly rather than true only by omission. `company/business-decisions.md` Q5 moved to Resolved; a new, narrower open item records the still-undetermined per-transition timing table, explicitly blocked on the pricing/billing-cycle model. `settings.md` is now unblocked — six merchant-facing actions (three capabilities × two directions), a reusable "pending change, takes effect on [date]" indicator pattern, and a way to cancel a pending change before it lands, tracked as its own UX design task.

## D23 — Session-scoped selling mode: capability as availability, a Business-level default, and a per-Session inventory-readiness recommendation
Resolves `product/99-rfc/0003-session-selling-mode.md` (Accepted). Raised when the Product Owner paused Q5 (`company/business-decisions.md`) to consider whether a richer model would resolve the underlying question — how selling mode actually gets decided — more cleanly than a direct self-service-editability answer to Q5 alone. `registrationMode` splits from a single Business-wide scalar into three distinct concepts, evaluated jointly by Architect (domain-modeling soundness) and UX Designer (interaction/friction) before any Foundation change was proposed, then refined directly by the Product Owner:

- **Selling Mode Capability** (`registrationMode`, Business-level, Identity context) — now a *set* of available modes, not one active value: `buttons` always included; `nfc` an add-on entitlement. Governs *availability* only, never which mode a given Session actually runs in.
- **Default Selling Mode** (`defaultSellingMode`, Business-level, Identity context) — a new stored field: the Business's normal operating mode, set via Onboarding (D19) and read as the fallback at Session start. Not itself the operative value. Named "Default," not "Preferred," on Architect's confirmation: the field represents an operational fallback the Session may resolve away from, not a subjective disposition Ana would need to keep updating — and creates no collision with the unrelated, lowercase "default" already used in the FIFO-allocation passage below (D5), a different concept in a different context.
- **Session Operating Mode** (`Session.operatingMode`, Session-level, Selling context) — a new stored field, resolved once at Session-open time, immutable for the remainder of that Session's `active` lifecycle. This closes a real, previously-identified gap: Session never used to snapshot which mode it ran under, since historically there was only ever one value to read. Fixed here as a direct consequence of this model, not a separate change.
- **NFC Readiness** — a computed, never-persisted, three-state evaluation run at Session-open time against sellable tagged inventory (`available` `InventoryUnit`s with an assigned `NFCTag`):
  - **Ready** — coverage above the readiness threshold. If `nfc` matches `defaultSellingMode`, the Session opens silently in `nfc` — no UI moment.
  - **Limited Ready** — some tagged inventory exists, but below threshold. `buttons` is recommended via a single lightweight inline nudge; the merchant may override toward `nfc` if her capability set allows it.
  - **Not Ready** — precisely zero sellable tagged inventory units exist. This is not a UX restriction or a stricter recommendation — it is an operational impossibility: `nfc` requires a physical tag to scan, and none exists, so `nfc` is withdrawn from the choice set entirely, overridable or otherwise. `buttons` is always available (it needs no tag), so selling itself is never blocked — only the impossible mode is withheld.

The recommendation is shown **only when it disagrees with `defaultSellingMode`** — the common case (Ready, matching the default) stays fully silent, preserving the substance of `architecture-principles.md` #1 ("capabilities resolved once, upstream, never asked mid-flow") even though the literal mechanism is now a per-Session read rather than a single frozen value. The readiness threshold itself is a configurable product/business rule, not a value hard-coded into the Foundation. If NFC capability is revoked while a Session is already active (e.g., a subscription lapse), that Session finishes normally in whatever mode it already resolved — the restriction applies starting with the next Session only.

Classified as RFC-worthy (not a plain decision-log entry) because it redefines a ubiquitous-language term and adds a new stored field to a frozen aggregate (`Session`) — the same category as D22/RFC 0002, not D17/D19's direct-entry precedent. No new bounded-context dependency edge was required — the readiness computation is answerable entirely from Inventory data Selling already reads (read-only, per the existing `architecture-principles.md` #6 direction).

**Relationship to other open items — deliberately not resolved here:**
- **Q5 (`company/business-decisions.md`) stays open.** This decision assumes a Business's capability set can change post-onboarding (e.g., `nfc` revoked by a subscription lapse) without itself deciding the general self-service-editability mechanism Q5 asks about (can a capability change post-onboarding, and by what mechanism — self-service in-app, or backend/support-mediated). That remains a separate, still-open Business Decision, narrower now than before this RFC only in that the *domain* question ("can the value change at all, without breaking anything") is settled; the *business/mechanism* question is not.
- **Q2 (`product/02-ux/product-decisions.md`) is unaffected, not superseded.** Q2 resolved a different, narrower scenario: an already-open `nfc`-mode Session encountering one specific untagged unit mid-Session (no data-model exception, redirect to Asignar Tags). This decision operates one level up, at Session-*start*, evaluating aggregate tagged-inventory coverage before a Session ever opens — it reduces how often Q2's scenario is reached (a Not Ready Session never even offers `nfc`), but doesn't replace Q2's own resolution for the residual case where overall coverage is fine yet one particular product's units happen to lack tags. Q2's own flagged UX design gap (`home.md` §3.10's redirect affordance) remains a separate, still-undesigned task.

**Applied:** `domain-model.md` (Business Capabilities table, entity-relationships diagram, Key Mechanisms), `architecture-principles.md` #1 (wording refresh), `ubiquitous-language.md` (new terms), `information-architecture.md` (Assign-Tags gate condition), `product/02-ux/home.md` and `product/02-ux/inventory.md` (UX updates per the RFC's scope) — full design pass (`ux-designer` → `ux-critic` → `reviewer`) tracked in `product/02-ux/ux-critic-findings.md`.

## D22 — Customer Segmentation is a core capability; Claim generalizes to multiple resolution mechanisms; Intelligence consumes only Derived Customer Intelligence
Resolves Q8 (`company/business-decisions.md`), after a three-round joint Planner (business-impact) and Architect (domain-implications) analysis. Product Owner chose the complete-capability design (previously "Path (a)") over narrowing Customer Segmentation to something identity-free ("Path (b)"), on the explicit grounds that Customer Segmentation is a core product capability from the start — not an artifact of which `registrationMode` a merchant happens to use.

**The complete target design, described here in full regardless of build order** (see `product/99-rfc/0002-loyalty-claim-complete-capability.md` for the full RFC):
- **Claim is one business capability** (`loyaltyEnabled`), resolvable through multiple mechanisms: the existing NFC tag scan (D4/D10, unit-level — one Claim per scanned tag), a new Sale-level **Claim Token** (Selling-owned, generated at Sale finalization whenever `loyaltyEnabled = true`, independent of `registrationMode`, displayed to the customer as e.g. a QR code so she can start the Loyalty-claim flow on her own device), and future mechanisms following the same pattern. All converge on the identical terminal write: one or more Customer↔SaleItem Claim links. A single Claim Token scan resolves into N independent SaleItem-level Claims for a multi-item Sale — architecturally identical in shape to how a multi-item NFC Sale already produces N independent claims via N separate tag scans (Architect's definitive ruling). No new "Sale-level Claim" concept was introduced — `ubiquitous-language.md`'s Claim definition stays structurally the same, generalized only in how it's triggered.
- **`registrationMode` determines which mechanism a given Sale uses, never whether the capability exists.** Customer Segmentation is gated only by `subscriptionTier=paid` and `loyaltyEnabled=true`.
- **Customer Identity belongs exclusively to the Loyalty platform.** The Merchant Application never performs identification and never reads a raw Customer or Claim record.
- **The Merchant Application consumes only Derived Customer Intelligence** — an anonymized, aggregate signal (e.g., counts of frequent vs. occasional buyers) that Loyalty-claim computes from its Claims and exposes read-only to Intelligence. No name, no contact info, no per-Claim drill-down ever reaches the merchant app.
- **New bounded-context dependency edges** (`domain-model.md`'s table): Loyalty-claim gains a read-only dependency on Selling (to resolve a Sale's SaleItem set for the Claim Token mechanism); Intelligence gains a read-only dependency on Loyalty-claim (Derived Customer Intelligence only). Selling itself gains no new dependency and stays completely unaware either context exists — the Claim Token is a field Selling generates and owns, the same shape NFCTag already has relative to Loyalty-claim (D4).
- **Claim Token security**: must be an opaque, signed reference, never the raw Sale ID — the same "customer scan can never affect a Sale" reasoning from D10 extends to "must not be guessable" for a token that can be scanned by anyone who sees it.

**Routed through `product/99-rfc/0002-loyalty-claim-complete-capability.md`** — this changes the bounded-context dependency graph (two new read edges) and generalizes a ubiquitous-language term (Claim), both explicit RFC triggers, same precedent as D20's Venue RFC.

**Implementation sequencing is explicitly not decided here.** Per the Product Owner's instruction, this entry and the RFC describe the complete target vision only; staged build order (which mechanism ships first) is tracked separately in `company/backlog.md` #2, not in the Foundation.

**Applied**: `reports.md` §3.6/§3.12/§3.13 ("Tus clientes") was redesigned as a real spec against this resolved architecture — gated by `subscriptionTier=paid` and `loyaltyEnabled=true` together, consuming only Derived Customer Intelligence — and went through its own full design pass (`ux-designer` → `ux-critic` → `reviewer`, zero Blockers/unresolved Majors). See `product/02-ux/ux-critic-findings.md`'s "Customer Segmentation (Q8) resolution cycle" entry for the full review record.
