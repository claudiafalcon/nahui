# Ubiquitous Language

One definition per term. If a document elsewhere seems to define a term differently, this file wins — fix the other document.

Each term is tagged with the bounded context that owns it (see `domain-model.md` for context definitions).

## Identity context

- **Business** — the merchant tenant (e.g., Ana). Root of all other data. Holds Business Capabilities. Carries `name` (required), `logo`/`description` (optional) — her own existing business identity, brought into Nahui at Onboarding rather than created there; `name`/`logo` render on the Digital Receipt, `description` is stored only today. `decision-log.md` D36. Also carries `loyaltyRewardThreshold` (optional) — how many completed Claims make up one reward cycle for this Business. `decision-log.md` D37. **Never created in isolation** — see User/BusinessMembership below and the Owner-creation invariant, `domain-model.md#key-mechanisms`. `decision-log.md` D44.
- **User** — an authenticated platform person. The concept `Customer` is explicitly *not* ("no login, no roles, no global account"). Global, not Business-scoped — the one deliberate exception to this Foundation's Business-scoping pattern, since a User's relationship to a Business is genuinely 1:N (via a future invitation flow), unlike Customer's 1:1-by-construction relationship to its one Business. Carries no credential of its own — every authentication method a User has verified lives on a separate `AuthIdentity` row (below); `User` is a bare identity anchor (`id`, `createdAt`) plus one person-level fact, `displayName` (optional, self-service-editable — `decision-log.md` D69, closing a gap this entry previously named as open). `decision-log.md` D44, amended by RFC 0012/D62, D69.
- **AuthIdentity** — one linked authentication credential belonging to a `User`. Own aggregate root, global (inherits `User`'s own already-justified exception to Business-scoping, not a second independent one). Carries `userId`, `type` (`phone` | `email` | `google` | `apple` — closed set, not self-service-extensible, same treatment as `BusinessMembership.role`/`Event.type`), `identifier` (the credential value — E.164 phone, email address, or OAuth provider subject ID, never the provider's associated email for `google`/`apple`), `verifiedAt` (nullable; non-null once that method's own verification completes). Unique on `(type, identifier)`, globally — resolvable by credential alone, before any single `User` is in context, the same structural test that already promoted `BusinessMembership`/`Invitation`/`EventAssignment`. A `User` may hold multiple `AuthIdentity` rows; adding one is always additive, never creates a second `User` (see "AuthIdentity resolution invariant," `domain-model.md#key-mechanisms`). At Nahui's current phone-only exposure, every `User` has exactly one row (`type=phone`) and this design is behaviorally identical to the pre-RFC-0012 model. `decision-log.md` D62.
- **BusinessMembership** — the join between a User and a Business, carrying `role` (`OWNER` | `SELLER` — closed set, same treatment as Event `type`, D16) and `status` (`active` | `revoked` — closed set, defaults `active`, flipped only by an OWNER-only revoke action, paired with a `revokedAt` timestamp set once on that same write, never deleted, no reactivation path designed, `decision-log.md` D55). A User holds at most one Membership per Business. Its own aggregate root, not nested inside Business — needed independently of any single Business to resolve which Businesses a User can reach (e.g., at login). The first verified User to complete Business onboarding receives an `OWNER` Membership, created atomically with the Business itself — no Business exists without one. `SELLER` Memberships are created atomically with a consumed `Invitation` — see Invitation, below. `decision-log.md` D44, D55, D56.
- **Invitation** — an OWNER's standing, single-use offer for a specific role (`SELLER` — closed set of one value, no picker exists since nothing distinguishes among options) on her Business, addressed to whoever holds its secure `token` — never to a phone number (RFC 0013/D64 — supersedes RFC 0012 §3's phone-specific ruling). Carries `businessId`, `token` (a cryptographically random, unguessable value, stored hashed at rest — the Invitation's real identity, embedded in a shareable link, still the sole way to *find* the offer), `role`, `status` (`pending` | `accepted` | `revoked` — closed set; `expired` is a derived read-time state, `status=pending AND now > expiresAt`, never itself written), `expiresAt`, a **required** `targetHint` (`{ type: 'email', value }` — the address the acceptance flow specifically authenticates through, pre-filled and locked, per `decision-log.md` D70; a security/UX gate on *accepting*, never a second way to *discover* the Invitation, and never `BusinessMembership`'s own canonical identity, which stays `userId`), and `acceptedByUserId` (nullable, set once on acceptance, historical record only). Unique on `token`, globally — resolvable by token alone, before any Business or User is in context, at link-open time (corrected from phone/OTP-verification-time resolution) — the same test that promoted `Venue`, `BusinessMembership`, and `EventAssignment`, one level generalized. Consumed, not merely referenced, on acceptance — the accepting `User`'s identity is resolved independently, through the ordinary `AuthIdentity` resolution invariant, narrowed to the Email method for this entry point specifically, before the acceptance write ever runs. `decision-log.md` D56, amended RFC 0012/D62, reworked RFC 0013/D64, RFC 0014/D70.

- **Disambiguation note** — `Invitation.token` is structurally similar to, but a distinct concept from, `Sale`'s own Claim Token (D22/D40) — different bounded contexts, different resolved thing (`Invitation.token` resolves a right to join a Business; `Sale`'s Claim Token resolves a Customer↔SaleItem link). Never conflate the two. Also distinct from this Foundation's capitalized **Capability** concept (a Business-level setting like `registrationMode`/`subscriptionTier`) — "bearer token" is unrelated security terminology, confined to architectural reasoning, never promoted schema or UI copy. `decision-log.md` D64.
- **Capability** — a Business-level setting that gates behavior elsewhere in the app. Never asked at Session/Sale time. See `domain-model.md#business-capabilities`.
  - **Selling Mode Capability** (`registrationMode`) — **redefined from a set to a boolean, `decision-log.md` D79 (previously "the set of selling modes available to the Business").** `buttons` was never actually a gated capability, so framing this as a set stopped fitting once Session-exclusive "mode" itself was retired (D79). Now: whether NFC is available to this Business at all — **read-time derived from `subscriptionTier`**, never independently stored or toggled (`nfcAvailable ⟺ subscriptionTier = paid`). The tier-derived entitlement layer beneath `nfcPerProductEnabled`'s own opt-in (below) and `Product.nfcTaggingEnabled`'s per-Product configuration — a three-layer structure, D79 makes explicit. `decision-log.md` D23, D27, D79.
  - `eventScheduling`: always available
  - `subscriptionTier`: `free` | `paid` — also entitles Frequent Customers (Claim collection, Loyalty participation) in full when `paid`, absent entirely when `free`. No separate merchant-facing toggle exists for this; see `decision-log.md` D40.
  - `nfcPerProductEnabled`: boolean, default `false` — the merchant's own opt-in to actually use NFC as an identification method, on top of Selling Mode Capability's own entitlement. Off by default even for an already-NFC-capable Paid Business. Gates the per-Product `nfcTaggingEnabled` toggle in Inventory and Selling's live "Leer con NFC" overlay — unconditionally, in every Session, never gated by a readiness threshold or a Session-resolved mode (both retired, D79). `decision-log.md` D71, D79.
- **Default Selling Mode** (`defaultSellingMode`) — **Retired, `decision-log.md` D79.** Formerly the Business's stored fallback selling mode, read at Session start alongside NFC Readiness to resolve Session Operating Mode. Its one remaining live reader (feeding that resolution) is gone now that both are retired — zero functional readers remain anywhere in the Foundation, confirmed by trace. Field kept in schema as inert historical data on any already-existing row (never deleted, D25); no code path reads or writes it going forward. `decision-log.md` D23, D27, D79.
- **Session Operating Mode** (`Session.operatingMode`) — **Retired, `decision-log.md` D79.** Formerly Session-level, `buttons` | `nfc`, resolved once at Session-open time, immutable for that Session's `active` lifecycle. Buttons, barcode scanning, and NFC tag scanning are now all live, composable selling capabilities within every Session, never a Session-wide exclusive mode — see "NFC as a live, composable selling capability," `domain-model.md#key-mechanisms`. No replacement field. `decision-log.md` D23, D79.
- **NFC Readiness** — **Retired outright, `decision-log.md` D79 (previously "Session-start resolution," D23).** Formerly the computed, never-persisted three-state evaluation (Ready / Limited Ready / Not Ready) run at Session-open time against sellable tagged inventory. Not narrowed or re-thresholded — no aggregate-coverage computation belongs in this decision under the corrected model; it existed only to arbitrate an exclusive Session mode that no longer exists. `decision-log.md` D23, D79.

## Inventory context

- **Catalog** — the set of Products a Business has ever sold. Persists independent of stock.
- **Product** — a sellable thing (e.g., "Pijama"). Exists independently of any Lot; stays in the Catalog even when sold out. Carries `defaultPrice` — the normal price Ana charges for this selling-group, set once at Product creation, editable later; a plain mutable current scalar, no version history. See `decision-log.md` D33. Also carries `photo` (optional) — a merchant-uploaded photo for this selling-group, capturable at creation or later, editable/removable anytime; one per Product, no gallery. See `decision-log.md` D54. Also carries `barcode` (optional) — a manufacturer/packaging barcode identifying this selling-group, scanned via phone camera, unique per Business (not globally). Captured the first time it's scanned during Inventory's own "Registrar mercancía" flow, never during a Sale — a Sale-time scan either resolves an already-known barcode to its Product (same as typing an already-known name) or dead-ends toward Inventario if unrecognized, since a genuinely new Product has no stock yet to sell. No external barcode-lookup database, by design — internal mapping only. See `decision-log.md` D65. **Clearable, `decision-log.md` D80** — a merchant can remove an existing `barcode`, returning the Product to the same "Sin código" state it had before one was ever scanned, so a Product is never permanently locked into its original identification method. Its own deliberate action, never an implicit consequence of saving a blank value; a single-column write that touches no `InventoryUnit` and no `NFCTag`, and that leaves `nfcTaggingEnabled` unchanged in either direction — clearing a barcode and opting into NFC stay two separate merchant actions. **A Product may be barcode-identified while some of its units still carry tags, and those units keep selling** (tag resolution reads no Product flag and no barcode, D79); any NFC-related fact shown about a Product must therefore be sourced from the live tagged-unit count — `InventoryUnit.tagId != null AND status IN ('available','reserved')`, D10's sale-time side of dual-purpose tag resolution; a `sold` unit keeps its `tagId`, since `finalize_sale` never deletes the `NFCTag` row — never from `nfcTaggingEnabled`. Also carries `nfcTaggingEnabled` (optional boolean, default `false`) — opts this Product's units into NFC tag-assignment eligibility in Inventory's Asignar Tags flow; visible/settable only when the Business's `nfcPerProductEnabled` Capability is on and this Product has no `barcode` — a Product is barcode-identified or NFC-tagging-eligible, never both. Never itself asserts that any specific unit is NFC-sellable (that stays a pure `InventoryUnit.tagId` read); turning it off never untags already-tagged units, only stops new tag-assignment going forward. See `decision-log.md` D71.
- **Supplier** — who merchandise was bought from. Present in the schema from v1, not yet exposed in any workflow.
- **Lot** — a merchandise receiving event (date, Supplier, the line items received that day). Owns its InventoryEntries and InventoryUnits. Carries `source` (`supplier_delivery` default | `correction`, D78) — distinguishes a real supplier receipt from a Lot generated by an upward InventoryCorrection; both flow through the identical InventoryEntry → InventoryUnit generation, never shown to the merchant.
- **InventoryEntry** — what the merchant actually types when registering a Lot: a Product + quantity + cost. Internal to Lot; never shown to the merchant as its own concept.
- **InventoryUnit** — one physical item, generated automatically from an InventoryEntry (typing "3 Hoodies" generates 3 InventoryUnit records). Carries a status: `available` → `reserved` → `sold`, plus `available` → `removed` (a correction leaving sellable inventory without a Sale — decrease-only originally, D77; bidirectional as of D78, see InventoryCorrection below). This is what actually gets sold and what preserves Lot traceability — the merchant never sees or thinks about it directly.
- **InventoryCorrection** — an append-only ledger entity, internal to Product, recording one correction to a Product's sellable count (either direction) without rewriting any historical receipt or Sale. Carries `type` (`increase` | `decrease`), `quantityDelta`, `unitIds` (unconditional on every row), `sourceLotId` (set only on `increase`, pointing at the `source='correction'` Lot that generated the new units). A decrease flips existing `available` units to `removed` (FIFO); an increase mints new `available` units through the ordinary Lot/InventoryEntry generation path. Never shown to the merchant as its own concept — she sees only "corregido a N (antes M)." See `decision-log.md` D77, D78, `product/99-rfc/0016-inventory-unit-bidirectional-correction.md`.
- **NFCTag** — a physical tag's UID, read from the tag's factory serial number (`NDEFReadingEvent.serialNumber` in Web NFC; `decision-log.md` D74) — Nahui never writes to a tag, so a blank factory tag is fully usable as-is — attached 1:1 to an InventoryUnit (only when NFC is available to the Business, per Selling Mode Capability — independent of any single Session, D79). Consumable — it leaves with the customer after the sale, or is released (deleted) if its InventoryUnit is corrected to `removed` (D77) — the model's one non-sale detachment case. **Consumability is physical, not a row deletion (clarified 2026-09-19):** `finalize_sale` never deletes the `NFCTag` row, so a `sold` unit keeps a non-null `tagId` — that persistence is what D10's dual-purpose resolution reads to tell a claim scan from a sale scan. `removed` is the only status whose write paths actually delete the row. Consequently **any count of tagged units must carry a status scope** (`status IN ('available','reserved')`, D80); an unqualified `tagId != null` counts garments the merchant has already sold. Carries `assignedAt` — when its physical attachment window began, written once at the scan that attaches it. See "Logical vs. physical identity" (`decision-log.md` D59): verified physical identity exists only during this window; nothing before it may be presented as physically verified.

## Selling context

- **Venue** — a place Ana sells (e.g., a specific bazaar location). Independent identity, referenced by ID from Event; multiple Events may share one Venue over time. Carries an `active` status independent of any single Event. Replaces what Event's freeform `Nombre` used to double as for identity/grouping, and carries the durable address/notes that replaces Event's former freeform `Lugar` field. See `decision-log.md` D20.
- **Event** — a scheduled occasion to sell. May span multiple days. Lightweight — Sessions reference it by ID, it does not own them. Always references exactly one Venue (required, not nullable) — Event no longer carries its own freeform name or location; both are Venue's. Type is one of a **closed** list for the current phase (Bazaar, Expo, Pop-up, Festival, Market, Office Sale — six values, not merchant-extensible) — see `decision-log.md` D16. The list may grow via a future product update, but is not open/self-service the way Product names are. Carries `bazaarCost` (optional, default `0`) — what attending this Event costs Ana (venue fee, optionally plus staffing); captured contextual data, not (in the MVP) an input to any profitability/margin computation. Owns **Price Override** (below). See `decision-log.md` D33.
- **Price Override** — an internal-only entity owned by Event (no identity or lookup outside its parent Event, the same shape as InventoryEntry under Lot): a `(Product, overridePrice)` pair recording that, for this specific Event only, a given Product's price differs from its `defaultPrice`. Pre-fills from the Product's `defaultPrice`, independently editable per Product — Ana adjusts only the selling-groups she actually wants to change for that Event, never a forced review of all of them. Never shown to the customer directly; consumed only by Price resolution (below). See `decision-log.md` D33.
- **EventAllocation** — how much of a Product's Business-wide stock is set aside for a specific Event, own aggregate root. Carries soft planning intent (`quantityPlanned`, zero pool effect) and hard commitment: a manual quantity (`quantityAllocated`, monotonic; `quantityRemaining`, **derived at read time as of D59, never stored**) and/or specific NFC-tagged `InventoryUnit`s — both modes now compose into one real, row-level committed set (`allocatedUnitIds`), never a forced choice and never a disconnected counter alongside it. Unique on `(eventId, productId)`. Not nested inside Event or Product — needed independently of either to resolve "what's allocated to this Event across every Product" and "what's allocated to this Product across every Event" (the second is what "Disponible en general" computes). Gains `commitAllocation()`/`releaseAllocation()` (D59) — real, row-level `InventoryUnit` reservations, generalizing the NFC scan mechanism to manual mode rather than gating a counter. `status: open | reconciled` — stays `open` through an Event's entire `closed` transition, for **either** mode; only an explicit merchant reconciliation action sets it `reconciled` — Event close never auto-releases anything, for either mode (D59). `decision-log.md` D57, D59.
- **AllocationMovement** — an append-only ledger entity internal to `EventAllocation` (no identity or lookup outside its parent, same class as `InventoryEntry`-under-`Lot`), never surfaced to Ana. One row per discrete allocation-affecting write (`initial_allocation` | `replenish` | `reallocate_in` | `reallocate_out` | `return_to_general` | `adjustment`). Carries `unitIds` (unconditional on every row as of D59, not NFC-only), `unitSource` (`scan` | `fifo_assignment`, D59 — how a unit entered `allocatedUnitIds`), `quantityExpected` (D59, manual-mode reconciliation writes only — what the merchant was asked to confirm against), and `counterpartEventAllocationId` on `reallocate_in`/`reallocate_out` pairs — the correlating key that makes an orphaned reallocation a well-defined query, not a heuristic match. `decision-log.md` D57, D59.
- **EventAssignment** — a standing record that a specific `BusinessMembership` is expected to sell at a specific `Event` (Selling context), own aggregate root. Unique on `(eventId, membershipId)`. Not nested inside Event or BusinessMembership — needed independently of either to resolve "who's assigned to this Event" and "which Events is this Membership assigned to." Plain-delete: unassigning removes the row outright, since no downstream write depends on a removed assignment surviving (contrast `BusinessMembership`/`Invitation`/`EventAllocation`'s soft-state discipline, each justified by a real historical dependent this concept has none of). Assigning a Membership to two date-overlapping Events is a warn-with-override case, never a hard block. `decision-log.md` D60.
- **Session** — one working day of selling. May optionally belong to an Event (`eventId`), or stand alone ("Quick Session"). Opens and closes independently.
- **Sale** — one transaction within a Session. References `sessionId`. Carries `performedByMembershipId` (required) — the acting `BusinessMembership` that finalized it, populated from already-resolved authorization context, never a new functional read into Identity; keeps resolving correctly even after that Membership is later revoked, since revocation never rewrites history (`decision-log.md` D58). Carries an opaque, signed **Claim Token**, generated at finalization whenever `subscriptionTier = paid` for the Business (regardless of `registrationMode`) — the artifact the merchant app displays (e.g. as a QR) so the customer can start the Loyalty-claim flow herself; a Free-tier Sale generates none. Whether it is actually shown to the customer for a given Paid-tier Sale is a per-interaction UI choice, not domain state (`decision-log.md` D40). Never the raw Sale ID — must not be guessable. See `decision-log.md` D22, D40, D58.
- **SaleItem** — exactly one InventoryUnit sold within a Sale. Not quantity-bearing — selling 2 Hoodies produces 2 SaleItems, because each may trace back to a different Lot. Carries `pricePaid`, resolved automatically at write time via Price resolution (this Event's Price Override for the sold Product if one exists, else the Product's `defaultPrice`) — never a merchant decision. This is what keeps Resultados' historical totals from silently drifting if a price is edited later. See `decision-log.md` D33. Also carries `eventAllocationId` (optional) — set once, at write time, to the `EventAllocation` its consumed unit was drawn from if one existed, else left unset for a plain Business-wide-pool consumption; never re-derived later, since `EventAllocation`'s own commit history is append-only and can't structurally distinguish a live commitment from an already-released one. See `decision-log.md` D67.

## Future: Loyalty-claim context (not built)

- **Customer** — a real aggregate root, owned by Loyalty-claim, **Business-scoped, not global**: identified through a post-sale claim mechanism (an NFC tag scan, a Sale-level Claim Token/QR scan, or a future mechanism), keyed to a single Business via `businessId` — the same physical person shopping at two different Nahui-powered Businesses produces two independent, unlinked Customer records. Carries `email` (required, captured at first Claim for that Business), optional `ageRange`/`gender`, and stored lifetime counters (`purchaseCount`, `lifetimeSpend`, `currentCycleProgress`, `completedCyclesCount`), updated incrementally as each Claim resolves. `maskedEmail` is a read-time derivation, not a stored field. Not an authenticated platform user — no login, no roles, no global Nahui customer account; the QR/Claim flow is identification, not authorization. Does not exist as a concept anywhere in the merchant application beyond the narrow Loyalty Participation Record view below — full Customer Identity otherwise belongs exclusively to the Loyalty platform. **Uniquely identified within a Business by `(businessId, email)`** — a returning customer's scan looks up her existing record for that pair rather than creating a duplicate. See `decision-log.md` D35, D37.
- **Claim** — the act of linking a Customer to an already-sold SaleItem. Entitled purely by `subscriptionTier` (`decision-log.md` D40) — a single capability, present in full when `subscriptionTier=paid`, structurally absent when `free`, resolvable through multiple mechanisms (NFC tag scan — unit-level; Sale-level Claim Token — resolves to one Claim per SaleItem in that Sale; future mechanisms) — all converging on the identical terminal write. Never creates a Sale. See `decision-log.md` D10 (the original NFC mechanism), D22 (the generalization to multiple mechanisms), and D40 (retiring the former `loyaltyEnabled` toggle in favor of tier-based entitlement).
- **Derived Customer Intelligence** — one of two forms in which customer-related information ever reaches the Merchant Application: an anonymized, aggregate signal (e.g., counts of frequent vs. occasional buyers) computed by Loyalty-claim from its Claims and exposed read-only to Intelligence. Contains no name, no contact information, and no per-Claim drill-down — ever. See `decision-log.md` D22.
- **Loyalty Participation Record** — the second, and only other, allowlisted form of customer-related information the Merchant Application may read — an *identified* (non-anonymized) view, alongside Derived Customer Intelligence, never a replacement for it. Not itself a stored entity: a fixed field projection of an existing Customer record, exposed read-only from Loyalty-claim to Intelligence. Consists of exactly: email or a derived masked-email display, age range, gender, purchase count, lifetime spend, and reward-cycle progress (current-cycle progress count, completed-cycles count), for a Customer belonging to the reading Business. Never phone, address, payment credentials, other unrelated personal data, or any Customer record belonging to another Business. Visibility gates on `subscriptionTier=paid` alone, same as Derived Customer Intelligence — never a second, separate merchant activation toggle. See `decision-log.md` D34, D35.

## Terms we deliberately do not use

- "Selling mode" as a per-Sale or per-Session choice — **retired framing, `decision-log.md` D79.** Buttons, barcode scanning, and NFC tag scanning are live, composable capabilities within every Session (see "NFC as a live, composable selling capability," `domain-model.md#key-mechanisms`) — never asked per Sale, never resolved once per Session either. Session Operating Mode / NFC Readiness (formerly the resolution mechanism here) are both retired, D79.
- "Bazaar" as the entity name — renamed to **Event** in the domain model (Bazaar is one Event type) even though it will likely stay "Bazaar" in Spanish UI copy for Ana specifically.
