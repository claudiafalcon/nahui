# Stage 7 — Backend Integration: Inventory, Selling, Events, Results

**Status: In progress, started 2026-09-13.** Working file per this folder's own knowledge-architecture discipline — holds what every dispatch touching this initiative actually needs, reduced to a pointer once complete (see `context/q24-q25-first-slice.md` for the precedent).

## What this is

Product Owner-directed: move the actual core product (Inventory, Selling/Sessions/Sales, Events, Results) off client-side/localStorage mock state onto the real Supabase Postgres backend, so two real pilot merchants' data survives browser clears/device switches and is visible to the business owner regardless of device. Authentication (WhatsApp OTP, Email, Google) already completed this migration earlier the same day — this is the much larger second half.

`architect`'s full Gap Analysis (2026-09-13) is the authoritative design reference — real Postgres schema for every aggregate, RLS policy design, sequencing, migration strategy, client-architecture changes. Not restated here in full; this file tracks status, decisions, and what changed as work actually lands.

## Decisions made, 2026-09-13 (Product Owner)

- **Existing local pilot data: clean cutover, no migration tool.** Confirmed by the Product Owner directly — the data only ever lived client-side, Nahui never had it centrally, so there's nothing to migrate from Nahui's own side even in principle.
- **Loyalty-claim's `customers`/`claims` tables: included now, same Supabase project** (not deferred, not a separate backend) — simplest choice at this scale, with the Merchant-App-never-reads-raw-Customer-data rule enforced via RLS, not just app-level convention.
- **Phone-OTP → real Supabase Auth session bridging: deferred, explicitly non-blocking.** `knowledge-mentor` confirmed there's no direct Admin API "mint a session" call — the documented pattern (`generateLink`+`verifyOtp` server-side) is unverified for phone-only/no-email users, and a possibly-simpler alternative (Supabase's "Send SMS Hook," letting the native phone-auth flow issue sessions automatically while still routing delivery through Twilio/WhatsApp) surfaced but needs real evaluation against why the current custom-Edge-Function approach was built instead. **Not resolved.** Deliberately not blocking Phase 0+, since phone/WhatsApp itself is separately blocked on Meta Business Verification (`company/business-decisions.md` Q19) and isn't going live for real users regardless — Phase 0 onward is being built to work correctly for Email/Google-authenticated merchants first, which is what real pilot users will actually use meanwhile.
- **RLS permission model confirmed against `product/02-ux/product-decisions.md`'s Q24/Q25 table** (not just the 3 OWNER-only actions `architect`'s own gap analysis initially named from the documents it read): OWNER — Business identity/Configuración, Catalog/Product management, Lot receiving/tagging, Event create/edit/pricing, allocate/replenish/reallocate/reconcile, invite/manage staff, business-level Resultados. SELLER — open/close own Session, register Sales, read sellable Products/prices (ungated), own current-session activity only. This is the authoritative permission table for every RLS policy across all phases, not just Phase 0's.

## Phase 1 design summary (`architect`, 2026-09-13 — full detail in the agent's own report, not restated here)

- **Six tables**, all Business-scoped with `business_id` denormalized directly onto every row (same pattern as Phase 0's `EventAllocation`/`EventAssignment` — lets every RLS policy call `is_active_member_of`/`is_active_owner_of` with no join): `suppliers` (D9's sanctioned exception — structurally present, zero UI, zero write RPC), `products` (gains `photo`/D54 and `barcode`/D65, `barcode` unique per `(business_id, barcode)` via a partial index so multiple NULLs coexist), `lots`, `inventory_entries` (`cost` present per D9, deliberately unused), `inventory_units` (the `available|reserved|sold` state machine, FIFO index on `(product_id, status, received_at)`), `nfc_tags` — a deliberate structural refinement from the prototype's inlined `InventoryUnit.tagId` scalar into its own table, giving `assignedAt` (D59) a real column.
- **Four SECURITY DEFINER RPCs**, OWNER-only, idempotency-keyed via the shared `idempotency_keys` table: `commit_lot` (mints new Products + Lot + InventoryEntry + InventoryUnit rows atomically — closes a real gap the prototype's own `commitLot()` doc comment flagged as unmet), `update_product_price`/`update_product_photo` (close the same flagged gap for `editPrice`/`setProductPhoto`), `assign_tag_to_next_pending_unit` (`SKIP LOCKED` FIFO-ordered tag assignment).
- **`products`/`inventory_units`/`nfc_tags` get SELECT-only RLS for any active member** (OWNER + SELLER) — matches the confirmed permission table's "SELLER: read sellable Products/prices ungated." **`inventory_units` deliberately gets no UPDATE policy at all in this phase** — status transitions belong to Selling-context RPCs (Phase 2), per the Foundation's own "Physical-location-exclusivity invariant."
- **Four open items, named not resolved:**
  1. **`Product.active` (`product-decisions.md` Q21) — resolved finding, not a live drift.** Checked directly: `domain-model.md`/`types.ts` never actually defined this field; D55's "same shape as `Product.active`" citation only ever borrowed Q21's *naming precedent*, and Q21 itself was never promoted into the Foundation (no decision-log entry, no `domain-model.md` update, no UX spec). **Applied directly (Architect Decision — `architecture-principles.md` #5, D9's own precedent against speculative schema-first modeling): not added to Phase 1's schema.** Q21 needs its own completion pass (Product Owner scope confirmation → `ux-designer` → a real decision-log entry, matching D54/D65's pattern) before it belongs in a permanent table.
  2. **`Product.photo` storage mechanism — NOT resolved, `reviewer` process-gap finding, 2026-09-13.** `architect` recommended real Supabase Storage (a bucket + the `photo text` column holding a path/URL) over inheriting the prototype mock's inline base64-data-URL shape, citing real costs given `Product.photo`/D54 is already live and merchant-facing for 2 real pilot merchants: row bloat, no CDN, Postgres text-column limits under load. `builder`'s Phase 1 implementation kept the data-URL shape instead and its own migration comment presented that as a settled, disclosed-and-done deferral rather than routing the deviation from architect's explicit recommendation back through Decision Ownership — the process gap `reviewer` flagged. Corrected (`20260913033000_inventory_persistence_layer_fixes.sql`): the column is now documented as **provisionally deferred, pending architect reconfirmation**, tracked as a real open item below, not a footnote. Building real Supabase Storage wiring itself (bucket, upload flow, URL generation) is separate, unscoped work — not done by that fix migration either.
  3. **`nfc_tags` as its own table** (vs. the prototype's inlined `tagId` scalar) — a real, deliberate shape change `builder` needs to account for when replacing `InventoryUnit.tagId` reads with a join/derived read.
  4. Barcode collision/confirm-on-scan UX (D65) — `ux-designer`'s call, in progress, doesn't block this schema (the uniqueness constraint + `barcode_already_registered` error surface are enforced regardless of what flow ships).

## Phase 2 design summary (`architect`, 2026-09-13 — full detail in the agent's own report, not restated here)

- **Six tables**: `venues` (minimal, matching the prototype's own `id`/`displayName` shape — no speculative `address`/`notes`/`active` columns, same restraint D26 already established for `Sale.claimToken`), `events` (status computed live from dates + `cancelledAt`, never a stored column — matches the already-built prototype exactly, no D53 overlap/uniqueness constraint since simultaneous multi-Event operation is the confirmed invariant), `price_overrides` (a real table, not a jsonb column, following Phase 1's own resolved precedent for internal-only entities of this class), `sessions` (gains `openedByMembershipId`, D66; a partial unique index makes "one active Session per Membership" a real hard constraint), `sales` (its own aggregate root, never nested in Session, specifically so Sale writes never contend on a shared Session lock — the `<3s` bar; a partial unique index enforces "at most one open Sale per Session"), `sale_items` (internal-only, `unit_id` uniqueness structurally enforces "a unit sells at most once, ever").
- **Confirmed out of scope for this phase, three independent ways**: `EventAllocation`/`AllocationMovement` (Phase 2b) and `EventAssignment` (Phase 2c) — neither has a hard FK dependency *into* this phase's tables, and `home.md`'s "lost the race" pattern is explicitly `EventAllocation`-scoped, not a general Sale-write mechanism. `add_item_to_sale` does plain Business-wide FIFO only, with one explicit comment marking exactly where Phase 2b's own compare-and-swap will extend it later — an addition, not a redesign.
- **Seven SECURITY DEFINER RPCs**: `create_event` (atomic venue create-or-reuse + Event insert, full idempotency treatment), `cancel_event` (naturally-idempotent status flip, no key needed — matches `revoke_membership`'s own precedent), `set_price_override` (upsert, light idempotency), `start_session` (naturally safe under concurrent double-submission via `ON CONFLICT` against the new partial unique index — no client-supplied key needed), `add_item_to_sale` (the `<3s`-critical write — `FOR UPDATE SKIP LOCKED` FIFO pick + atomic `available→reserved` flip in one transaction, the identical concurrency-safety mechanism `assign_tag_to_next_pending_unit` already established in Phase 1), `add_item_to_sale_by_tag` (nfc-mode counterpart, one-unit lookup instead of FIFO scan), `finalize_sale`/`cancel_sale`/`remove_sale_item`/`close_session` (the remaining Sale/Session lifecycle writes — `close_session` deliberately does not independently block on an open Sale, matching `store.tsx`'s own existing behavior; that guarantee lives in the UI flow, not a new server-side check an approved spec never called for).
- **Two direct Architect Decisions, applied to the Foundation in this same pass** (`decision-log.md` D66): `Session.openedByMembershipId` — a real, permanent column, not a prototype-only artifact as its own doc comment had framed it; RFC 0008 §7's "zero schema change" claim reasoned correctly about uniqueness/relationships but never separately addressed attribution. "One active Session per Membership" — confirmed as a real, already-enforced (in `store.tsx`) invariant that was simply never promoted into `domain-model.md`'s text; now a real partial unique index.
- **Two genuine absences, correctly not built**: a general Event-edit RPC (venue/type/dates) — no approved spec or built code calls for one; speculative `venues` columns (`address`/`notes`/`active`) — no UI surfaces them.

## Phase 2b design summary (`architect`, 2026-09-13 — full detail in the agent's own report, not restated here)

- **Three tables**: `event_allocations` (root; `quantityRemaining` deliberately NOT a stored column per D59 — derived at read time), `event_allocation_units` (new, the D59-mandated real row-level replacement for the client's `allocatedUnitIds[]` array — needed because the release/compare-and-swap logic requires an indexed, lockable `SELECT ... FOR UPDATE` over it, which an array column can't support), `allocation_movements` (write-once audit ledger, array columns fine here since it's never a selection target).
- **Two private (unexposed) SQL helpers factor out D59's two core mechanisms**, reused by every public RPC: `_fifo_commit_to_allocation` (generalizes NFC's `available→reserved` conditional write to manual mode, `FOR UPDATE SKIP LOCKED`, partial-fulfillment tolerant) and `_release_from_allocation` (most-recently-committed-first release, flips `event_allocations.status→reconciled` only when a `return_to_general` release leaves zero reserved units of either source).
- **Seven public SECURITY DEFINER RPCs**: `save_event_allocations` (bulk manual-mode allocate/replenish, `commit_lot`-shaped batch write), `scan_unit_into_event_allocation` (NFC-mode, live per-scan), `reallocate_event_allocation` (D57's single-transaction move between two simultaneously-active Events, handles both manual-quantity and specific-tag moves), `return_scanned_units_to_general`/`reconcile_manual_allocation` (the two Event-close reconciliation paths), plus the two private helpers above.
- **A real, necessary finding beyond what was asked, correctly flagged rather than silently expanding scope: once a unit is committed to an `EventAllocation` its status flips to `reserved`, making it invisible to Phase 2's existing `add_item_to_sale`/`add_item_to_sale_by_tag` (both currently filter on `status='available'` only) — the actual server-side half of the "lost the race" mechanism requires extending both, and `remove_sale_item`/`cancel_sale` need a matching correction** (an allocated unit removed from an in-progress Sale must revert to `reserved`, not `available` — releasing it from the Sale must never silently release it from the Event's own allocation too). All four are already-shipped, already-reviewed Phase 2 functions; extending them is in scope for this phase's build, not deferred.
- **Five open items, four still open**: (1) the four Phase 2 function extensions above weren't explicitly named in the original dispatch scope but are structurally required — recommended as in-scope for this build; (2) no dedicated Sale-time copy exists for a tag scanned mid-Sale that resolves to a unit reserved by a *different* Event's allocation (reuses the generic `no_match` framing — a `ux-designer` call, not resolved here); (3) ~~D57's own still-open Q20~~ **Resolved 2026-09-13, `architect-questions.md`** — NFC Readiness's `available`-status filter automatically excludes any unit committed to an open `EventAllocation`, by construction (both commit paths flip `InventoryUnit.status` to `reserved` via the same field Readiness reads live, no new schema needed); (4) `allocation_movements`' `unit_source` column can't cleanly represent a hypothetical mixed manual+scan single reallocation call — the UI as specified never produces this shape, but the RPC signature doesn't structurally forbid it; worth a one-line `ux-designer` confirmation; (5) D59's own flagged RFC 0010 Open Item 7 (stale counter-mechanism copy in `home.md`) appears already swept on inspection, but not independently line-by-line re-verified — recommend `reviewer` do a final confirmation pass.

## Phase 2c design summary (`architect`, 2026-09-13 — full detail in the agent's own report, not restated here)

- **One table**: `event_assignments` — plain `(event_id, membership_id)` pairing, `business_id` carried directly for the SELLER-resolution query, unique on `(event_id, membership_id)`. Plain hard-delete, no `status` column — matches RFC 0011 §1's own explicit justification (no downstream write ever references a row here directly, unlike `business_memberships.status`).
- **RLS reuses Phase 2's own established shape verbatim**: OWNER reads every row for her Business (needed for §3.26's live conflict-warning line, which checks every *other* assignment for every listed Membership, not just this Event's own roster); a SELLER reads only her own rows via `caller_membership_id`.
- **Two RPCs, both correctly key-free**: `assign_to_event` (`ON CONFLICT DO NOTHING` — assigning an already-assigned Membership is a safe no-op) and `unassign_from_event` (a no-op delete on an already-unassigned pair is already correct) — neither needs a client-supplied idempotency key under `architecture-principles.md` #7's own test, both directions explicitly checked, not assumed. Both re-verify their target ids belong to the calling Business (the same defensive check Phase 2's own round-1 review found missing on `start_session`/`set_price_override`, applied here from the start) and that the target Membership is `active` (RFC 0011 Open Item 4, already resolved by D60, re-checked server-side).
- **The scheduling-conflict warning needs no new RPC at all** — confirmed purely a client-side computation against data the RLS design already grants in the same round trips the screen needs anyway (every `event_assignments` row + every `events` row for the Business), matching the "never a stored flag that could go stale" pattern `Event.status` already established. The write itself carries zero awareness of the check, correctly preserving RFC 0011's "warn, never block" rule.
- **No status gate on assign/unassign, deliberately** — unlike `set_price_override`'s Event-status check, `events.md` §3.26 is reachable from both the `scheduled` and `active` Event-detail screens; adding a gate would invent a restriction the Approved UX never calls for.
- **One item correctly left undesigned, matching where the UX spec itself already flagged it**: orphaned `event_assignments` rows after a Membership revocation — not a referential-integrity question (Memberships are never hard-deleted), a data-hygiene one with no live merchant-facing dependency; `events.md` §3.26's own "Future considerations" section already names this as open, not resolved here.

## Read-side data hydration design (`architect`, 2026-09-14 — full detail in the agent's own two-part report, not restated here)

- **Pure Architect Decision, no RFC needed** — additive composition over RLS access already granted on every table; touches no aggregate boundary, no ubiquitous-language term, no bounded context. Explicitly excludes Loyalty-claim (`customers`/`claims`) — a hard guardrail, never queried.
- **One `hydrateFromBackend(businessId)` function**, `Promise.all` of one `.select('*')` per domain table (every `AppState` array slice gets a matching query) — not partitioned per-tab, since `AppState.business` is already singular and RLS already does all the role-narrowing server-side (a SELLER and an OWNER issue the identical query).
- **Triggers**: once on mount when auth resolves to a real `business_id`/`membership_id`; again on `visibilitychange` → visible (tab regains focus); again on Resultados' own mount. Not per-tap, not polling — matches `architecture-principles.md` #1's "resolved once, upstream" discipline and the `<3s` bar's inability to tolerate a live fetch on the Selling path.
- **Composition with the existing write-mirror pattern — the one genuinely hard part, resolved via a `knowledge-mentor` consultation plus a second design pass.** Confirmed via Supabase's own documentation (not assumed): the standard tier has no Read Replica, so every `.select()`/`.rpc()` reads the one primary Postgres instance — no async replication lag to guard against. The real risk is a same-tab race between an in-flight write's local mirror and a concurrent hydration read, in **both** directions (a write starting before hydration, and a write starting *during* an already-in-flight hydration and landing first) — the second direction was missed in the first design pass, caught by `knowledge-mentor`, and closed in a follow-up. **Final mechanism: a monotonic write-generation counter** (`writeGenerationRef`, incremented by a new `applyWriteMirror()` helper that replaces the raw `setState` call at all 22 existing write-mirror sites — mechanical, same updater body, no logic change). `hydrateFromBackend` captures the generation before issuing its reads and re-checks it after they resolve, before applying anything — a mismatch means a write landed mid-cycle, so that cycle's snapshot is discarded outright (never merged), retried up to twice, then abandoned for the next natural trigger. Never risks correctness for freshness: a discarded cycle leaves the write's own already-applied mirror untouched.
- **Wholesale-replace each state slice on hydration, never a per-row merge** — the domain model has no `updated_at`/version columns to support a merge, and inventing one now would be exactly the speculative schema-first modeling `architecture-principles.md` #5 warns against with no observed need.
- **Loading/error states need no new UX design** — `home.md`/`inventory.md`/`events.md`/`reports.md`'s existing §3.1 (near-instant skeleton)/§3.2 (slow "Un momento…")/§3.14-or-equivalent (defensive fallback) states were already designed generically, latency-and-failure-agnostic; this is pure implementation, wiring a real Promise's pending/resolved/rejected states into already-Approved branches.
- **Real-time (live cross-device updates) explicitly out of scope** — no Approved UX spec calls for it; deferred as a named future improvement that composes cleanly later on the same RLS, no schema change needed.
- **One new piece of state**: a transient `hydrationStatus: 'idle'|'loading'|'ready'|'error'`, not persisted to `localStorage`/`AppState` (not domain data).

## Phase 3 (Results/Resultados) design summary (`architect`, 2026-09-14 — full detail in the agent's own report, not restated here)

- **No new tables, no new RLS policies** — every figure `reports.md` shows is a read-side sum/count/grouping over rows Phases 1/2/2b already persist (`sales`, `sale_items`, `sessions`, `events`, `venues`, `products`). Confirmed neither "ticket promedio" nor "Top productos" needs a materialized aggregate at pilot scale (low hundreds of rows) — a live query is sufficient, and a materialized one would reintroduce a dual-write consistency risk for no real performance need.
- **Existing RLS already shapes correctly**: OWNER reads every row for her Business, a SELLER reads only her own (already true today for `sales`/`sale_items`/`sessions`). Resultados' OWNER-only *screen* restriction is a navigation-layer decision, not a new security boundary — a SELLER's RLS-scoped query would just silently return a partial, misleadingly-labeled Business-wide figure, which is why the tab stays OWNER-only, the same pattern `home.md`'s own role-scoped resolution already establishes.
- **Recommendation: reuse the existing, already-reviewed pure functions in `selectors.ts` verbatim** (`allTimeTotals`, `topProductsAllTime`, `sessionTotals`, `eventRollup`, `venuePerformance`, etc.) over real fetched data instead of mock arrays — never a second, parallel SQL reimplementation of the same computations, which would risk exactly the kind of silent drift D33/D27's "capture business truth once" discipline exists to prevent.
- **Never re-reads `price_overrides` or `products.default_price` to compute a dollar figure** — every figure is `sale_items.price_paid`, already resolved once at Sale-write time (D33's Price Resolution). Named explicitly so `builder` doesn't reintroduce a second pricing computation.
- **Real, named documentation gap**: `reports.md` itself never states its own OWNER-only scope anywhere in its text (unlike `home.md`/`events.md`/`settings.md`, all amended for the Q24/Q25 SELLER-experience pass) — a plain, additive fix needed before `builder` treats the nav gate as canonical rather than inferred. Routed to `ux-designer`.
- **"Tus clientes" confirmed fully out of scope** — no `customers`/`claims` tables exist anywhere; the client correctly renders the zero-Claims empty state unconditionally. Not a decision to revisit, a structural fact (no `Customer` rows can exist yet).
- **A named future scaling boundary, not a defect today**: the fetch-and-reduce approach stops being cheap once a Business accumulates months of daily selling (thousands-plus `sale_items`) — a future pass would add server-side aggregate views/RPCs and a composite index at that point, not now.
